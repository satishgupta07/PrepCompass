How JavaScript runs

“Everything in JS happens inside the Execution Context.”

1 The Execution Context step 0

In plain words

Think of a kitchen. The pantry holds every ingredient (your variables and functions). The chef follows the recipe one line at a time. Together they are the Execution Context (EC). Whenever JS runs code, it builds a kitchen first.

  • Memory component (Variable Environment): stores variables and functions as key:value pairs
  • Code component (Thread of Execution): runs the code one line at a time, in order
  • so JS is synchronous and single-threaded: it can’t do two things at once

2 Two phases of execution

When a program starts, JS creates the Global Execution Context (GEC) and fills it in two passes.

  • Phase 1 · Memory creation: scans the code before running it
    • var → space reserved, value = undefined
    • function declarations → the whole function body is stored
    • let/const → space reserved but locked in the Temporal Dead Zone
  • Phase 2 · Code execution: runs line by line
    • real values replace undefined
    • a function call creates a brand-new EC with its own two phases
    • when the function returns, that EC is thrown away
var n = 2
function square(num) { var ans = num * num; return ans }
var square2 = square(n)
var square4 = square(4)

Walk through it:

momentmemory (global)
after phase 1n: undefined · square: {function body} · square2: undefined · square4: undefined
line 1 runsn: 2
square(n) callednew EC → num: 2, ans: undefined → ans: 4 → returns 4 → EC deleted
line 3 finishessquare2: 4 (then the same dance for square(4) → square4: 16)

3 The Call Stack

In plain words

A stack of plates. A function call puts a plate on top, a return takes it off. JS only works on the plate at the top.

  • GEC is pushed when the program starts; each call pushes a new EC; each return pops it; GEC pops at the very end
  • also called Program Stack, Control Stack, Runtime Stack, Machine Stack, Execution Context Stack
Stack overflow + added

The stack has a size limit. A function that keeps calling itself with no end fills it up and JS throws RangeError: Maximum call stack size exceeded. Every recursive function needs a base case (a condition where it stops calling itself).

function boom() { boom() }
boom()  // RangeError

Also: “hoisting” is a mental model. Nothing physically moves; the engine just creates the bindings when it enters an EC.

Remember!
  • EC = memory + code
  • JS does one thing at a time
  • call = push, return = pop

Variables & data types

1 Variables step 1

In plain words

A variable is a labelled box that holds a value. JS gives you three kinds of label, and they differ in where the box is visible (scope) and whether you can put a new value in it (reassignment).

keywordscopereassign?advice
constblocknodefault choice: signals “this won’t change”
letblockyescounters, loop variables
varfunctionyesavoid: leaks out of if / for blocks
const accountId = 144553        // cannot be changed
let accountEmail = "a@b.com"    // can be updated
var accountPassword = "123"     // avoid
const ≠ immutable + added

const locks the label, not the contents. You can’t point it at a new object, but you can still change what’s inside the object it points to.

const user = { name: "A" }
user.name = "B"     // OK, object mutated
user = {}           // TypeError, reassignment

2 Data types step 2

In plain words

JS is dynamically typed: the value has a type, not the variable. var a = 5 can later become a = "hello". Every value is either a primitive (a simple value) or a reference (an object).

Reference types: Object, Array, Function.

typeof null === "object" is an old JS bug. null is NOT an object.

undefined vs “not defined”

  • undefined = the variable exists (memory was reserved in phase 1) but has no value yet
  • not defined = never declared anywhere → ReferenceError
  • never assign undefined yourself; let JS do it
console.log(x)   // undefined (var x was hoisted)
var x = 25
console.log(a)   // ReferenceError: a is not defined

Stack vs Heap

In plain words

Primitives live right inside the variable, so copying makes an independent copy. Objects live in a big shared area (the heap); the variable only holds an address. Copying the variable copies the address, so both variables point to the same object, like two people holding keys to one house.

let a = "hello"; let b = a; b = "world"
console.log(a)             // "hello": independent

let o1 = { email: "a@b.com" }; let o2 = o1
o2.email = "x@y.com"
console.log(o1.email)      // "x@y.com": same object!
Number gotchas & copying objects + added
  • 0.1 + 0.2 gives 0.30000000000000004 (binary floating point). Compare with a tolerance or work in integers (paise/cents)
  • NaN !== NaN; test with Number.isNaN(x). typeof NaN is "number"
  • all typeof results: undefined, boolean, number, bigint, string, symbol, object, function
  • shallow copy {...obj} / [...arr] copies the top level only; nested objects are still shared
  • deep copy structuredClone(obj) (can’t copy functions)
Remember!
  • const → let → never var
  • primitives copy, objects share
  • typeof null is “object” (bug)

Hoisting, TDZ & shadowing

1 Hoisting step 3

In plain words

Remember phase 1 of the Execution Context? JS reserves memory for variables and functions before running any code. That’s hoisting. It’s why you can call a function above where it is written, but you can’t use a variable’s value above its assignment.

declarationhoisted?what you see before its line
var variableyesundefined
function declarationyesthe full function, callable right away
var f = function(){}partlyf is undefined → calling it = TypeError
let / constyes (to the TDZ)not accessible → ReferenceError
getName()           // "Namaste JavaScript" – works!
console.log(x)      // undefined
var x = 7
function getName() { console.log("Namaste JavaScript") }

// greet()          // TypeError: greet is not a function
var greet = function () { console.log("Hi!") }
greet()             // "Hi!" – works after assignment

Key insight: hoisting isn’t magic. The engine makes two passes, memory setup first, execution second. That explains most “why does this work?!” moments.

2 Temporal Dead Zone (TDZ) step 4

The TDZ is the gap between let/const being hoisted and its line actually running. Touching the variable in that gap throws a ReferenceError. Best practice: declare at the top of the block so the gap is zero.

// console.log(a)   // ReferenceError: Cannot access 'a' before initialization
let a = 10          // TDZ ends here
console.log(a)      // 10

3 Block scope

A block is anything inside { } (if, for, plain braces). let and const stay inside it; var ignores blocks and leaks out.

{
  var leaks = "visible outside"
  let stays = "invisible outside"
}
console.log(leaks)    // "visible outside"
// console.log(stays) // ReferenceError

4 Shadowing

In plain words

If an inner block declares a name that already exists outside, the inner one “shadows” (hides) the outer one while you’re inside. With let/const they are two separate variables. With var there is only one, so the outer one gets overwritten.

let score = 100
{ let score = 20; console.log(score) }   // 20
console.log(score)                       // 100, unchanged

var count = 100
{ var count = 10; console.log(count) }   // 10
console.log(count)                       // 10, outer was modified!

Illegal shadowing: you can’t shadow a let with var in the same scope (the var would leak into the scope where the let lives). let shadowing let is fine.

Remember!
  • function declarations: fully hoisted
  • let/const: hoisted but in TDZ
  • var doesn’t shadow, it overwrites

Type conversion & comparison

1 Type conversion step 5

In plain words

JS quietly converts values to other types when an operator needs it (coercion). You can also convert on purpose (explicit conversion). Knowing the rules stops the weird bugs.

Number("33")     // 33
Number("33abc")  // NaN  (invalid conversion)
Number(true)     // 1
Boolean("")      // false
Boolean("hi")    // true
String(42)       // "42"

The + operator has two jobs

Addition for numbers, concatenation for strings. JS reads left to right, and once a string appears everything after is joined as text.

"1" + 2 + 2   // "122": "1"+2 → "12", then "12"+2 → "122"
1 + 2 + "2"   // "32":  1+2 = 3, then 3+"2" → "32"

Increment timing

let x = 5
console.log(x++)  // 5: returns THEN increments (post)
console.log(++x)  // 7: increments THEN returns (pre)
More coercion rules + added
  • - * / always produce numbers: "5" - 2 is 3, but "5" + 2 is "52"
  • parseInt("42px") → 42 (stops at the first invalid char); Number("42px") → NaN
  • give parseInt a radix: parseInt("08", 10)

2 Comparison operators step 6

In plain words

== converts types first, then compares (surprising). === compares type and value with no conversion (predictable). Always use ===.

"2" === 2        // false: different types
null > 0         // false  (null → 0, so 0 > 0)
null == 0        // false  (== treats null specially)
null >= 0        // true   (null → 0, so 0 >= 0)  ← surprising!
undefined == 0   // false
undefined > 0    // false  (undefined → NaN; NaN comparisons are always false)

Never use < > <= >= with null or undefined; the results are inconsistent.

More == surprises + added
  • 0 == "" true · "0" == false true · null == undefined true (equal only to each other)
  • Object.is(NaN, NaN) is true while NaN === NaN is false
Remember!
  • === always
  • + concatenates once a string appears
  • NaN is never equal to anything

Strings, numbers & dates

1 Strings step 7

In plain words

A string is text. Strings are immutable: you can’t edit one in place. Every string method hands back a new string and leaves the original alone. Write them with single quotes, double quotes, or backticks (template literals).

const name = "hitesh"
`Hello ${name}`            // template literal: embeds expressions, can span lines

str.charAt(2)              // char at index 2
str.indexOf('t')           // first position (-1 if not found)
str.substring(0, 4)        // chars 0..3 (no negatives)
str.slice(-8, 4)           // like substring, negatives count from the end
str.trim()                 // strip whitespace both ends
str.replace('%20', '-')    // replaces the FIRST match only
str.includes('hello')      // true / false
str.split('-')             // → array
str.toUpperCase()
Handy extras + added

replaceAll, startsWith, endsWith, padStart(2,"0"), at(-1) (last character).

2 Numbers & Math step 8

JS has one Number type for integers and decimals (IEEE 754 double). Precise up to 2^53 − 1; beyond that use BigInt.

(123.8966).toFixed(2)              // "123.90"  rounds, returns a STRING
(123.8966).toPrecision(4)          // "123.9"   4 significant digits (string)
(1000000).toLocaleString('en-IN')  // "10,00,000"

Math.abs(-4)     // 4      Math.round(4.6)  // 5
Math.ceil(4.2)   // 5      (always up)
Math.floor(4.9)  // 4      (always down)
Math.min(4, 3)   // 3      Math.max(4, 3)   // 4
Math.random()    // 0 ≤ x < 1

// random integer from min to max, both included
Math.floor(Math.random() * (max - min + 1)) + min

3 Dates step 9

In plain words

A Date secretly stores one number: milliseconds since 1 Jan 1970 UTC (the Unix Epoch). Everything else (year, month, weekday) is calculated from it, which is why timestamps work the same in every timezone.

  • months are 0-indexed (0 = January, 11 = December); days of the month are 1–31; weekdays start at 0 = Sunday
new Date()                 // now
new Date(2023, 0, 23)      // 23 Jan 2023: month 0!
new Date("2023-01-14")     // ISO string, most reliable format

date.getFullYear()    date.getMonth() + 1    date.getDate()    date.getDay()
Date.now()            // ms since epoch (IDs, timing)
date.getTime()
Timezone trap & strict mode + added
  • new Date("2023-01-14") is read as UTC, new Date(2023, 0, 14) as local time; they can differ by a day
  • use toISOString() for APIs and Intl.DateTimeFormat for display
  • strict mode ("use strict"): undeclared assignment throws and plain-function this is undefined. Modules and classes are strict automatically
Remember!
  • strings: new string every time
  • toFixed returns a string
  • months start at 0

Control flow & loops

1 Control flow step 10

In plain words

Control flow decides which code runs and when. In any condition, JS treats every value as truthy or falsy, so if (value) works even when value isn’t a boolean.

  • Only 8 falsy values: false 0 -0 0n "" null undefined NaN
  • truthy even though they look empty: "0", [], {}, function(){}
if (score > 90) { ... } else if (score > 60) { ... } else { ... }

// switch uses ===; add break or it falls through to the next case
switch (month) {
  case "jan": console.log("January"); break;
  default:    console.log("Other");   break;
}

age >= 18 ? "adult" : "minor"        // ternary = compact if/else

let val = userInput ?? "default"     // ?? : right side only if left is null/undefined
Short-circuit + added

a || b returns the first truthy value; a && b returns the first falsy value (or the last). So user && user.name avoids a crash when user is null (today you’d write user?.name).

2 Loops step 11

Loops repeat a block of code. Picking the right one keeps code clear.

loopbest for
forknown number of iterations
whileunknown count, condition checked before the body
do…whilemust run at least once
for…ofVALUES of arrays, strings, Maps, Sets
for…inKEYS of plain objects
for (let i = 0; i < 10; i++) { }
while (condition) { }
do { } while (condition)
for (const item of array) { }                        // "js", "ruby", "python"
for (const key in object) { console.log(key, object[key]) }
  • break leaves the loop completely · continue skips only the current round
Loop pitfalls + added
  • for…in on an array gives string indexes (and can include inherited properties); use for…of
  • forEach can’t break or return early; use for…of, some or every
Remember!
  • falsy list = 8 values
  • switch needs break
  • of = values, in = keys

Functions

1 Functions step 12

In plain words

A function is a reusable recipe: write it once, run it whenever you call it. In JS, functions are first-class citizens: they’re values like numbers, so you can store them in variables, pass them in, and return them. That one property is why map and filter exist.

  • Declaration is hoisted (callable before it appears); expression is not
  • Default parameter: used when the argument is missing or undefined
  • Rest parameter ...rest gathers all remaining arguments into an array; it must be LAST
  • objects/arrays are passed as references, so mutating them inside changes the original
function add(a, b) { return a + b }
function greet(name = "Guest") { return `Hello ${name}` }
greet()            // "Hello Guest"

function cart(a, b, ...rest) { return rest }
cart(1, 2, 3, 4, 5)   // [3, 4, 5]
Small but important + added
  • no return → the function returns undefined
  • parameter = name in the definition; argument = value you pass in
  • spread in a call: Math.max(...arr)
  • pure function: same input → same output, no side effects (easiest to test)

2 First-class functions step 13

typehoisted?syntax

named expressionnoconst foo = function bar(){}
anonymousnofunction(){} (must be used as a value)

[1, 2, 3].map(x => x * 2)                    // function passed IN

const double = makeMultiplier(2); double(5)  // 10

var factorial = function compute(n) { return n <= 1 ? 1 : n * compute(n - 1) }
// the name "compute" exists only inside (useful for recursion)

3 Arrow functions step 14

ES6 short syntax, ideal for callbacks. The big difference: an arrow has no this of its own. It borrows this from the place it was written (lexical). A regular function gets this from whoever calls it (dynamic).

const add = (a, b) => { return a + b }   // block body: explicit return
const add = (a, b) => a + b              // implicit return
const double = a => a * 2                // one param: parens optional
const makeObj = a => ({ value: a })      // wrap object literal in ( )
  • rule of thumb: methods → regular function · callbacks → arrow
Arrow limits + added

No arguments object, can’t be used with new, no prototype.

4 IIFE step 15

An Immediately Invoked Function Expression defines and runs a function in one step. The outer ( ) makes it an expression; the trailing ( ) calls it. Use it to run setup once, create a private scope, and avoid polluting globals.

(function init() { console.log("Runs immediately") })();
((name) => { console.log(`Hello ${name}`) })('hitesh');
Remember!
  • functions are values
  • arrow: no own this
  • declaration hoisted, expression not

Arrays

1 Arrays: basics step 16

In plain words

An array is an ordered numbered list. It grows and shrinks by itself, can mix types, and starts counting at 0. Under the hood it’s a special kind of object.

  • mutating methods (change the original): push add to end · pop remove last · unshift add to start · shift remove first

slice vs splice: the most confused pair

The sort() trap + added

Default sort() compares items as strings and mutates the array.

[10, 9, 1].sort()                  // [1, 10, 9]
[10, 9, 1].sort((a, b) => a - b)   // [1, 9, 10]

Non-mutating versions (ES2023): toSorted, toReversed, with; check browser support. Use includes(x) to test membership.

2 Arrays: advanced step 17

  • Merging: [...arr1, ...arr2] (spread, preferred, makes a new array) or arr1.concat(arr2)

arr1.push(arr2) is wrong for merging: it nests arr2 as ONE element.

Array.isArray(val)       // the only reliable array check

Array.from({name:"x"})   // []   plain objects aren't iterable
Array.of(1, 2, 3)        // [1,2,3]  (new Array(3) makes 3 EMPTY slots)
Array destructuring + added

Unpack values into variables in one line, and swap without a temp variable.

const [first, second, ...others] = [1, 2, 3, 4]
let a = 1, b = 2;
[a, b] = [b, a]
Remember!
  • slice copies · splice mutates
  • merge with spread
  • sort() needs a compare fn for numbers

Objects

1 Objects: basics step 18

In plain words

An object is a bag of labelled values (key–value pairs). Keys are strings or Symbols; values can be anything, including functions and other objects. Almost everything in JS is an object, so this is the foundation.

  • dot notation by default · bracket notation when the key has spaces, is dynamic, or is a Symbol
  • Object.freeze(obj) blocks further changes (they silently fail)
  • a function stored in an object is a method; inside it, this is the object
const sym = Symbol("key1")
const obj = {
  name: "Hitesh",
  "full name": "Hitesh C",     // bracket notation needed
  [sym]: "mykey1",             // Symbol key
  age: 18,
}
obj.name   obj["full name"]   obj[sym]
obj.greet = function () { console.log(`Hi ${this.name}`) }
Object extras + added
  • Object.freeze is shallow: nested objects can still change
  • shorthand { name, age } · computed key { [k]: v }
  • "key" in obj tests existence · delete obj.key removes it

2 Objects: advanced step 19

Merging: spread makes a new object; Object.assign writes into its first argument (so pass {} first).

const merged = { ...obj1, ...obj2 }      // new object, preferred
Object.assign({}, obj1, obj2)            // also new (target is {})
// { obj1, obj2 }  ← NESTS them, does NOT merge

Inspecting:

Object.keys(obj)           // property names
Object.values(obj)         // values
Object.entries(obj)        // [[key, value], ...]
obj.hasOwnProperty('key')  // own property (not inherited)?

Destructuring pulls properties into variables; renaming avoids clashes.

const course = { coursename: "js", price: "999", courseInstructor: "hitesh" }
const { courseInstructor } = course
const { courseInstructor: instructor } = course
console.log(instructor)   // "hitesh"
Destructuring power + added 
const { a = 1, b: { c } = {}, ...rest } = obj    // default, nested, rest
Object.fromEntries(Object.entries(o).map(([k, v]) => [k, v * 2]))
Object.hasOwn(obj, "k")                          // modern hasOwnProperty
Remember!
  • spread merges, {obj1,obj2} nests
  • freeze is shallow
  • bracket notation for odd keys

map, filter, reduce

1 Higher-order functions step 20

In plain words

A higher-order function (HOF) takes a function or returns one. The function you pass in is the callback. The payoff is DRY code: instead of rewriting a loop for every job, write the loop once and pass in what to do.

// ❌ one loop per operation
const calculateArea = (radius) => {
  const output = []
  for (let i = 0; i < radius.length; i++) output.push(Math.PI * radius[i] * radius[i])
  return output
}

// ✅ separate the "what" from the "how"
const area = r => Math.PI * r * r
const circumference = r => 2 * Math.PI * r
const calculate = (radiusArr, operation) => radiusArr.map(operation)
calculate([1, 2, 3, 4], area)
calculate([1, 2, 3, 4], circumference)

2 The big four

methodreturnschanges original?purpose
forEachundefinednoside effects only; can’t chain
filtershorter new arraynokeep elements that match

In plain words

map = convert each item. filter = keep some items. reduce = fold everything into one thing (a sum, a max, an object). The acc (accumulator) carries the running result from item to item.

const arr = [5, 1, 3, 2, 6]
arr.map(x => x * 2)                                      // [10, 2, 6, 4, 12]
arr.map(x => x.toString(2))                              // binary strings
arr.filter(x => x % 2)                                   // odd: [5, 1, 3]
arr.reduce((acc, curr) => acc + curr, 0)                 // sum: 17
arr.reduce((max, curr) => curr > max ? curr : max, 0)    // max: 6

const users = [{ firstName: "Alok", age: 23 }, { firstName: "Ashish", age: 29 }, { firstName: "Pranav", age: 50 }]
users.filter(u => u.age < 30).map(u => u.firstName)      // chaining → ["Alok","Ashish"]

users.reduce((acc, curr) => {                            // count by age
  acc[curr.age] = (acc[curr.age] || 0) + 1
  return acc
}, {})                                                   // { 23: 1, 29: 1, 50: 1 }

Always give reduce an initial value (second argument). Without it, an empty array throws a TypeError.

Classic gotcha + added

map passes (value, index) to the callback, and parseInt reads the second argument as a radix.

["1", "2", "3"].map(parseInt)   // [1, NaN, NaN]
["1", "2", "3"].map(Number)     // [1, 2, 3]
Remember!
  • map transform · filter keep · reduce fold
  • none of them mutate
  • reduce needs an initial value

Scope & closures

1 Scope & lexical environment step 21

In plain words

Scope is the answer to “can this piece of code see that variable?” An inner function can see the variables of every function around it. An outer function can never see into an inner one. Like rooms inside rooms: you can look out of a window, not through a wall.

Global Scope                ← visible everywhere
└── Function Scope          ← visible inside that function
    └── Block Scope         ← visible inside { } (if, for…)
  • let/const are block-scoped · var is function-scoped (ignores if and for braces)
  • a top-level var becomes global only because no function contains it
  • Lexical scope = scope is decided by where code is written
  • each EC carries a Lexical Environment = its own memory + a pointer to its parent’s. Looking up a variable walks this scope chain until found, or until null
function a() {
  c()
  function c() { console.log(b) }   // 10: found by walking c → a → global
}
var b = 10
a()

function z() { var q = 10 }
z()
console.log(q)    // ReferenceError: global can't see inside z
Scope vs this + added

Scope = which variables you can see (decided where code is written). this = which object called you (decided where code is called). Don’t mix them up.

2 Closures step 22

In plain words

A closure is a function that keeps a backpack of the variables from where it was born, even after that place is gone. When makeCounter finishes, its count would normally vanish, but the inner function still holds a live reference to it.

function makeCounter() {
  let count = 0                 // lives on in the closure
  return function () { count++; return count }
}

  • it’s a live reference, not a snapshot; every function in JS is a closure
  • uses: data privacy · stateful functions (counters, caches) · event handlers · function factories · memoization

Interview classic: setTimeout + closure 
for (var i = 1; i <= 5; i++) {
  setTimeout(function () { console.log(i) }, i * 1000)
}
// 6 6 6 6 6: every callback shares ONE i; the loop ends at 6

// Fix 1: let gives each iteration its own i

// Fix 2: a wrapper function creates a new i per call (works with var)
for (var i = 1; i <= 5; i++) {
  (function (i) { setTimeout(function () { console.log(i) }, i * 1000) })(i)
}

Why: var = one shared binding. let = a fresh binding every iteration. When the timers fire later, var-callbacks all see the final value.

    3 Callback hell & inversion of control step 37

    Callbacks are the foundation of async JS, but deeply nested ones cause two real problems.

    • Callback hell (pyramid of doom): each async step nests inside the previous one, so code drifts right and becomes unmaintainable
    • Inversion of control: you hand your callback to someone else’s function, so they decide when, whether and how often it runs. If they have a bug, your payment callback might never run, or run twice (customer charged twice)
    createOrder(cart, function (order) {
  proceedToPayment(order, function (payment) {
    showOrderSummary(payment, function (summary) {
      updateWallet(summary, function (result) { /* harder to read at every level */ })
    })
  })
})

    Both problems are why Promises were invented: a flat .then() chain fixes the pyramid, and you attach the handler, which fixes the inversion of control.

    • sync → microtasks → timers
    • Web APIs wait so JS doesn’t
    • callbacks = hell + lost control

    Promises & async/await

    1 Promises step 38

    In plain words

    A promise is a receipt for a result that isn’t ready yet, like a restaurant buzzer. It’s pending while you wait, then becomes either fulfilled (food ready) or rejected (kitchen failed). You attach .then() for success and .catch() for failure.

    • states: pending → fulfilled (resolve(value)) or rejected (reject(reason)); it has a promiseState and promiseResult
    • a promise settles once and is then immutable, so it’s safe to pass around
    • always return inside .then to keep the chain going; one .catch at the end handles any rejection above it
    // producer
function createOrder(cart) {
  return new Promise(function (resolve, reject) {
    if (!validateCart(cart)) reject(new Error("Cart is not valid"))
    const orderId = "12345"
    resolve(orderId)
  })
}

// consumer
createOrder(["shoes", "pants", "kurta"])
  .then(orderId => proceedToPayment(orderId))     // return → next .then gets it
  .then(paymentInfo => showOrderSummary(paymentInfo))
  .then(balance => updateWallet(balance))
  .catch(err => console.log(err))                 // catches all rejections above

    Control restored: with callbacks you pass your function to someone else. With promises you attach .then() yourself and it fires exactly once.

    2 async / await

    In plain words

    async/await is the same promises with nicer clothes: it lets async code read top-to-bottom like normal code. await pauses only that function, while the rest of the program keeps running.

    • an async function always returns a Promise, even if you return a plain value
    • await suspends the async function until the promise settles; the call stack is not blocked

getData()   // Promise { 'Namaste JavaScript' }

  console.log("Hi")              // prints immediately
  const val = await p            // function suspended, stack free
  console.log("Hello There!")    // only after p resolves

    In plain words

    2 Currying, composition, memoization step 47

    Functional patterns built on closures that make functions reusable and composable.

    In plain words

    Currying: instead of one function taking 2 arguments, a chain of functions each taking 1, so you can lock in the first and reuse. Composition: an assembly line where each function’s output feeds the next. Memoization: a cheat sheet that remembers answers you already computed.

    // currying

[1, 2, 3].map(add5)           // [6, 7, 8]

// composition
const pipe = (...fns) => x => fns.reduce((acc, fn) => fn(acc), x)
const trim = s => s.trim()
const toLower = s => s.toLowerCase()
const removeSpaces = s => s.replace(/\s+/g, "-")
const toSlug = pipe(trim, toLower, removeSpaces)
toSlug("  Hello World  ")    // "hello-world"

// memoization
function memoize(fn) {
  const cache = new Map()
  return function (...args) {
    const key = JSON.stringify(args)
    if (cache.has(key)) return cache.get(key)
    const result = fn(...args)
    cache.set(key, result)
    return result
  }
}
const fib = memoize(n => n <= 1 ? n : fib(n - 1) + fib(n - 2))

    • find one · some any · every all
    • pipe = left-to-right assembly line
    • memoize = closure + cache

    2 Debounce & throttle

    In plain words

    Debounce: wait until the user stops doing something (typing) for N ms, then run once. Throttle: run at most once every N ms, however often the event fires (scrolling). Both are closures plus timers.

    function debounce(fn, ms) {
  let id
  return (...args) => {
    clearTimeout(id)                          // restart the countdown every call
    id = setTimeout(() => fn(...args), ms)
  }
}
input.addEventListener("input", debounce(search, 300))

function throttle(fn, ms) {
  let last = 0
  return (...args) => {
    const now = Date.now()
    if (now - last >= ms) { last = now; fn(...args) }
  }
}
window.addEventListener("scroll", throttle(onScroll, 200))

    JavaScript engine & V8

    1 Runtime vs engine step 48

    In plain words

    The engine is the program that understands and runs JavaScript. The runtime is the engine plus everything around it (Web APIs, event loop, queues). Chrome and Node.js both use the V8 engine but offer different extras (DOM vs file system).

    Every JS environment (browser, Node.js, Deno) is a JavaScript Runtime Environment: engine + Web APIs + event loop + callback queue + microtask queue.

    What the engine does, in 3 steps

    • 1 · Parsing: source code → tokens → an Abstract Syntax Tree (AST), a JSON-like tree of the program’s structure (try astexplorer.net)
    • 2 · Compilation (JIT): not purely interpreted, not purely compiled. An interpreter turns the AST into bytecode for fast startup, while an optimising compiler watches for “hot” code and recompiles it into fast machine code at runtime
    • 3 · Execution: runs on the Call Stack, with a Memory Heap for objects, and a garbage collector (V8 uses Mark & Sweep) that frees unused memory

    Google’s V8 (Chrome, Node.js, Edge, Deno)

    componentrole
    Ignitioninterpreter: AST → bytecode for fast startup
    TurboFanoptimising compiler: hot bytecode → machine code
    Orinocogarbage collector (Mark & Sweep)

    • SpiderMonkey: Firefox (the first JS engine, by Brendan Eich)

    15 Closures (deep dive + follow-ups) Part B

    Say this“A closure is a function bundled with a reference to its surrounding lexical scope, so it keeps accessing those outer variables even after the outer function has returned.”
    function makeCounter() {
  let count = 0               // private
  return () => ++count        // inner fn closes over count
}

counter()  // 2

    Why they matter: data privacy, stateful functions (counters/caches), event handlers that remember context, function factories, memoization.

    Follow-up: values or references?

    References, not snapshots. The closure points at the live variable, so it sees later changes. That’s the classic var-loop bug:

    for (var i = 1; i <= 3; i++) setTimeout(() => console.log(i), 0)   // 4 4 4: one shared i
for (let i = 1; i <= 3; i++) setTimeout(() => console.log(i), 0)   // 1 2 3: let = binding per iteration

    Follow-up: how can closures leak memory?

    A closure keeps its captured variables alive as long as the closure is reachable. An event listener you never remove, or a closure over a large object, stops the GC from freeing it. Fix: removeEventListener when done and null out references you no longer need.

    Follow-up: why don’t cyclic references break modern GCs?

    Old reference-counting GCs couldn’t free two objects pointing at each other (count never hits 0). Modern engines use mark-and-sweep: start from roots (global, call stack), mark everything reachable, sweep the rest, including unreachable cycles. Reachability, not count, is the test.

    Follow-up: closure variables during mark-and-sweep?

    While a live closure references them they’re reachable from a root, so they’re marked and kept. Once the closure itself is unreachable (listener removed, nothing points to the function), its captured variables go too, on the next cycle.

    Interview edge“Every JS function is a closure. Closures aren’t special syntax; they’re the natural result of lexical scoping plus first-class functions. The var-vs-let loop question is the most-asked closure question. Know it cold.”
    Remember!
    • call=comma · apply=array · bind=new fn
    • closures hold references
    • GC = reachability

    Follow-up: why do promises run before setTimeout?

    After each sync run (and each macrotask) the loop fully drains the microtask queue before touching the macrotask queue. Promise callbacks are microtasks, setTimeout is a macrotask, so promises win even with a 0 delay.

    Follow-up: what is event-loop starvation?

    If microtasks keep scheduling more microtasks, the queue never empties, so macrotasks (and rendering) never run and the page can freeze.

    function starve() { Promise.resolve().then(starve) }   // setTimeout callbacks never fire

    Follow-up: how do you yield to keep the UI responsive?

    Split heavy work into chunks and yield between them so the loop can render and process input.

    await new Promise(r => setTimeout(r, 0))      // yield between chunks
await scheduler.yield?.()                     // modern, where available
requestIdleCallback(doLowPriorityWork)        // run when the browser is idle

    Follow-up: why does the event loop belong to the host?

    ECMAScript defines only the promise job queue. The full event loop, Web APIs (setTimeout, fetch, DOM) and the macrotask queue come from the host: the browser or Node.js (libuv).

    Interview edge“Nail the order: sync → all microtasks → one macrotask → all microtasks → next macrotask. Mentioning that the loop also renders (~60fps) between macrotasks, and that it’s host-provided, signals depth.”

    Say this“Promise.all takes an iterable of promises and resolves with an array of results in order, but rejects immediately if any one rejects (fail-fast). My polyfill tracks a completion counter and preserves index order.”

  return new Promise((resolve, reject) => {
    const results = []
    let completed = 0
    if (promises.length === 0) return resolve(results)

          if (completed === promises.length) resolve(results)
        })
        .catch(reject)                         // first rejection rejects the whole thing
    })
  })
}

    34 Performance: de-optimisation & delete Part F

    Say this“V8 gives objects a hidden ‘shape’ (hidden class) so property access is fast. Operations that change a shape unpredictably, especially delete, force V8 to abandon those optimisations and fall back to slow dictionary mode.”
    const obj = { a: 1, b: 2, c: 3 }   // V8 builds a hidden class for this shape
delete obj.b                        // shape changes → may switch to slow dictionary mode
obj.b = undefined                   // keeps the shape, just clears the value

    Why delete is slow: V8 stores properties in a compact, shape-based layout (like a struct). delete punches a hole in it, so V8 often converts the object to a hash table, making all later property access slower.

    Other de-optimisers: changing a property’s type repeatedly (monomorphic → polymorphic), adding properties in inconsistent order across instances, and “holey” (sparse) arrays.

    Interview edge“Keep shapes stable: initialise all properties in the constructor in the same order, set unwanted values to null/undefined instead of delete, and use a Map when you genuinely add/remove keys dynamically. Saying hidden classes / inline caches shows you understand the engine.”

    36 Implement debounce (+ throttle) Part G

    Say this“Debounce delays running a function until a pause in activity. It resets the timer on every call, so the function fires only once the events stop for N milliseconds.”
    function debounce(fn, delay) {
  let timerId
  return function (...args) {
    clearTimeout(timerId)                     // cancel the pending call
    timerId = setTimeout(() => {
      fn.apply(this, args)                    // preserve this and args
    }, delay)
  }
}
const onSearch = debounce(query => fetchResults(query), 300)
input.addEventListener("input", e => onSearch(e.target.value))

    Follow-up: debounce vs throttle?

    • Debounce waits for silence: fires once, after activity stops. “Run after the user is done.”
    • Throttle fires at most once per interval during activity. “Run at a steady rate.”
    function throttle(fn, limit) {
  let waiting = false
  return function (...args) {
    if (!waiting) {
      fn.apply(this, args)
      waiting = true
      setTimeout(() => (waiting = false), limit)
    }
  }
}

    Follow-up: real-world uses

    • Debounce: search-as-you-type, form validation, auto-save, resize handlers that rebuild layout
    • Throttle: scroll tracking, mouse-move, drag, infinite-scroll triggers, rate-limiting API calls
    Interview edge“Two details interviewers check: forwarding this and args via apply, and the closure over timerId that persists between calls. Debounce = wait for the dust to settle; throttle = a steady drip.”
    Level-up: cancel + leading edge + added 
    function debounce(fn, delay, { leading = false } = {}) {
  let id
  const d = function (...args) {
    const callNow = leading && !id
    clearTimeout(id)
    id = setTimeout(() => { id = null; if (!leading) fn.apply(this, args) }, delay)
    if (callNow) fn.apply(this, args)
  }
  d.cancel = () => { clearTimeout(id); id = null }   // e.g. on component unmount
  return d
}

    3. Order of output? console.log(1); setTimeout(()=>console.log(2),0); Promise.resolve().then(()=>console.log(3)); console.log(4)

    answer
    1, 4, 3, 2. Sync code first, then the microtask queue (promise), then the callback queue (timer).

    4. What is [10, 9, 1].sort() and why? How do you sort numbers properly?

    answer
    [1, 10, 9]. The default sort compares strings. Use .sort((a, b) => a - b).

    5. When would you pick Promise.all and when Promise.allSettled?

    answer
    all when you need every result and one failure should fail everything (it fails fast). allSettled when you want every outcome, including failures, such as a dashboard loading several independent widgets.
    Summary
    • JS runs one thing at a time in Execution Contexts on the call stack; async work goes through Web APIs and the event loop (microtasks first).
    • Scope, closures, this and prototypes explain most “weird” behaviour. Learn those four deeply.
    • Prefer const, ===, arrow callbacks and async/await with try/catch; avoid var, == and blocking the main thread.
