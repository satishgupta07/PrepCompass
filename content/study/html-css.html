What HTML really isHTML README §1

Think of HTML as the labels on moving boxes. A label says what is inside — “kitchen”, “fragile”, “books” — but not how the new room should look. The browser reads the labels and builds the room; CSS decorates it later.

  • HyperText Markup Language — a markup language, not a programming language: no variables, no loops, no logic.
  • You wrap content in tags that describe what each piece means.
  • A page is a tree of nested elements. The browser reads it top to bottom, builds the DOM (Document Object Model) in memory, then paints it.
  • Separation of concerns: HTML for structure, CSS for looks, JavaScript for behaviour.
  • HTML is a living standard kept by the WHATWG — there is no “HTML 6”.
LayerLanguagePurpose
StructureHTMLWhat the page is (a heading, a list, a form)
PresentationCSSWhat it looks like (colour, layout, animation)
BehaviourJavaScriptWhat it does (interactivity, async data)

Browsers are forgiving: broken HTML still renders by guesswork, so your own mistakes can hide. Validate early with the W3C Validator.

+ added

View source vs Elements panel. “View source” shows the text you wrote. DevTools → Elements shows the live DOM, after the browser has repaired mistakes and after JavaScript has changed things. When the page looks wrong, trust the Elements panel.

Anatomy of a tagHTML README §2

A tag pair is like bookends round a row of books. Attributes are little stickers on the opening bookend with extra instructions, like “this link goes to…”. Some elements are so small they have no books to hold — those are void elements and need only one bookend.

<a href="https://example.com">Click me</a>
<!-- <a ...>     opening tag (tag name = a)
     href="..."   attribute: key="value"
     Click me     content (text or other tags)
     </a>        closing tag
     all of it    = one element -->

<img src="cat.jpg" alt="A grey cat">   <!-- void element: no content, no closing tag -->
  • Element = opening tag + content + closing tag. Attribute = a key/value pair that configures it; some are required (<img> needs src and alt).
  • Tag names are case-insensitive, but write them in lowercase. Wrap attribute values in double quotes — unquoted values break on spaces or special characters.
  • Void elements never have content: <br> <hr> <img> <input> <link> <meta> <source> <track>. The trailing /> (as in <br />) is optional but harmless.
  • HTML collapses whitespace: spaces, tabs and newlines become one space. Use <pre> or CSS white-space: pre to keep them, and &nbsp; to stop two words splitting across lines.
  • Comments (<!-- … -->) are sent to the browser and are visible in View source.
CharEntityCharEntity
<&lt;"&quot;
>&gt;'&apos;
&&amp;With <meta charset="UTF-8"> you can type café, ©, ★, 你好, 🚀 directly.

Never put secrets in a comment — anyone can read them in View source.

⚑ check the source

The source says these five characters “can’t be typed directly”. Strictly, only < and & must be escaped in normal text; quotes matter inside a quoted attribute value. &apos; is valid in HTML5 (it was not in HTML 4).

+ added

More void elements: <area>, <base>, <col>, <embed>, <wbr>. Boolean attributes (disabled, checked, required) are “on” whenever they are present — disabled="false" still disables. Remove the attribute to turn it off.

Remember!

  • HTML marks meaning; CSS styles; JS acts.
  • The browser builds a DOM tree from your tags — and forgives errors silently.
  • Void elements have no closing tag; whitespace collapses.

The document skeletonHTML README §3 · Step 1

The skeleton is like the cover sheet of a form. The first line says which rulebook you are using (the DOCTYPE), the next gives your language, then come the hidden office notes (head) and the part visitors actually read (body).

<!DOCTYPE html>                 <!-- use modern standards mode -->
<html lang="en">                <!-- root element + page language -->
  <head>                        <!-- info ABOUT the page -->
    <meta charset="UTF-8" />    <!-- character encoding -->
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
                                <!-- render at the phone's real width -->
    <title>Page title</title>   <!-- tab title + search result title -->
  </head>
  <body>                        <!-- everything the user sees -->
    <!-- visible content -->
  </body>
</html>
  • DOCTYPE is not a tag but a declaration. HTML5 shortened the old long DTD line to <!DOCTYPE html>.
  • Without it the browser enters quirks mode, mimicking 1990s bugs (the box model and margin collapsing misbehave). With it: standards mode.
  • lang takes a BCP 47 tag (en, en-US, fr, hi…). It helps screen readers pronounce text, browsers offer translation, search engines pick regions, and CSS :lang() target languages.
  • <head> = metadata, links to CSS, scripts; only <title> shows. <body> = everything visible.

Forget the DOCTYPE and layouts break in small, confusing ways.

+ added

Good titles. Make each page’s <title> unique and descriptive, with the specific part first. Favicon: add <link rel="icon" href="/favicon.ico"> in the head. Without it, browsers request /favicon.ico anyway and may log a 404.

<!DOCTYPE html> in depthadded topic · expands README §3

The DOCTYPE is like the rulebook title on the first line of a board game box: “this game uses the modern rules”. If the line is missing, the browser assumes you are playing by the old, messy house rules from the 1990s, just so ancient pages don’t break.

+ added 
<!DOCTYPE html>          <!-- the whole modern doctype: no version, no URL -->

/* old HTML 4.01 / XHTML doctypes were long and named a DTD file: */
/* <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd"> */

/* check which mode the browser chose (type in the DevTools console): */
document.compatMode   /* "CSS1Compat" = standards mode, "BackCompat" = quirks mode */
  • What it really does: it is not an HTML version label. It exists only to switch the browser into standards mode. HTML5 has no versions, so the short form is all you need.
  • Three modes exist: standards (modern rules), quirks (legacy behaviour, triggered by a missing or old DOCTYPE), and limited-quirks (almost standards, triggered by some transitional HTML 4 / XHTML doctypes; it differs mainly in how images sit in table cells).
  • Where it goes: the very first thing in the file, before <html>. Keep nothing but whitespace or comments above it; some older browsers fall into quirks mode if a comment comes first.
  • Typing it: case-insensitive (<!doctype html> works), but write <!DOCTYPE html> by convention. It has no closing tag and is not an element, so it never appears in the DOM tree as a tag you can style.
  • Fixing a mystery layout: if sizes, heights or fonts look off, first check document.compatMode. A missing DOCTYPE is a cheap thing to rule out.

Don’t copy an old XHTML doctype from an ancient tutorial: it can drop you into limited-quirks or XHTML-flavoured behaviour for no benefit.

⚑ check the source

The source says quirks mode makes “the box model behave differently”. I can’t confirm that for modern browsers: their quirks modes mostly differ in things like table text not inheriting font size, percentage heights on body/html, and line-height quirks, and the full list is long and browser-specific. The safe takeaway is unchanged: always include the DOCTYPE and you never have to learn the list.

Meta tags — a deep diveHTML README §4 · Steps 27–28

Meta tags are the page’s ID card and business card. One group tells the browser how to read the file, another tells search engines how to list it, another tells chat apps how to preview a shared link.

<meta charset="UTF-8" />
<meta name="..."       content="..." />
<meta http-equiv="..." content="..." />
<meta property="..."   content="..." />   <!-- Open Graph -->

Required / near-required

<meta name="viewport" …>Mobile browsers render at the device’s real width. Without it, phones show a zoomed-out desktop layout.
<title>Tab and search-result title. Required for valid HTML.

Browser & app behaviour

⚑ check the source

+ added

A minimal Open Graph set, using the tags the source lists:

<meta property="og:title" content="My page">
<meta property="og:description" content="One-line summary">
<meta property="og:image" content="https://example.com/card.png">  <!-- use a full absolute URL -->
<meta property="og:url" content="https://example.com/">
<meta name="twitter:card" content="summary_large_image">

Viewport gotcha: never add user-scalable=no or maximum-scale=1 — they block pinch-zoom and fail accessibility checks.

Remember!

  • Always start with <!DOCTYPE html> and lang.
  • Charset first, viewport second, title always.
  • Meta tags talk to browsers, search engines and social apps.

Block vs inlineHTML README §5

Block elements are like paragraphs on a page — each starts on a fresh line and spans the full width. Inline elements are like words inside a sentence: they flow along and take only the space they need.

  • Block — new line, fills the container’s width: <div> <p> <h1> <section>.
  • Inline — flows with text, only as wide as its content: <a> <span> <strong> <em>.
  • Every element has a default display. CSS can override it, but you write HTML against the default.
<p>I am a block. <strong>I am inline</strong> inside it,
   and so is <a href="#">this link</a>.</p>
<p>A second block starts on its own line.</p>

Global attributes are like the standard fields on every ID card — name, address, photo. Any element can carry them, whatever its job.

+ added
  • Nesting rules matter: a <p> cannot contain block elements (the parser closes it early), a link cannot contain another link or a button, and <ul>’s direct children must be <li>.
  • Avoid positive tabindex (1, 2, 3…): it overrides the natural order and confuses keyboard users. Use 0 or -1 only.
  • hidden can be undone by your CSS: if a rule sets display: flex on that element, it will show again.
  • Newer globals such as inert and popover exist; I’m not certain of their current support in every browser, so check before relying on them.

Remember!

  • Block = new line, full width. Inline = flows in text.
  • Pick the element whose meaning fits, not the one that looks right.
  • id is unique; class is reusable.

Headings, paragraphs & breaksPhase 1 · Step 2

Headings are the chapter titles of a book. Nobody picks a chapter title because it looks big — it marks where a new idea starts, and screen-reader users jump from heading to heading like flipping to a chapter.

<h1>Pasta at home</h1>          <!-- the page title -->
<h2>Ingredients</h2>            <!-- a section -->
<h3>For the sauce</h3>          <!-- a sub-section: don't jump from h1 to h3 -->
<p>Boil water.<br>Add salt.</p>   <!-- br = a line break INSIDE a paragraph -->
<hr>                           <!-- thematic break: the topic shifts -->
  • Headings form the document outline used by screen readers and search engines. Use one <h1> and never skip levels for styling — size comes from CSS, the level is meaning.
  • <p> is for prose. <br> is a line break inside a paragraph (a poem, an address), not a vertical spacer — use CSS margin. <hr> is a thematic break, not a decorative line.

Don’t choose <h3> because it is smaller. Choose by meaning, then size with CSS.

⚑ check the source

“Exactly one <h1>” is stated as a rule. It is a widely recommended convention, but I don’t believe the HTML spec forbids several — so treat it as best practice, not a validation error.

+ added

Outline test: read only your headings, top to bottom. Do they tell the story of the page? If not, the structure needs work — this is exactly what a screen-reader user hears first.

Calling <b> and <i> “just bold / just italic” is a useful simplification. In HTML5 they do have defined roles (b: draw attention without extra importance; i: an alternate voice, such as a foreign term). The advice to prefer strong/em for importance and stress still stands.

+ added

<pre> keeps whitespace and line breaks (good for code). Use <mark> for relevance (a search hit), not decoration. Put the language on foreign phrases with lang="fr" so screen readers switch pronunciation.

Remember!

  • Headings give structure — choose level by meaning, never by size.
  • <br> is not spacing; <hr> is not decoration.
  • Prefer strong/em over b/i when meaning matters.

ListsPhase 1 · Step 4

An unordered list is a shopping list — the order doesn’t matter. An ordered list is a recipe — step 3 can’t come before step 1. A description list is a glossary: a word, then what it means.

<ul><li>Eggs</li><li>Flour</li></ul>                 <!-- order doesn't matter -->

<ol type="A" start="3" reversed>                    <!-- order matters -->
  <li>Mix</li>
  <li>Bake
    <ul><li>180°C, 20 min</li></ul>                <!-- lists nest inside an li -->
  </li>
</ol>

<dl><dt>DOM</dt><dd>The in-memory tree of a page.</dd></dl>
  • <ol> attributes: type (A/a/I/i), start, reversed. <dl> holds <dt> (term) / <dd> (definition) pairs — glossaries, metadata.
  • Lists nest: an <li> can contain another <ul> or <ol>.

LinksPhase 1 · Step 5

A link is a signpost. The href is the address on the sign; the text between the tags is the words people read. A good sign says where it leads.

<a href="https://example.com">External</a>
<a href="about.html">Relative file</a>
<a href="#contact">Same-page section (matches id="contact")</a>
<a href="mailto:hi@example.com">Email</a>   <a href="tel:+911234567890">Call</a>
<a href="https://example.com" target="_blank" rel="noopener noreferrer">New tab</a>
<a href="guide.pdf" download>Download the guide</a>
<a href="#top">Back to top</a>   <!-- special case: needs no matching id -->

target="_blank" + no rel="noopener noreferrer" lets the new tab reach window.opener — a real phishing vector.

  • download forces a file download instead of navigating. href="#top" and bare href="#" scroll to the top — a browser special case, not a real anchor.
+ added

Link text should make sense alone — screen-reader users list all links, so “click here” tells them nothing; write “Read the installation guide”. Modern browsers treat target="_blank" as if noopener were set, but I can’t vouch for every older browser, so keep the rel — it is harmless.

ImagesPhase 1 · Step 6

An image is a photo in a frame, with a caption card for anyone who can’t see it. That card is the alt text: it tells a screen reader (or a broken-image icon) what the picture is for.

<img src="chart.png" alt="Sales rose 40% in Q3"
     width="640" height="360"       <!-- reserves space: no layout shift -->
     loading="lazy"                 <!-- load only when near the screen -->
     srcset="chart-1x.png 1x, chart-2x.png 2x">   <!-- right resolution per device -->

<img src="swirl.svg" alt="">       <!-- decorative: empty alt, screen readers skip it -->

<figure>
  <img src="chart.png" alt="Sales by quarter">
  <figcaption>Figure 1: Sales by quarter</figcaption>
</figure>
  • src and alt are required. alt="" for purely decorative images.
  • width/height prevent layout shift (Cumulative Layout Shift, a Core Web Vital). loading="lazy" defers offscreen images.
  • Use <figure> + <figcaption> when an image needs a caption and is referenced as a unit (a chart, a code listing).

Describe purpose, not “image of…”. A missing alt makes screen readers read the filename.

+ added

Width-based srcset: the source shows density (1x, 2x). You can instead list widths and tell the browser how wide the image will display:

<img src="hero-800.jpg" alt="Mountain at sunrise"
     srcset="hero-400.jpg 400w, hero-800.jpg 800w, hero-1600.jpg 1600w"
     sizes="(min-width: 800px) 800px, 100vw">

Don’t lazy-load the main above-the-fold image — it delays the most important thing on screen.

Remember!

  • ul unordered, ol ordered, dl term + definition.
  • target="_blank" always gets rel="noopener noreferrer".
  • Every image needs alt — empty if purely decorative.

Landmark elementsPhase 2 · Step 7

A building has a sign over the door, corridors with arrows, a main hall, side rooms and a basement notice board. Before HTML5, every room was just <div class="room">. Landmark tags put the real names on the doors, so visitors, search engines and screen readers can find their way.

<body>
  <header><h1>My Blog</h1></header>
  <nav aria-label="Primary"><a href="/">Home</a> <a href="/about">About</a></nav>
  <main>                                   <!-- exactly one per page -->
    <article>                              <!-- self-contained: could live in an RSS feed -->
      <h2>Post title</h2>
      <section><h3>Intro</h3><p>…</p></section>   <!-- thematic group, has a heading -->
    </article>
    <aside>Related links</aside>              <!-- tangential content -->
  </main>
  <footer>© 2026</footer>
</body>
ElementRole
<header>Top of a page or section (logo, intro, byline). Can appear many times.
<nav>Major navigation. Add aria-label="Primary" etc. when there are several.
<main>The unique main content — exactly one per page.
<section>Thematic group; should have a heading.
<article>Self-contained, syndicatable unit (post, recipe, comment).
<aside>Tangentially related content (sidebar, pull-quote, glossary).
<footer>Bottom of a page or section (copyright, related links).
+ added
  • Landmark mapping: a page-level <header> acts as the “banner”, page-level <footer> as “contentinfo”. Inside an <article> or <section> they are just section headers/footers, not page landmarks.
  • A <section> only becomes a navigable “region” for screen readers when it has an accessible name (for example aria-labelledby pointing at its heading).
  • Article or section? Ask: “Would this still make sense on its own in a feed?” Yes → article. No, it’s just a themed chunk → section.

<div> vs <span>Phase 2 · Step 8

div and span are blank sticky labels: they carry no meaning, only a hook for styling. A div is a big blank label on its own line; a span is a tiny one inside a sentence. Use them only when no meaningful element fits.

<div class="card">                       <!-- block hook for layout -->
  <p>Total: <span class="price">$9</span></p>   <!-- inline hook inside text -->
</div>
If the thing is……use…not

  • One <main> per page; label repeated <nav>s.
  • div/span are the last resort, not the first.

Table basicsPhase 3 · Step 9

A table is a printed spreadsheet. The caption is the title above it, header cells (th) name each column or row, and data cells (td) hold the numbers. Tables are only for data that really has rows and columns — never for page layout.

<table>
  <caption>Fruit prices</caption>   <!-- title; read out first by screen readers -->
  <tr>                           <!-- tr = table row -->
    <th>Fruit</th>                <!-- th = header cell (semantic) -->
    <th>Price</th>
  </tr>
  <tr><td>Apple</td><td>$1</td></tr>   <!-- td = data cell -->
</table>
  • <table> wraps everything; <caption> is the title; <tr> a row; <th> a header cell; <td> a data cell.
  • Layout tables were a 1990s hack. CSS Grid replaced them completely.

Structured & accessible tablesPhase 3 · Step 10

Real reports have a header band, a body and a totals row. thead, tbody and tfoot name those three bands. scope then tells a screen reader which direction each header points — “this labels the column below” or “this labels the row beside”.

<table>
  <thead>
    <tr><th scope="col">Item</th><th scope="col">Q1</th><th scope="col">Q2</th></tr>
  </thead>
  <tbody>
    <tr><th scope="row">Pens</th><td>10</td><td>12</td></tr>
    <tr><th scope="row">Pads</th><td colspan="2">sold out</td></tr>   <!-- merges 2 columns -->
  </tbody>
  <tfoot><tr><th scope="row">Total</th><td>10</td><td>12</td></tr></tfoot>
</table>
  • scope="col" = labels a column; scope="row" = labels its row. Critical for screen-reader navigation.
  • colspan="2" merges cells horizontally, rowspan="2" vertically.

When a cell spans down, don’t repeat it in the next row’s markup — the renderer already counts it.

+ added
  • Wide tables on phones: wrap the table in a <div> with overflow-x: auto so it scrolls inside its own box instead of stretching the page (this notebook does exactly that).
  • Complex tables with several header levels can link cells to headers with id and headers="…".
  • Style hooks: border-collapse: collapse removes double borders; <colgroup>/<col> style whole columns.

Remember!

  • Tables are for data, never for layout.
  • Caption + thead/tbody/tfoot + scope = accessible.
  • Spanning cells: don’t repeat them in later rows.

Form submission essentialsPhase 4 · Step 11

A form is a paper order slip. action is the counter you hand it in at, method is how you hand it over, each field’s name is the printed heading on the slip, and the label is the question printed next to the blank.

<form action="/submit" method="post">   <!-- where & how to send the data -->
  <label for="email">Email</label>      <!-- label points at the input's id -->
  <input id="email" name="email" type="email" />   <!-- name = key in the payload -->
  <button type="submit">Send</button>
</form>
  • action = URL it posts to. method: get (data in the URL — searches, bookmarkable) or post (data in the body — sensitive, large, or changing things).
  • Every input that should be sent needs a name. No name → no value.
  • <label for="id"> tied to <input id>: clicking the label focuses the input, the hit target grows, and screen readers announce it.

An input without name is silently dropped on submit.

+ added
  • A <button> inside a form submits by default. For buttons that do something else, write type="button".
  • File uploads need method="post" and enctype="multipart/form-data" on the form.
  • Wrapping alternative: <label>Email <input name="email"></label> works without for/id.
  • autocomplete (for example email, current-password, one-time-code) lets browsers fill fields correctly — a big win on phones.

What CSS really isCSS README §1

CSS is like ordering from a menu: you say what you want (“blue headings, big gaps”) and the kitchen — the browser — works out how to cook it. You never describe the cooking steps.

selector {                 /* picks WHICH elements */
  property: value;         /* one declaration */
  property: value;         /* another declaration */
}
/* comments use slash-star only; two slashes are NOT valid CSS */
  • Cascading Style Sheets — a declarative language. Selector + its declarations = a rule; each property: value = a declaration.
  • For every element the browser builds a computed style (the final value of every property) in three steps: 1 Cascade (many rules match — who wins?), 2 Inheritance (some properties flow from the parent), 3 Defaults (the browser’s own stylesheet fills the rest).
  • Understanding the cascade is the biggest conceptual leap in CSS.

Three ways to attach CSSCSS README §2 · Step 1

The cascade — how rules are pickedCSS README §3 · Step 2

Picture a talent contest with three judges who score in a fixed order. Judge 1 looks at who sent the entry and how loudly (origin and importance). If it’s a tie, Judge 2 counts how precisely the entry aimed at its target (specificity). Still a tie? Judge 3 simply picks whoever came last (source order).

Origin & importance

  • Three sources: user-agent (the browser’s default sheet — <h1> is big, links are blue), user (rare), and author (your stylesheet). Normally author > user > user-agent.
  • !important is a code smell: it locks future contributors out and starts an arms race. Use it only for true overrides (utility classes, escaping a third-party widget).
⚑ check the source

“With !important the order partly reverses” is vague. Precisely: for normal declarations author beats user beats browser-default; for !important declarations the order flips, so browser-default !important beats user !important beats author !important. For everyday work, remember “author !important beats author normal”.

+ added

Cascade layers (@layer) add a step before specificity: you declare the layer order once and a later layer beats an earlier one regardless of selector strength. They are a modern cure for specificity wars (I believe broadly supported since 2022 — verify for your audience). Under !important, layer order flips again.

@layer reset, base, components;       /* later = stronger */
@layer reset      { a { color: inherit; } }
@layer components { .btn { color: white; } }   /* wins over reset, even with a weaker selector */

Remember!

  • CSS is declarative: say what, not how.
  • Cascade order: origin & importance → specificity → source order.
  • External stylesheet nearly always; !important almost never.

Specificity — the 4-tupleCSS README §3 · Step 3

Specificity is like a sports league table that compares goals first, then assists, then fouls. Count ids first; only if ids tie do you look at classes; only if those tie do you look at plain elements. One id beats any number of classes.

p               { }   /* 0,0,0,1 */
.btn            { }   /* 0,0,1,0 */
p.btn:hover     { }   /* 0,0,2,1  (class + pseudo-class + element) */
#header .nav a  { }   /* 0,1,1,1 */
/* style="color:red" on the element itself = 1,0,0,0 */
  • Compare left to right: 0,1,0,0 beats 0,0,99,0.
  • The universal selector * and the combinators (> + ~) score 0.
  • When everything ties, the later rule wins — that’s source order. “The last imported stylesheet wins” is the same idea at file scale.

Needing !important or #id #id .class .class means the architecture is wrong. Lower your selectors instead of raising them.

⚑ check the source

The (a, b, c, d) tuple is a popular teaching model. The official specification scores only three numbers — ids, classes/attributes/pseudo-classes, elements/pseudo-elements — and treats inline styles and !important as separate cascade stages. The results are the same, so use whichever you find clearer.

+ added

Functional pseudo-classes: :is(), :not() and :has() take the specificity of the most specific selector inside; :where() always counts as zero. Debug tip: in DevTools, the Styles panel lists every matching rule with the losers struck through; the Computed panel shows the winning value.

InheritanceCSS README §3

Some traits run in families — eye colour passes from parent to child, a scar doesn’t. Text traits (colour, font) pass to children; box traits (margin, border) don’t. If you don’t set a value, the child first asks its parent.

Pseudo-classes — element state (one colon)CSS README §4 · Step 6

  • State: :hover :focus :focus-visible (keyboard-only focus — the modern way to keep focus rings without showing them on every mouse click) :active :visited. Form state: :disabled :checked :placeholder-shown :required :optional :valid :invalid.

Content, padding, border, marginCSS README §5 · Step 8

Every element is a framed picture on a wall. The picture is the content; the matting round it is padding; the frame is the border; the empty wall between this frame and its neighbour is the margin.

  • content — the text or image itself. padding — clear space inside the border (the background colour extends here).
  • border — the visible edge. margin — clear space outside the border; transparent, so the parent’s background shows through.

box-sizing — the most important resetCSS README §5 · Step 8

Imagine ordering a 200 cm wardrobe and being told “200 cm of wood, plus the doors and handles on top”. That’s content-box. border-box is the sane promise: the finished wardrobe is 200 cm, doors included.

.box { width: 200px; padding: 20px; border: 2px solid; }
/* content-box (default): 200 + 20+20 + 2+2 = 244px wide  <-- the classic layout bug */

*, *::before, *::after { box-sizing: border-box; }   /* universal modern reset */
/* now width: 200px means the whole box is 200px */

With the default content-box, “two 50% columns with padding” overflow their row. Reset once, globally.

Shorthand & margin collapsingCSS README §5 · Step 9

Two neighbouring paragraphs each “want” breathing room. Instead of stacking both gaps, the browser lets them share, using the bigger one. It’s like two people each wanting an arm’s length of personal space: one arm’s length between them satisfies both.

margin: 10px;                  /* all four sides */
margin: 10px 20px;             /* vertical | horizontal */
margin: 10px 20px 30px;        /* top | horizontal | bottom */
margin: 10px 20px 30px 40px;   /* top | right | bottom | left — clockwise */

/* p { margin-bottom: 30px }  then  p + p { margin-top: 20px }  =>  gap = 30px, not 50px */
  • Vertical margins between adjacent block siblings collapse — the gap is the larger, not the sum. It also happens between a parent and its first/last child, unless something separates them: a border, padding, overflow: hidden/auto, display: flex/grid or display: flow-root.
  • It does not happen on flex/grid items, floats or positioned elements — one reason flex and grid feel saner. Negative margins are legal and pull elements together (“bleed” overlaps).
+ added
  • Centre a block horizontally: give it a width and margin-inline: auto (or margin: 0 auto).
  • Percent padding/margin are relative to the parent’s width, even for the vertical sides.
  • gap (flex/grid) replaces most margin hacks between siblings, and outline never adds to the box size.

Remember!

  • Four layers: content → padding → border → margin.
  • Start every project with box-sizing: border-box.
  • Vertical margins collapse (bigger wins); flex/grid items don’t.

positionCSS README §8 · Step 17

Normal layout is people standing in a queue. relative lets one person shuffle sideways while keeping their place. absolute lifts someone out of the queue to stand at an exact spot measured from the nearest “anchor” relative to them. fixed sticks a notice to the window; sticky is a notice that rides along until it reaches the top, then stays there.

⚑ check the source

Two lines are loose. (1) fixed “scrolls with the page only if its containing block is transformed” — the accurate version: an ancestor with transform (or filter) becomes the containing block, so the “fixed” element is positioned against that ancestor rather than the viewport. (2) sticky “needs a scrollable ancestor” — it needs a threshold such as top: 0 and sticks within its parent while scrolling the nearest scrolling ancestor (the page by default). An ancestor with overflow: hidden is the usual reason it fails.

z-index & stacking contextsCSS README §8 · Step 17

Stacking contexts are like folders on a desk. A sheet with z-index 9999 inside folder “1” can never rise above a sheet in folder “2” — the folders are compared first, then the sheets inside each folder.

  • z-index only works on positioned elements (or flex/grid items).
  • The classic gotcha: z-index: 9999 inside a parent with z-index: 1 will never beat a sibling of that parent with z-index: 2. z-index is compared only inside the same stacking context.
  • New stacking contexts come from: position relative/absolute/fixed/sticky + a non-auto z-index; opacity < 1; transform, filter, will-change; isolation: isolate.
.modal-wrap { isolation: isolate; }    /* a tidy new stacking context: z-index battles stay inside */

Defining tracksCSS README §10 · Step 22

Grid is a sheet of graph paper you draw yourself: you decide how many columns and rows, then drop items into the squares — or let them flow in. Flex lays things out along a line; grid lays them out across a page.

Media queries & mobile-firstCSS README §11 · Step 26

A media query is an “if” for CSS: if the screen is at least this wide, or the user prefers this, apply these rules. Mobile-first means you write the phone layout as the default and add extras for bigger screens — like starting with a small tent and adding rooms.

@media (min-width: 600px) { … }
@media (max-width: 599px) and (orientation: portrait) { … }
@media (prefers-color-scheme: dark) { … }
@media (prefers-reduced-motion: reduce) { … }
@media (hover: none) { … }      /* touch-only devices */
@media print { … }

/* mobile-first: base = phone, then upgrade */
.grid { grid-template-columns: 1fr; }
@media (min-width: 600px) { .grid { grid-template-columns: repeat(2, 1fr); } }
@media (min-width: 900px) { .grid { grid-template-columns: repeat(3, 1fr); } }
  • Combine conditions with and; OR with a comma; not inverts.
  • Why mobile-first? The base styles are simplest, additions are predictable, and CSS with no query works on every device.

Modern responsive — fewer breakpointsCSS README §11 · Step 27

  • clamp() — fluid sizing. repeat(auto-fit, minmax(…)) — auto-flowing columns. aspect-ratio: 16 / 9 — keep proportions without padding-bottom hacks.
  • Container queries respond to the parent’s width, not the viewport: set container-type: inline-size on the parent, then @container card (min-width: 400px) { … }. Component-level responsiveness.
  • prefers-color-scheme: dark — free dark mode. prefers-reduced-motion: reduce — respect motion-sensitive users.
.card-wrap { container-type: inline-size; container-name: card; }
.card { display: grid; gap: 1rem; }
@container card (min-width: 400px) { .card { grid-template-columns: 120px 1fr; } }
.thumb { aspect-ratio: 16 / 9; object-fit: cover; width: 100%; }
+ added
  • Range syntax: @media (width >= 600px) is a newer, more readable form of min-width; I believe it is widely supported but verify for old browsers.
  • Choose breakpoints by content (where your layout breaks), not by specific phone models. Test by dragging the window narrow and using DevTools’ device mode.
  • Responsive needs the viewport meta tag from page 2, or phones ignore your queries and show a zoomed-out page.

Remember!

  • rem for type, %/fr for layout, clamp() for fluid.
  • Mobile-first: base styles + min-width upgrades.
  • Container queries ask “how wide is my parent?”.

Transforms — move, scale, rotateCSS README §12 · Step 29

Keyframes — multi-stage choreographyCSS README §12 · Step 30

:is(), :where() and :has()CSS README §13 · Step 32

:is and :where are shorthand for “any of these”. :has finally lets a parent ask about its children: “style me if I contain an unread message” — something CSS couldn’t do before.

+ added

  • 1. The cascade is the system. Most “weird CSS” is a cascade misunderstanding — read DevTools’ Computed (winner) and Styles (all matches).
  • 2. Reset box-sizing: border-box once, globally. 3. Animate transform and opacity only.
  • 4. Mobile-first, content-first. 5. Prefer modern over historical: flex/grid over float, gap over margin hacks, clamp() over breakpoint chains, :has() over JS toggles.
  • 6. Respect user preferences: prefers-color-scheme, prefers-reduced-motion, :focus-visible. 7. Specificity wars are a smell — !important or #id #id .class .class means the architecture is wrong.

Quick check5 questions · tap to reveal

1. A box has width: 200px, padding: 20px, border: 2px solid. How wide is it by default, and how do you make it 200px?

244px (200 + 20 + 20 + 2 + 2) because the default is content-box. Fix it with *, *::before, *::after { box-sizing: border-box; }.

2. Which wins for a link: #nav a or .menu .item a.link?

#nav a scores 0,1,0,1; the other scores 0,0,3,1. One id beats any number of classes, so #nav a wins.

3. How do display: none, visibility: hidden and opacity: 0 differ?

none: gone, no space, no clicks, hidden from assistive tech. visibility: hidden: invisible but keeps its space. opacity: 0: invisible, keeps space, still clickable and still read by assistive tech.

4. Why can z-index: 9999 still lose to z-index: 2?

z-index is compared only inside one stacking context. If the 9999 element’s parent made a context at a lower level than the 2’s, the whole parent group sits below it. Fix the stacking context (for example isolation: isolate), not the number.

5. Give two reasons to use <button> instead of <div onclick>.

A button is keyboard-focusable and announces itself as a button, and it answers Enter and Space for free. A div does none of that, so you’d have to rebuild it with tabindex, a role and key handlers.

Three-line summarythe short version

1. HTML is meaning: pick the element whose meaning matches, label every control, and keep it accessible.
2. CSS is the cascade plus the box: specificity decides ties, border-box keeps sizes honest, flex handles lines and grid handles pages.
3. Go modern and kind: custom properties, clamp(), :focus-visible, reduced motion — and verify support when you’re unsure.
