Why the real DOM is slowCore Concepts

In plain wordsThink of the DOM as a huge wall of sticky notes. Moving one note can make the browser re-measure the whole wall and repaint it. React keeps a sketch of the wall on paper, works out exactly which notes changed, and only then touches the real wall.
  • The real DOM is a tree of objects; each change can trigger a reflow (re-calculate layout) and a repaint (redraw pixels)
  • React never edits the DOM blindly: describe the UI as plain JS objects, compute the minimum changes, apply only those

The Virtual DOMCore Concepts

In plain wordsThe Virtual DOM is just a tree of ordinary JavaScript objects describing “what the screen should look like right now”. Comparing two such trees is quick because nothing touches the browser’s layout engine.
  • Each node is a plain object made by React.createElement()
  • Update cycle: setState → re-render → diff → minimal DOM patch (commit)
a virtual DOM node
{
  type: 'div',
  props: {
    className: 'card',
    children: [
      { type: 'h1', props: { children: 'Title' } },
      { type: 'p',  props: { children: 'Body text' } }
    ]
  }
}

▶ What the user sees: a <div class="card"> with a heading and a paragraph. The object is only the description.

Reconciliation: the diffing rulesCore Concepts

In plain wordsComparing two trees perfectly is very slow (O(n³)). React cheats with three sensible guesses, which brings it down to O(n). It is like proof-reading two drafts: same chapter title? Only check the changed words. Different title? Throw the whole chapter away.
  • Different type → unmount the whole subtree and mount a fresh one (all its state is lost)
  • Same type → keep the DOM node, patch only the changed props
  • Lists → match items by key (identity), not by position
keys: why they matter
// Without key: inserting at the top makes every item below look "changed"
<li>B</li>  →  <li>A</li>   // React thinks: B changed to A
<li>C</li>  →  <li>B</li>   // React thinks: C changed to B

// With key: React matches by identity, only the new item is inserted
<li key="b">B</li>  →  <li key="a">A</li>  // inserted
<li key="c">C</li>  →  <li key="b">B</li>  // moved, no DOM change

⚠ Missing or unstable keys give a console warning and subtle bugs (inputs keeping the wrong text).

React FiberCore Concepts · React 16+

In plain wordsThe old reconciler was a cook who, once started, could not stop until the whole banquet was done. Fiber is a cook who writes each step on a card, so they can pause, serve an urgent order first, and then continue.
  • Each component gets a Fiber node, a JS object that is one unit of work
  • Fibers form a linked list instead of a call stack, so rendering can pause and resume

Why keys help, and why React is fastNamaste notes · pp. 24-26, 56-57

  • Render in the notes means “updating something in the DOM”. Reconciliation minimises the work React has to do to apply changes
  • Adding an <li> at the end of siblings is cheap; adding one at the top makes React re-do everything below
  • Solution: keys. With key="2014" and so on, React matches children in the old tree to children in the new tree, so it does very little work. Always use keys with multiple children
  • The Virtual DOM is a representation of the real DOM kept by React. Reconciliation is the algorithm that diffs one tree against the other and changes only the small part that differs
  • React Fiber (React 16): a new reconciliation engine, responsible for the diff algorithm. “Read about React Fiber” (the notes’ homework). See page 1
  • Why React is fast: virtual DOM, reconciliation and the diff algorithm: the current tree is compared with the new tree, and only the difference reaches the DOM
⚑ imprecise in notes“React is fast because of its fast DOM manipulation.” React doesn’t make DOM changes faster than hand-written JavaScript could; it makes them fewer by working out the minimum. Page 1 explains the real mechanism. Also note the notes’ use of “render” for DOM updates: in React, rendering means calling your component to get JSX; the DOM is touched in the later commit step.

The two phases: render and commitCore Concepts

In plain wordsRender is drafting on scrap paper: you may stop, throw it away, redo it. Commit is pasting the final draft onto the real wall in one go, and that part is never interrupted.
  • Render phase: walk the Fiber tree, diff, build the change list. Pure, no DOM changes yet, safe to re-run
  • Commit phase: apply DOM changes, then useLayoutEffect, then paint, then useEffect. Always synchronous
  • React holds two trees (current + work-in-progress) and commit swaps them with one pointer, so nobody sees a half-finished screen
The render → commit → effects cycle

Concurrent renderingCore Concepts · React 18

In plain wordsTyping in a box is urgent; filtering a giant list is not. Concurrent rendering lets React pause the slow, low-priority work when you type, handle the keystroke first, then resume.
  • Updates get priority lanes: user input highest → startTransition → useDeferredValue lowest
  • An urgent update arriving mid-render pauses the current work, runs first, then work resumes
⚑ error in referenceThe heading says “Concurrent Mode”. That was the name of an old experimental API. In React 18 it is called concurrent rendering / concurrent features, switched on by using createRoot and then opting in per update (startTransition, useDeferredValue, Suspense). The idea in the reference is right; only the label is dated.
+ added

Rendering must be pure. A component is a recipe: same props + state in, same JSX out. No writing to outside variables, no Math.random() or Date.now() in the output, no fetching. Because React may call your function twice (StrictMode, or after pausing in concurrent rendering), impure renders cause bugs.

Batching React 18+: several setState calls in the same event are grouped into one re-render. React 18 also batches inside timeouts, promises and native handlers; React 17 only batched inside React event handlers.

When does a component re-render?Quick Reference

In plain wordsA component re-runs its function for three reasons only: its own memory (state) changed, its parent re-ran, or a shared noticeboard (context) it reads was updated.
TriggerExplanation
Its own state changesAny setState / dispatch schedules a re-render of that component
Its parent re-rendersChildren re-render by default, even if props are identical. React.memo opts out
A context it consumes changesAnything calling useContext(X) re-renders when X’s value changes
Parent re-renders, Child re-renders
function Parent() {
  const [tick, setTick] = useState(0)
  return (
    <>
      <button onClick={() => setTick(tick + 1)}>tick {tick}</button>
      <Child count={42} />   {/* re-renders every tick, even though 42 never changes */}
    </>
  )
}

const Child = React.memo(function Child({ count }) {
  return <p>{count}</p>       // skipped unless count changes
})

▶ What renders: a button and “42”. After clicking, only the button text changes, and with memo Child does not even re-run.

⚠ “Props changed” is not a trigger on its own. Props change because the parent re-rendered.

Remember!

  • Render = pure drafting, commit = pasting onto the DOM
  • Keys let React match list items by identity
  • Re-render triggers: own state, parent, context

The very first React in the browserNamaste notes · pp. 1-6

In plain wordsThe notes start by building the same heading three ways: plain JavaScript, then React with createElement, then JSX. Seeing all three side by side shows that React is just a library that builds the same page for you.
  • React is a library. Difference from a framework: a library takes minimum effort to put into your code (you add it where you want it)
  • The page needs <div id="root"></div> and React + ReactDOM loaded over a CDN
plain JavaScript, then React
// plain JS
const heading = document.createElement("h1");
heading.innerHTML = "Namaste Javascript";
const root = document.getElementById("root");
root.appendChild(heading);

// React
const heading = React.createElement("h1", { id: "title" }, "Namaste Everyone");
const root = ReactDOM.createRoot(document.getElementById("root"));
root.render(heading);

▶ What renders: an h1 reading “Namaste Everyone” inside #root.

  • createElement arguments: 1st = the tag, 2nd = attributes (props), 3rd = the children
  • The object in the 2nd argument can hold anything: { id: "container", hello: "world" }. These are called props
  • React overwrites everything inside root with whatever you give render
  • Two children: React.createElement("div", { id: "container" }, [heading, heading2]), with the children in an array

What a React element really is00_customReact

In plain wordsJSX looks like HTML but is really a shorthand for building a JavaScript object. A renderer is the thing that reads that object and builds real screen output. Writing a tiny one yourself shows there is no magic.
  • Every JSX expression compiles to a createElement() call, which returns a plain object
  • A renderer reads the object and produces real output (DOM nodes, native views…)
customreact.js: ~10 lines
// JSX:
<a href="https://google.com" target="_blank">Click me</a>

// what Babel produces:
React.createElement('a', { href: 'https://google.com', target: '_blank' }, 'Click me')

// the "virtual DOM node" (simplified, see the pink box):
{ type: 'a', props: { href: 'https://google.com', target: '_blank' }, children: 'Click me' }

function customRender(reactElement, container) {
  const domElement = document.createElement(reactElement.type)   // 1. create node
  domElement.innerHTML = reactElement.children                    // 2. set text
  for (const prop in reactElement.props) {                        // 3. set attributes
    domElement.setAttribute(prop, reactElement.props[prop])
  }
  container.appendChild(domElement)                               // 4. mount
}

▶ What the user sees: a clickable “Click me” link inside the container element.

JSX, and the chain behind itNamaste notes · pp. 26-30

In plain wordsJSX is not HTML hiding inside JavaScript. It only looks like HTML. Behind the scenes Babel rewrites it into createElement calls, which make an object, which React turns into the real page.
JSX → createElement → object → DOM
  • The browser cannot understand JSX; Babel does (it ships with Parcel)
  • JSX is valid JavaScript once Babel has run. You can keep a JSX expression in a variable: const heading = ( <h1 id="title" key="h1">HelloWorld</h1> )
  • React keeps track of the key
  • Advantages: developer experience, syntactic sugar, readability, less code, maintainability, no repetition
  • Why it exists: Facebook’s idea was to write lots of HTML-like markup in JavaScript, because JavaScript is very performant

Homework in the notes: the difference between HTML and JSX, other uses of JSX, and how to make an image tag in JSX. (See page 2 for JSX rules; images are <img src={url} alt="…" />, self-closed, with the value in braces.)

Functional components and JSX01_basic_react

In plain wordsA component is a function that starts with a capital letter and answers “what should be on screen?” by returning JSX. Using <Chai /> is just calling that function.
Chai.jsx / App.jsx

  return <h3>Chai is ready | React</h3>
}

function App() {
  return (
    <>                          {/* Fragment: no extra DOM node */}
      <h1>Hello World</h1>
      <Chai />                  {/* composition: Chai lives inside App */}
    </>
  )
}

▶ What renders: an h1 and an h3 as siblings, with no wrapper div.

Composition: three ways, and JSX safetyNamaste notes · pp. 30-33

In plain words“Everything is a component in React.” A component is a plain function that returns JSX. A React element is an object; a functional component is a function. Put one component inside another and you have composition.
  • Two types: functional (the new way) and class-based (the old way, see page 16)
  • The name starts with a capital letter. Not mandatory, but a strong convention (and needed for JSX to treat it as a component)
  • Render one with <HeaderComponent />
three ways to compose
const Title = () => { return <h1>Hello World</h1> }

const HeaderComponent = () => {
  return (
    <div>
      {Title()}            {/* 1. call it as a function inside {} */}
      <Title />            {/* 2. generally used */}
      <Title></Title>      {/* 3. open and close tag */}
      <h2>Namaste React</h2>
    </div>
  )
}

▶ What renders: the “Hello World” heading three times, then “Namaste React”.

  • Whenever you write JSX you can put any piece of JavaScript between { }. A plain variable also works: const title = ( <h1>…</h1> ) then {title}
  • JSX is secure. It sanitises what you put in { }, so injected code can’t run, e.g. {data} from an API
  • Not mandatory: JSX, TypeScript, ES6. You can build React without them
+ added
  • Prefer <Title /> over {Title()}. Calling a component as a plain function skips React’s component handling: it won’t appear as its own item in DevTools, and if Title uses hooks, those hooks silently attach to the caller.
  • JSX escapes text, which blocks the usual injection route. It is not a shield for everything: dangerouslySetInnerHTML and untrusted URLs in href are still your job to check.

JSX rulesQuick Reference

  • Component names are PascalCase (<Card /> not <card />)
  • Every element must be closed: <br /> not <br>
  • className instead of class; htmlFor instead of for
  • One root per return; use a Fragment if needed
+ added
  • Attributes are camelCase: onClick, tabIndex, maxLength
  • style takes an object, not a string: style={{ backgroundColor: color }} (outer braces = JS, inner = object)
  • true, false, null, undefined render nothing; numbers like 0 do render
  • JSX text is escaped by default, which protects against XSS. dangerouslySetInnerHTML turns that protection off, so avoid it
  • React 17+ the “new JSX transform” means you no longer need import React just to write JSX

React.StrictMode01_basic_react

In plain wordsStrictMode is a safety inspector who works only in development. They run every component twice on purpose, so a sneaky side effect inside render shows up straight away.
let requestCount = 0
function Component() {
  requestCount++                       // ❌ side effect during render
  return <p>Requests: {requestCount}</p>
}  // StrictMode: renders twice, so the count is 2 on first mount, not 1

⚠ useEffect running twice in development is expected. Fix it with a proper cleanup function, never by deleting StrictMode.

Remember!

  • JSX is sugar for createElement, which returns a plain object
  • Curly braces take expressions, not statements
  • StrictMode double-runs in dev to expose impure code

Bundlers and package managersNamaste notes · pp. 7-10

In plain wordsTo make a real app you need outside tools: one that packs your files together (a bundler) and one that fetches other people’s code (a package manager). The notes build their own “create-react-app” from these two pieces, instead of using a ready-made one.

  • A production-ready app must be minified (shrunk), have its console logs removed, be bundled, and be served by a real server

Igniting the app with ParcelNamaste notes · pp. 11-16, 21-22

In plain wordsParcel is a one-command workshop: give it your index.html and it starts a local server, reloads the page when you save, and later boxes up an optimised copy for the real world.
npx parcel index.html          # "execute using npm"; index.html is the entry point
                               # → starts a mini server like localhost:1234
npx parcel build index.html    # production build → minified files in the dist/ folder
npx parcel index.html --https  # run the dev server over https

// we removed the CDN links, so React must now be imported:
import React from "react";
import ReactDOM from "react-dom/client";
// the browser errors on `import` in a normal script tag, so tell it this is a module:
// <script type="module" src="App.js"></script>

"scripts": {

// npm run build
  • Before this, React came from CDN links. “Not a good way”: React should live in node_modules (npm install react)
  • HMR (Hot Module Reload): Parcel tracks every file you edit with file-watcher algorithms (written in C++) and tells the server to reload
  • parcel-cache is a folder Parcel creates for its own working space. dist holds the minified output. Both are auto-generated, so put them in .gitignore
  • The slow part of most websites is media and images. Parcel optimises images, and caches while you develop
  • Parcel also takes care of older browsers and can serve https for dev (some features only work over https)
⚑ imprecise in notesThe notes write “npx = npm run”. They are different: npm run runs a script from package.json; npx executes a package (a local binary from node_modules, or one it downloads for the occasion). npx parcel index.html works because Parcel’s command is in node_modules.

useState: the component’s memory02_counter

In plain wordsA normal variable is forgotten every time the function runs again. State is a notebook React keeps for the component between runs. Change the notebook with the setter and React re-draws the screen.

  • Treat the value as read-only. Only the setter schedules a re-render
  • Hooks let function components use React features such as state

Events: pass a reference, don’t call it02_counter

In plain wordsonClick wants a recipe it can follow later, not a finished dish. The () means “cook it now”. onClick={cook} hands over the recipe; onClick={cook()} cooks during render and hands over the leftovers.
<button onClick={addValue}>Add</button>        // ✅ reference: React calls it on click
<button onClick={addValue()}>Add</button>      // ❌ runs NOW during render
                                              //   (a state update here = infinite loop)

// Need an argument? Wrap in an arrow function (defines, doesn't call):
<button onClick={() => setColor("red")}>Red</button>   // ✅
<button onClick={setColor("red")}>Red</button>           // ❌ runs immediately
the three patterns
// 1. No arguments: pass the reference
<button onClick={handleClick}>Click</button>
// 2. Arguments needed: wrap in an arrow
<button onClick={() => handleClick("some-id")}>Click</button>
// 3. Event object AND arguments
<button onClick={(e) => handleClick(e, "some-id")}>Click</button>

⚠ Calling a state setter directly in the render body (or onClick={setX(1)}) causes “too many re-renders”.

The prevState (functional update) pattern02_counter

In plain wordsWithin one click, counter is a photograph taken at the start of the render, so four counter + 1 all say “photo plus one”. The functional form instead says “whatever the latest value is, plus one”, so the updates stack up.

setCounter(counter + 1)
setCounter(counter + 1)

setCounter(prev => prev + 1)
setCounter(prev => prev + 1)
setCounter(prev => prev + 1)

function useCurrencyInfo(currency) {
  const [state, setState] = useState({ status: "loading", data: null, error: null })

  useEffect(() => {
    const controller = new AbortController()          // lets us cancel the request
    setState({ status: "loading", data: null, error: null })

    fetch(`https://example.com/${currency}.json`, { signal: controller.signal })
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`)   // fetch doesn't throw on 404/500
        return res.json()
      })
      .then(json => setState({ status: "success", data: json[currency], error: null }))
      .catch(err => {
        if (err.name === "AbortError") return          // cancelled: not a real error
        setState({ status: "error", data: null, error: err })
      })

    return () => controller.abort()    // cleanup: cancel the old request when currency changes
  }, [currency])

  return state
}

useCallback: keep the same function05_passwordGenerator

In plain wordsEvery render writes a brand-new copy of your inner functions. useCallback says “reuse last time’s copy unless one of these inputs changed”, so anything comparing function identity sees the same function.

  // generates password from current settings
}, [length, numberAllowed, charAllowed, setPassword])
//  ↑ recreate only when these values change

  • Without useCallback, the function is new every render; since it’s an effect dependency, the effect fires every render → infinite re-generation loop
  • setPassword in the deps is harmless but unnecessary: state setters are stable

useMemo: remember a computed value05_passwordGenerator

// Without useMemo: recalculates on every render

// With useMemo: only recalculates when items changes

React.memo: skip re-rendering a component05_passwordGenerator

In plain wordsBy default, when a parent re-draws, all its children re-draw too. React.memo puts a bouncer at the child’s door: “same props as last time? Then you’re not coming in.”
const InputBox = React.memo(function InputBox({ value, onChange }) {
  // only re-renders when value or onChange actually changes
  return <input value={value} onChange={onChange} />
})
+ added

Putting the pieces together. A memoised child is skipped only if every prop is shallowly equal. A function or object created inline in the parent is new every render, so it defeats the memo. useCallback/useMemo exist to keep those props stable:

const List = React.memo(function List({ items, onPick }) {
  console.log("List render")
  return items.map(i => <button key={i} onClick={() => onPick(i)}>{i}</button>)
})

function Parent() {
  const [text, setText] = useState("")
  const items = useMemo(() => ["a", "b", "c"], [])           // stable array
  const onPick = useCallback((i) => console.log(i), [])      // stable function

    <>
      <input value={text} onChange={e => setText(e.target.value)} />

    </>
  )
}

  }
  render() {
    if (this.state.hasError) return <h2>Something went wrong.</h2>
    return this.props.children
  }
}

Virtual DOM, reconciliation and Fiber: what actually happensasked 8+ times across the list

Say this“Rendering produces a tree of plain objects, the virtual DOM. Reconciliation diffs the new tree against the previous one using two heuristics: different element types means rebuild that subtree, and key tells React which list item is which. Fiber is the rewrite of the engine that stores this work as a linked list of units, so React can split rendering into small chunks, pause it, and prioritise urgent updates over slow ones.”
  • Diff is O(n), not O(n³), because of those two assumptions.
  • Why Fiber exists: the old recursive renderer could not be interrupted, so a big update froze typing. Fiber made rendering interruptible, which unlocks useTransition, Suspense and time slicing.
  • Two phases: render (interruptible, must be pure) and commit (synchronous, touches the DOM). That is why render must have no side effects: it may run twice or be thrown away.
  • The virtual DOM is not “faster than the DOM”. It lets React batch and minimise real DOM writes while you describe UI declaratively.

A reusable useFetch hook: loading, error, cancel, retryasked 4 times

Say this“A custom hook is a function starting with use that composes other hooks and returns state plus actions. My fetch hook owns three states, cancels on unmount or URL change, retries transient failures with backoff, and exposes a refetch.”
function useFetch(url, { retries = 2 } = {}) {
  const [state, setState] = useState({ data: null, error: null, loading: true })
  const [nonce, setNonce] = useState(0)                 // bump to refetch
  const refetch = useCallback(() => setNonce(n => n + 1), [])

  useEffect(() => {
    const ctrl = new AbortController()
    setState(s => ({ ...s, loading: true, error: null }))

    async function run() {
      for (let attempt = 0; ; attempt++) {
        try {
          const res = await fetch(url, { signal: ctrl.signal })
          if (!res.ok) throw Object.assign(new Error("HTTP " + res.status), { status: res.status })
          return setState({ data: await res.json(), error: null, loading: false })
        } catch (e) {
          if (e.name === "AbortError") return                       // cancelled: do nothing
          const retryable = !e.status || e.status >= 500           // never retry 4xx
          if (!retryable || attempt >= retries)
            return setState({ data: null, error: e, loading: false })
          await new Promise(r => setTimeout(r, 2 ** attempt * 500)) // 0.5 s, 1 s, …
        }
      }
    }
    run()
    return () => ctrl.abort()
  }, [url, retries, nonce])

  return { ...state, refetch }
}

Say this“An error boundary catches errors thrown while rendering, in lifecycle methods and constructors of its children, and shows a fallback. It does not catch event handlers, async code, server rendering, or errors in the boundary itself.”

Many requests fail at once, what do you do?One layer decides, not every component. Send all calls through one client (axios interceptor or a fetch wrapper, or the TanStack QueryCache onError).
  • Retry only what is safe: network errors, 502/503/504 and 429 (respect Retry-After), on idempotent requests. Never retry 400/401/403/404, and never blindly retry a POST without an idempotency key.

  • 401: refresh the token once, queue the other failed requests behind that single refresh, then replay them.
  • Collapse the noise: show one toast (“Some data failed to load”), per-section inline errors with a Retry button, and keep stale data visible. Report to Sentry with the request id.
  • A circuit breaker on the client stops hitting an endpoint that keeps failing for a short cool-down.

const ROW = 40, VIEW = 400, OVERSCAN = 5

function VirtualList({ rows }) {
  const [top, setTop] = useState(0)
  const start = Math.max(0, Math.floor(top / ROW) - OVERSCAN)
  const end   = Math.min(rows.length, Math.ceil((top + VIEW) / ROW) + OVERSCAN)

  return (
    <div style={{ height: VIEW, overflow: "auto" }}
         onScroll={e => setTop(e.currentTarget.scrollTop)}>
      <div style={{ height: rows.length * ROW, position: "relative" }}>   {/* full height */}
        {rows.slice(start, end).map((r, i) => (
          <div key={r.id}
               style={{ position: "absolute", top: (start + i) * ROW, height: ROW }}>
            {r.name}
          </div>
        ))}
      </div>
    </div>
  )
}

  • Often the real fix is not to load 50,000 rows at all: server-side pagination, filtering and sorting with cursor paging, and virtualise only what remains.
  • With real-time updates: batch incoming messages (apply once per animation frame), update rows by id, and keep row components memoised.

Memory leaks in React: causes and how to debugasked 3 times

Say this“A leak is memory that stays reachable after the component is gone. In React it almost always means something outside React still holds a reference: a listener, a timer, a subscription or a cache.”
  • Causes: addEventListener / setInterval / WebSocket / observer not cleaned up in the effect return; subscriptions to a store; closures holding big objects; global or module-level caches that only grow; detached DOM nodes kept in a ref or variable; uncancelled long requests.
  • Fix: every effect that starts something returns the function that stops it (removeEventListener, clearInterval, socket.close(), observer.disconnect(), ctrl.abort()). Bound caches (LRU), use WeakMap for per-object data.
  • Debug: Chrome DevTools → Memory → take a heap snapshot, use the feature, navigate away, force GC, take a second snapshot and use “Comparison”. Look for Detached nodes and growing counts. The Performance panel’s memory graph with a sawtooth that never returns to baseline is the symptom.
  • Catch it early: React Strict Mode runs effects twice in development, which exposes missing cleanup immediately.

Server Components vs Client Componentsasked 3 times

Say this“A Server Component renders only on the server: it can read the database directly, and its code and dependencies never ship to the browser. A Client Component ("use client") ships JS and can use state, effects and browser APIs. The goal is a smaller bundle and fewer client-side waterfalls.”

1. What does this render after ONE click?

function Box() {

  return <button onClick={go}>{n}</button>

AnswerIt shows 2. All three calls read the same snapshot (n = 0); they set 1, 1, then 2, and the last one wins. With prev => prev + 1 each time it would be 3.

2. Stale-closure puzzle: the counter ticks to 1 and stops. Why? Fix it.

useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000)
  return () => clearInterval(id)
}, [])
AnswerThe effect runs once and its closure captured count = 0, so every tick sets 0 + 1. Fix: setCount(c => c + 1) (then [] is correct), or add count to the dependencies.

3. What does this show when the list is empty?

{items.length && <List items={items} />}
AnswerThe digit 0, because 0 && … evaluates to 0, and React renders numbers. Use items.length > 0 && ….

4. Why does this effect loop forever?

useEffect(() => { setList([...list, 1]) })
AnswerNo dependency array, so it runs after every render; it sets a new array, which triggers a render, which runs the effect… Add a dependency array and use a functional update.

5. In which situation does useCallback actually help?

AnswerWhen the function is passed to a React.memo child (so identity stays equal) or is a dependency of another hook (useEffect, useMemo). Otherwise it adds cost for no gain.
