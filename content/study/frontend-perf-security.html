From bytes to pixelsasked in 4 loops

Say this“The browser parses HTML into the DOM and CSS into the CSSOM, combines them into a render tree (only visible nodes), runs layout to compute sizes and positions, paints pixels into layers, and the compositor composites the layers on the GPU. JavaScript can interrupt every step.”
Change a property early in the chain and everything after it re-runs.
  • Critical rendering path = the steps and resources needed for the first paint. Shorten it by sending less, sooner.
  • CSS is render-blocking: the browser will not paint until the CSSOM is built, so keep critical CSS small (inline it) and load the rest later.
  • JavaScript is parser-blocking by default: a plain <script> stops HTML parsing while it downloads and runs, and it waits for pending CSS.

Reflow, repaint and what is cheap to animateasked in 3 loops

Say this“Changing geometry (width, top, margin, font size) forces layout and usually paint. Changing colour forces only paint. Changing transform or opacity on a promoted layer only needs compositing on the GPU, so I animate those.”

⚠ layout thrashing 
// Read, write, read, write: each read forces a synchronous layout
items.forEach(el => {
  const h = el.offsetHeight          // READ  → forces layout
  el.style.height = h + 10 + "px"    // WRITE → invalidates layout
})

// Fix: batch all reads, then all writes
const heights = items.map(el => el.offsetHeight)
items.forEach((el, i) => { el.style.height = heights[i] + 10 + "px" })
  • Move things with transform: translateX(), not left. Hint with will-change: transform sparingly: every layer costs memory.
  • Do visual updates inside requestAnimationFrame so they run once per frame, just before paint.
  • Set width/height (or aspect-ratio) on images so the layout does not jump (CLS).
  • content-visibility: auto lets the browser skip layout and paint for off-screen sections.

How the event loop interacts with renderingasked in 3 loops

Say this“JavaScript and rendering share the main thread. One loop turn runs a task, then drains all microtasks (promises, queueMicrotask), and only then may the browser render. A long task or an endless promise chain starves rendering and input.”
button.onclick = () => {
  el.textContent = "Loading…"           // style change queued
  Promise.resolve().then(() => heavy()) // microtask: runs BEFORE the browser paints "Loading…"
}

button.onclick = () => {
  el.textContent = "Loading…"
  setTimeout(heavy, 0)                  // macrotask: browser can paint first, then run heavy()
}
  • Order per turn: one macrotask → all microtasks → (maybe) rAF callbacks → style, layout, paint.
  • A task over 50 ms is a “long task”. Break up work with setTimeout / scheduler.yield(), or move it to a Web Worker.
  • async/await is microtask based: await alone never lets the browser paint.
interview edgeTie it back to a symptom: “Typing lags because a long task blocks the main thread, so the browser cannot process the keypress. I find it in the Performance panel (red-cornered tasks) and fix it by chunking, deferring or moving the work to a worker.”

Remember!

  • DOM + CSSOM → render tree → layout → paint → composite
  • CSS blocks render, plain JS blocks parsing
  • Animate transform and opacity only
  • Microtasks run before the browser paints

Shrinking and analysing the JavaScript bundleasked in 3 loops

Say this“JavaScript is the most expensive byte: it must be downloaded, parsed, compiled and executed on the main thread. I look at the bundle visually, find the heavy and duplicated parts, then split, tree-shake or replace them.”
  • Analyse: webpack-bundle-analyzer, rollup-plugin-visualizer, vite-bundle-visualizer, source-map-explorer. Look for one giant vendor chunk, duplicated packages and whole-library imports.
  • Route-level code splitting (React.lazy, dynamic import()) so each route ships only its own code, then split heavy widgets (charts, editors, maps).
  • Tree shaking needs ES modules and "sideEffects": false. Import what you use, not the world.
  • Dedupe and replace: one version of each dependency, lighter alternatives, native APIs.
  • Third-party scripts: analytics, chat and tag managers often cost more than your own code: load them async, after interaction or in a worker.
  • Budget: fail CI when a route’s JS grows past a limit (size-limit, bundlesize).
import _ from "lodash"                  // pulls the whole library

import { debounce } from "lodash-es"       // tree-shakeable build

const Chart = lazy(() => import("./Chart"))        // loaded only when rendered

button.onclick = async () => {
  const { exportPdf } = await import("./exportPdf")  // on demand, on click
  exportPdf(data)
}
interview edgeFor “hundreds of routes”: split by route automatically (the framework does it), keep a shared chunk for common code but not a catch-all vendor chunk, and enforce a per-route budget in CI so the 200th route cannot quietly add 300 KB.

Compression, caching and the CDNasked in 2 loops

  • Brotli (or gzip) for text assets: HTML, CSS, JS, JSON, SVG. Not for already-compressed images.
  • Hashed filenames (app.3f9a1c.js) + Cache-Control: public, max-age=31536000, immutable: cached forever, and a new deploy gets a new URL.
  • HTML is not hashed, so no-cache (revalidate with ETag) or a short max-age, so users pick up new deploys.
  • A CDN serves static files from the nearest edge, cutting latency and origin load. HTTP/2 or HTTP/3 multiplexes many requests over one connection.

Remember!

  • Analyse → split → tree-shake → budget
  • preload = now, prefetch = next, preconnect = origin
  • Never lazy-load the LCP image
  • Hashed assets cached forever, HTML revalidated

Large tables with real-time updatesasked in 3 loops

Say this“Render only what is visible (virtualisation), update only the rows that changed (by id, memoised rows), and batch incoming messages so I commit at most once per frame, however fast the feed is.”
// Buffer socket messages, flush once per animation frame
const buffer = new Map()
let scheduled = false
socket.onmessage = e => {
  const row = JSON.parse(e.data)
  buffer.set(row.id, row)                     // later update of same id replaces earlier one
  if (!scheduled) {
    scheduled = true
    requestAnimationFrame(() => {
      applyUpdates([...buffer.values()])      // ONE state update
      buffer.clear(); scheduled = false
    })
  }

  • Normalise rows into a map by id; rows get stable keys and React.memo, so only changed rows re-render.
  • Highlight changes with a CSS animation class instead of re-rendering styles in JS.
  • Server-side sort, filter and cursor pagination so the client never holds a million rows.
  • Pause updates while the user is scrolling or selecting, then catch up.

Keeping the main thread freetoolbox

  • Chunk the work: process 500 items, await scheduler.yield() (or setTimeout), continue. The browser handles input between chunks.
  • Defer non-urgent work: requestIdleCallback, React transitions, load third parties after the first interaction.
  • Cache expensive results: memoise pure functions; useMemo for derived data; a Map keyed by input.
  • Passive event listeners for scroll and touch ({ passive: true }) so scrolling never waits on your handler; IntersectionObserver instead of scroll handlers.
  • Throttle continuous events (scroll, resize, mousemove) with rAF; debounce “wait until the user stops” events (typing).

Memory leaks in the browserasked in 3 loops

Say this“A leak is memory that stays reachable when it should be garbage. Usual suspects are listeners, timers, observers, sockets and caches that outlive the thing that created them, and DOM nodes still referenced after removal.”
  • Detect: DevTools → Memory → take a heap snapshot, repeat the action, force GC, take another and use Comparison. Filter “Detached” to find DOM nodes kept alive. The Performance panel memory graph that never returns to its baseline is the symptom.
  • Fix: pair every add with a remove; AbortController to cancel listeners and fetches; disconnect() observers; clearInterval; bounded caches (LRU); WeakMap/WeakRef for per-object metadata.
const ctrl = new AbortController()
window.addEventListener("resize", onResize, { signal: ctrl.signal })
window.addEventListener("scroll", onScroll, { signal: ctrl.signal, passive: true })
// teardown: one call removes both listeners
ctrl.abort()

Remember!

  • Profile → read the colour → fix that cost
  • Batch live updates per animation frame
  • Chunk long tasks or use a worker
  • Heap snapshot comparison finds leaks

A data-fetching layer: caching, background updates, retries, deduplicationasked in 3 loops

Say this“I do not write this per component. One client layer owns caching keyed by request, deduplicates identical in-flight calls, serves stale data while revalidating in the background, and retries safe failures with backoff. TanStack Query or SWR already give this.”
// The core idea in 15 lines
const cache = new Map()      // key → { data, time }
const inflight = new Map()   // key → Promise

async function query(key, fetcher, { staleMs = 30_000 } = {}) {
  const hit = cache.get(key)
  if (hit && Date.now() - hit.time < staleMs) return hit.data         // fresh: no network
  if (inflight.has(key)) return inflight.get(key)                       // dedupe concurrent calls
  const p = fetcher()
    .then(data => { cache.set(key, { data, time: Date.now() }); return data })
    .finally(() => inflight.delete(key))
  inflight.set(key, p)
  return hit ? hit.data : p       // stale-while-revalidate: show old data, refresh behind it
}
  • Query keys identify data (["user", id]); mutations invalidate related keys so screens refetch.
  • Revalidate triggers: window focus, reconnect, interval, after a mutation.
  • Pagination and infinite scroll: cursor-based, keep pages in the cache, prefetch the next page.
  • API versioning and inconsistent shapes: put an adapter at the edge that maps every response to one internal type, validate with a schema (Zod), and keep components unaware of the wire format.

function connect(url, onMsg) {
  let tries = 0
  const open = () => {
    const ws = new WebSocket(url)
    ws.onopen    = () => { tries = 0 }
    ws.onmessage = e => onMsg(JSON.parse(e.data))
    ws.onclose   = () => {                                  // reconnect with backoff + jitter
      const wait = Math.min(30000, 500 * 2 ** tries++) * (0.5 + Math.random() / 2)
      setTimeout(open, wait)
    }
  }
  open()
}
interview edgeFor chat, also say: reconnect and resync (send the last message id so the server replays what you missed), heartbeat/ping to detect dead connections, de-duplicate by message id, show optimistic messages as “sending”, and keep typing indicators ephemeral (throttle them, never persist).

  • One fetching layer: cache, dedupe, SWR, retry
  • no-cache ≠ do not cache
  • SSE one-way, WebSocket two-way
  • Reconnect with backoff, then resync

  e.waitUntil(caches.open("shell-v3").then(c => c.addAll(["/", "/app.js", "/app.css"]))))

The outbox pattern for offline writesasked in 2 loops

// 1. Every write goes to IndexedDB first, with a client-generated id
async function save(note) {
  const op = { opId: crypto.randomUUID(), type: "UPDATE_NOTE", note, baseVersion: note.version }
  await db.outbox.add(op)             // durable
  applyLocally(note)                  // UI updates instantly
  flush()
}

// 2. Replay in order when online; the server de-duplicates by opId (idempotent)
async function flush() {
  if (!navigator.onLine) return
  for (const op of await db.outbox.orderBy("createdAt").toArray()) {
    const res = await fetch("/api/ops", { method: "POST",
      headers: { "Idempotency-Key": op.opId }, body: JSON.stringify(op) })
    if (res.status === 409) { await handleConflict(op, await res.json()); continue }
    if (!res.ok) break                  // keep it, retry later
    await db.outbox.delete(op.opId)
  }
}
addEventListener("online", flush)

What cross-site scripting isasked in 4 loops

Say this“XSS is when an attacker gets their JavaScript to run in my page’s origin. It can then read cookies that are not HttpOnly, read localStorage, call my API as the user, and rewrite the page. The root cause is treating untrusted data as code or HTML.”

Defence in depththe answer to “how do you protect against XSS?”

  • 1 · Output encoding by default. Frameworks like React escape interpolated text. Do not bypass them with dangerouslySetInnerHTML, innerHTML, v-html.
  • 2 · Sanitise when you must render HTML (rich text, markdown): DOMPurify with a strict allow-list, on output, ideally also on the server.
  • 3 · Validate URLs: allow only http:/https:/mailto: for user-supplied links; add rel="noopener noreferrer" to target="_blank".
  • 4 · Content Security Policy: a response header that limits where scripts can come from, so an injected script is blocked even if it gets in.
  • 5 · Cookies: HttpOnly so injected script cannot read the session cookie.
  • 6 · Trusted Types (Chromium) force every dangerous sink to go through a sanitising policy.
  • 7 · Third-party scripts and dependencies run with full power: pin versions, use Subresource Integrity, audit, minimise.
Content-Security-Policy:

  script-src 'self' 'nonce-r4nd0m' 'strict-dynamic';   /* only scripts carrying this per-response nonce */
  object-src 'none';
  base-uri 'none';
  frame-ancestors 'none'                               /* also blocks clickjacking */

Where should you store the auth token?asked in 4 loops

Say this“localStorage is readable by any script on the page, so one XSS steals the token. An HttpOnly; Secure; SameSite cookie cannot be read by JavaScript, but it is sent automatically, which opens CSRF, so I pair it with SameSite and CSRF protection.”
WhereXSS can steal it?CSRF risk?Verdict
localStorage / sessionStorageyesno (sent manually)avoid for long-lived tokens
JS memory (variable)only while XSS is active; gone on refreshnogood for a short-lived access token
HttpOnly cookiecannot read it, but can still make requests as the useryes, needs defencesgood, especially for the refresh token
  • Common pattern: short-lived access token (about 5–15 min) kept in memory, long-lived refresh token in an HttpOnly, Secure, SameSite cookie scoped to the refresh endpoint, with refresh-token rotation and reuse detection.
  • BFF (backend for frontend): the browser only holds a session cookie; a server-side layer holds the real tokens and calls APIs. No token ever reaches JavaScript.
  • Honest note: no storage option survives a full XSS, so XSS prevention matters more than the storage choice.

CSRF: what it is and the defencesasked in 3 loops

Say this“CSRF tricks a logged-in user’s browser into sending a request to my site from another site. The browser attaches my cookies automatically, so the server sees a valid session. It only matters when authentication is carried by something the browser sends on its own, like cookies.”
  • SameSite cookies: Lax (browser default) stops cookies on cross-site POST, Strict on all cross-site requests. First line of defence.
  • CSRF token (synchroniser or double-submit): a random value the page must echo in a header or body; an attacker site cannot read it.
  • Check Origin/Referer on state-changing requests.
  • Never change state with GET. Require a custom header or JSON content type, which forces a CORS preflight.
  • Bearer tokens in the Authorization header are not sent automatically, so classic CSRF does not apply (but XSS exposure does).

CORS: what it does and does not doasked in 3 loops

Say this“CORS is a browser rule that relaxes the same-origin policy. The server states which other origins may read its responses. It protects users’ browsers; it does not protect my server from curl, Postman or a malicious script, so it is not authentication.”
  • Same origin = same scheme + host + port.
  • Simple requests (GET/POST with basic headers) are sent, and the browser then decides whether the page may read the response. Other requests (PUT/DELETE, JSON content type, custom headers like Authorization) trigger a preflight OPTIONS first.
  • With cookies you need credentials: "include" on the client, Access-Control-Allow-Credentials: true and a specific Access-Control-Allow-Origin, never *.
  • Cache preflights with Access-Control-Max-Age. Do not reflect any Origin back blindly: use an allow-list.
  • In development, avoid CORS pain with a dev-server proxy so the browser sees one origin.
// Preflight response the API must send
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true
Access-Control-Max-Age: 600

Environment config without leaking secretsasked in 2 loops

Say this“Anything that reaches the browser bundle is public. Secrets live on the server; the frontend calls my API, which holds the key. Only non-secret values (API base URL, public keys, feature flags) go into frontend config.”
  • Bundlers expose only prefixed variables (VITE_*, NEXT_PUBLIC_*). Never prefix a secret. Search the built output for keys in CI (secret scanning).
  • Build once, deploy many: avoid baking per-environment values into the bundle. Load a runtime /config.json or injected window.__CONFIG__ so the same artifact runs in dev, staging and prod.
  • Third-party keys that must be public (maps, analytics) get restricted by domain and quota.
  • .env files stay out of git; secrets come from a secret manager or CI variables.
⚠ anti-patternconst stripe = new Stripe(import.meta.env.VITE_STRIPE_SECRET): a secret key compiled into every user’s browser. Payment-capturing calls belong on the server.

Other frontend security checklistone-liners

  • Clickjacking: Content-Security-Policy: frame-ancestors 'none' (or X-Frame-Options).
  • Dependencies: npm audit, lockfile, Dependabot/Renovate, review install scripts; supply-chain attacks are real.
  • HTTPS everywhere with HSTS; Secure cookies; no mixed content.
  • Open redirects: validate ?next= targets against an allow-list.
  • postMessage: always check event.origin.
  • Never trust the client: role checks and price calculations are re-done on the server.

How do you make sure the app is accessible (WCAG)?asked in 3 loops

Say this“Accessibility is built in, not bolted on. Start with semantic HTML, make everything work from the keyboard, manage focus, keep sufficient contrast, and use ARIA only to fill gaps semantic elements cannot. Then test with automated tools and a screen reader.”
  • Semantic first: <button> for actions, <a href> for navigation, landmarks (header, nav, main), one h1, ordered headings, <label for> on every input. “First rule of ARIA: do not use ARIA if a native element does it.”
  • Keyboard: everything reachable with Tab, activated with Enter/Space, visible focus ring (never outline: none without a replacement), logical tab order, no keyboard traps, skip-to-content link.
  • Focus management: when a modal opens, move focus into it, trap Tab inside, close on Escape, and return focus to the trigger. After a route change, move focus to the new page heading.
  • Announce changes: aria-live="polite" for toasts and results; role="alert" for errors; aria-expanded, aria-controls, aria-current on widgets.
  • Visual: text contrast 4.5:1 (3:1 for large text), do not rely on colour alone, respect prefers-reduced-motion, allow 200% zoom without breaking, touch targets at least 24 to 44 px.
  • Images and media: meaningful alt (empty alt="" for decoration), captions for video.

A responsive architecture: mobile, tablet, desktop, touch and mouseasked in 2 loops

  • Mobile-first CSS: base styles for small screens, min-width media queries add layout. Fewer overrides, less shipped CSS for phones.

An A/B testing frameworkasked in 1 loop

  • Assignment: hash of userId + experimentId → bucket, so a user always sees the same variant. Anonymous users: a persistent cookie id.
  • Exposure event logged only when the user actually sees the variant, with experiment id, variant and user id. Without it the analysis is biased.
  • No flicker: assign on the server or at the edge, not after the page renders.
  • Metrics: one primary metric, plus guardrails (error rate, latency, revenue). Decide the sample size and duration before starting; do not stop at the first green number.
  • Isolation: mutually exclusive experiments on the same surface; the same flag system serves both.

Micro-frontends: when and howasked in 2 loops

Say this“Micro-frontends split one large UI into independently built and deployed pieces owned by different teams, composed in the browser or at the edge. They solve an organisational problem (many teams, release independence), not a technical one, and they cost runtime and consistency.”
CompositionHowTrade-off
Module Federationa shell loads remote bundles at runtime and shares dependenciesflexible; version-sharing mistakes break at runtime

Web Componentseach team exposes custom elementsframework-agnostic; styling and state sharing need care
Server / edge compositionfragments stitched into HTML (SSI, edge)fast first paint; infra complexity
Build-time packagesteams publish npm packagessimple, but a deploy of one needs a rebuild of all
  • Shell owns routing, auth, layout and shared contracts; each micro-frontend owns one route or domain.
  • Communication: prefer URL, props and a small typed event bus. Avoid shared global state; it recreates the monolith.
  • Shared dependencies: share React as a singleton; agree on a design system; version contracts between shell and remotes.
  • Failure isolation: an error boundary around each remote with a fallback; remote load timeouts.
  • When NOT to: one team, small app. A well-structured monolith or monorepo is cheaper.

Monorepo: shared packages and dependency managementasked in 2 loops

  • Tooling: pnpm or npm workspaces for linking, Turborepo / Nx for task graphs, remote caching and “affected-only” builds and tests.
  • Structure: apps/* (deployables) and packages/* (ui, config, utils, types). Packages never import from apps; apps import packages.
  • Boundaries: lint rules or Nx tags that forbid illegal imports, to stop a tangle.
  • Versions: a single version policy for React and TypeScript across the repo; Changesets for versioning published packages; strict peer dependencies, no phantom (undeclared) dependencies.
  • Pain points: CI time (fix with caching and affected builds), a bad shared package breaking everyone (fix with tests and gradual rollout), ownership (CODEOWNERS).

Migrating a legacy frontend without disrupting usersasked in 3 loops

Say this“I never rewrite big-bang. I use the strangler-fig pattern: put a routing layer in front, move one route or feature at a time to the new stack, keep both running, and retire the old code as its traffic drops to zero. Each step ships, is measurable, and can be rolled back.”
StepWhat I do
1 · Understandinventory routes, dependencies, traffic and pain; pick the first slice that is valuable but low-risk
2 · Safety netcharacterisation tests and E2E on current behaviour before touching it; monitoring and baselines
3 · Coexistreverse proxy or shell routes by path; shared auth/session; shared design tokens so the two look identical
4 · Migrate by slicebehind a feature flag, roll out to 1% → 100%, compare errors and vitals, keep the old path as a fallback
5 · Retiredelete old code and flags; update docs; celebrate by removing, not adding
  • Why not rewrite: months with no shipped value, lost undocumented behaviour, and the old system keeps changing underneath.
  • Put an anti-corruption/adapter layer between old data shapes and the new UI so the new code is not shaped by legacy quirks.
  • Communicate: a visible plan, a status page of “% migrated”, and a rule that new features go in the new stack only.

Quick checkanswers folded away

1. Which CSS properties are cheapest to animate, and why?

transform and opacity: they can be handled by the compositor on the GPU, skipping layout and paint.

2. async vs defer scripts?

Both download in parallel. async runs as soon as ready (order not kept, pauses parsing). defer runs after parsing, in order.

3. Name the Core Web Vitals and their “good” thresholds.

LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1, at the 75th percentile of real users.

4. Why does a promise chain starve rendering?

Microtasks are drained completely after each task and before the browser renders, so an endless chain keeps the main thread busy.

5. What does Cache-Control: no-cache do?

The response may be stored but must be revalidated before reuse. no-store is the one that forbids storing.

6. Where do you store an access token and a refresh token?

Access token short-lived in memory; refresh token in an HttpOnly, Secure, SameSite cookie with rotation. Or use a BFF so JS never sees tokens.

7. Does CORS protect your API from attackers?

No. It only controls which origins may read responses in a browser. Authentication and authorisation on the server are what protect the API.

8. How do you stop XSS in React?

Rely on default escaping, avoid dangerouslySetInnerHTML (or sanitise with DOMPurify), validate link protocols, add a strict CSP and HttpOnly cookies.

9. SSE or WebSocket for a notification feed?

SSE: one-way server to client, auto-reconnect, plain HTTP. WebSocket only if the client also sends frequent low-latency messages.

10. How do you resolve offline edit conflicts?

Detect with versions/ETags (409), then merge per data type: field-level merge, three-way text merge, ask the user, or CRDTs. Replay writes with idempotency keys.

11. Why is the strangler-fig approach safer than a rewrite?

It ships value incrementally, keeps the old system as fallback, is measurable per slice and can be rolled back.

12. Your first move when a page “feels slow”?

Measure: field data to find the worst metric, a lab trace to find whether network, main-thread JS, or rendering is responsible, then fix the biggest cost.
