What an OS doesUNIT 1

In plain wordsApplication software does a job for the user (a browser, an editor). System software runs the machine and gives applications a platform. The operating system is the system software that manages every resource (CPU, memory, disks, devices, files) and hides the hardware’s complexity behind a clean interface, so many programs can share one machine safely and efficiently.
The OS sits between the programs and the hardware.
RoleMeaning
Resource manager (arbitration)decides who gets the CPU, memory, disk, devices and for how long: process, memory, file, device and security management
Abstractionhides hardware detail: a program reads a “file”, not disk sectors; it uses “memory”, not RAM chips
Isolation and protectionone program cannot read or corrupt another’s memory, or monopolise the machine
Interfacea user interface (GUI, shell) and a programming interface (system calls)
  • Without an OS: every app would carry its own hardware-driving code (bulky and complex), one app could exploit all resources, and there would be no memory protection.
  • Goals: maximum CPU utilisation, minimum starvation, honour priorities, fast response, and fair sharing.

Types of operating systemsLEC-2

TypeIdeaTrade-off / example
Single processone program runs at a timeoldest; MS-DOS (1981)
Batchusers hand jobs (punch cards) to an operator, who groups similar jobs into batches run one after anotherno priorities, a long batch starves others, CPU idles during I/O. ATLAS (Manchester, late 1950s)
Multiprogrammingkeep several jobs in memory; when one waits for I/O, run anotherone CPU, switch only when a job blocks; CPU idle time drops. THE (Dijkstra, early 1960s)
Multitasking (time sharing)multiprogramming plus time slices: the CPU switches every few milliseconds, even if nothing blocksresponsive, interactive. CTSS (MIT, early 1960s); every desktop OS today
Multiprocessingmore than one CPU/core in one computerhigher throughput and reliability (one CPU can fail). Windows NT, Linux
Distributedindependent networked machines that act as one systemscale and fault tolerance, but network failures. LOCUS
Real-time (RTOS)results must arrive within a deadline; hard real-time (air-traffic control, pacemakers, robots) vs soft (video playback)predictability matters more than throughput. FreeRTOS, VxWorks
⚑ correctedThe notes say multitasking is “able to run more than one task simultaneously” on a single CPU. One core runs one instruction stream at a time. Multitasking only looks simultaneous because the OS switches very fast (concurrency). Real simultaneity (parallelism) needs several cores.
+ addedConcurrency vs parallelism: concurrency = dealing with many things at once (interleaving, possible on one core); parallelism = doing many things at the same instant (needs multiple cores). Interviewers love this distinction, and it is the heart of Node.js (concurrent, single JS thread) vs worker threads (parallel).

Remember!

  • OS = resource manager + abstraction + protection
  • Multiprogramming switches on I/O; multitasking on a timer
  • Concurrency ≠ parallelism
  • RTOS = deadlines, not speed

Kernel, user space and the shellLEC-4

In plain wordsThe kernel is the core of the OS: the first part loaded at boot, always in memory, talking directly to the hardware. Everything else, your apps, the GUI and the shell, runs in user space with no direct hardware access. A shell is a command interpreter (bash, zsh, PowerShell) that takes your commands and asks the kernel to run them.
Kernel functionWhat it does
Process managementcreate/terminate processes and threads, schedule them on CPUs, suspend/resume, provide synchronisation and communication
Memory managementallocate and free memory, track what is used by which process, isolate address spaces
File managementcreate/delete files and directories, map them onto storage, permissions, backup support
I/O managementdrivers for devices; buffering (smooth speed differences inside one job, e.g. video buffering), caching (keep hot data in fast memory), spooling (queue output for a slow shared device, e.g. print or mail spooling)
Security / protectionusers, permissions, isolation

User mode vs kernel mode (dual-mode operation)+ added

In plain wordsThe CPU has a mode bit. In user mode it cannot run privileged instructions (talk to devices, change page tables, halt the CPU). In kernel mode it can. Hardware enforces this, which is what makes protection possible: a buggy app cannot overwrite the OS.
  • The switch from user to kernel mode happens only through a controlled entry: a system call, an interrupt, or an exception. The switch back happens on return.
  • Kernel mode is also called supervisor mode, ring 0. If a user program tries a privileged instruction, the CPU raises an exception and the OS typically kills the process.

System callsLEC-5

In plain wordsA system call is how a user program asks the kernel to do something it is not allowed to do itself: open a file, create a process, send network data. mkdir laks is just a program that calls the kernel’s mkdir system call; the kernel’s file module creates the directory.
The dashed line is the user/kernel boundary; crossing it is a mode switch.
  • Most programs call a wrapper in the C library (glibc), which puts the call number and arguments in registers and executes a special instruction (syscall, or int 0x80/svc on other CPUs). That traps into the kernel; the kernel runs the handler, then returns.
  • Each system call costs a mode switch plus checks, so batching work (one big read instead of many small ones) is faster.

⚑ corrected(1) The notes say system calls “are the only way” into kernel mode. Interrupts (a timer or a network card) and exceptions (a page fault, divide by zero) also enter the kernel, just not on the program’s request. (2) “System calls are implemented in C” is only half true: the wrappers are C, but the entry itself is a CPU instruction written in assembly. (3) In LEC-4 the question “how do user mode and kernel mode communicate?” is answered with IPC. IPC is communication between two processes; crossing between user and kernel mode is done by system calls (and interrupts).

  • System call = request across the boundary (a trap)
  • Interrupt async · exception sync fault · trap deliberate

What happens when you turn on a computerLEC-6

+ addedUEFI vs BIOS: UEFI supports big disks (GPT, over 2 TB), faster boot, a graphical setup, and Secure Boot (only signed bootloaders run). BIOS+MBR is limited to 2 TB disks and 4 primary partitions. Interview line: “firmware → bootloader → kernel → init”.

32-bit vs 64-bitLEC-7, corrected

32-bit64-bit

Runs32-bit software only64-bit software, and 32-bit with compatibility mode

⚑ correctedThe notes say a 32-bit CPU “executes 4 bytes in one instruction cycle and a 64-bit one 8 bytes”, that extra RAM “doesn’t impact a 32-bit OS”, and that 64-bit “makes graphics faster because of 8-byte calculations”. These are oversimplified: instruction timing is not “bytes per cycle”, 32-bit systems with PAE can address more than 4 GB (but each process still sees at most 4 GB), and graphics speed comes from the GPU, not register width. The real wins of 64-bit: a huge address space per process (memory-mapped files, large heaps), more registers, and a modern instruction set.

The memory hierarchyLEC-8

  • Going down the hierarchy: cheaper per byte, larger, slower, non-volatile. Registers, cache and RAM are primary memory; disks are secondary.
  • It works because of locality of reference: programs reuse recent data (temporal) and nearby data (spatial), so a small fast cache serves most accesses. This same idea drives CPU caches, the page cache, TLBs, and demand paging.

Program vs processLEC-9

In plain wordsA program is a passive file of compiled instructions on disk. A process is a program in execution: the code plus its memory, registers and resources. Two processes can run the same program.
  • How the OS creates a process: load the program and static data into memory → allocate the run-time stack → set up the heap → set up I/O (stdin, stdout, stderr) → hand control to main().

Context switchingLEC-11

  • Switching the CPU from one process to another means saving the old context (registers, program counter) into its PCB and loading the new one from its PCB.
  • It is pure overhead: no useful work happens during the switch. It also hurts caches and the TLB, which makes the real cost bigger than the copy itself. Time slices that are too short waste time here.

Creating processes: fork, exec, wait+ added, the classic Unix question

In plain wordsUnix makes a process in two steps. fork() clones the caller into a child (a near-identical copy). exec() then replaces the child’s program with a new one. The parent wait()s for the child to finish.
pid_t pid = fork();                 // one call, returns TWICE: once in each process
if (pid < 0) {
  perror("fork failed");
} else if (pid == 0) {              // child: fork() returned 0
  execlp("ls", "ls", "-l", NULL);   // replace this process image with `ls`
  _exit(127);                       // only reached if exec failed
} else {                            // parent: fork() returned the child's PID
  int status;
  waitpid(pid, &status, 0);         // block until the child ends, and "reap" it
}
  • The child gets a copy of the parent’s address space, made cheap by copy-on-write: pages are shared until someone writes to them.
  • If a loop calls fork() twice, you get 4 processes; n forks give 2n processes. A classic interview puzzle (“how many times is hello printed?”).

Benefits of multithreadingLEC-15, corrected

  • Responsiveness: a UI thread stays alive while a worker thread does slow work.
  • Resource sharing: threads share memory, so no IPC copying.
  • Economy: creating and switching threads is cheaper than processes.
  • Scalability: on multiple cores, threads run in parallel.
⚑ correctedThe notes say a single-CPU system would “never gain” from multithreading. That is wrong. Even on one core, threads help whenever a thread blocks on I/O (disk, network, user input): another thread runs while it waits, so the CPU stays busy and the program stays responsive. What a single core cannot give you is faster CPU-bound work; only extra cores do that.

Many-to-one / one-to-one / many-to-manyhow user threads map to kernel threadsLinux and Windows use one-to-one; Go and Erlang use many-to-many (goroutines, processes)
+ addedThis is the Node.js story. JavaScript runs on one thread with an event loop, so there are no data races on JS variables, and I/O is handed to the OS (epoll/kqueue/IOCP) and to libuv’s thread pool. CPU-heavy work blocks the loop, so you move it to worker_threads (real threads with their own V8 heap, communicating by messages or SharedArrayBuffer + Atomics) or to a separate process with cluster/child_process. “One thread, many connections” is concurrency without parallelism.

How a thread gets the CPULEC-15

  • Each thread has its own program counter; the OS scheduler picks a thread and runs the instructions at its PC. Context switches happen on blocking I/O or when the time quantum expires, saving state into the TCB.
  • Thread-safety: code touching shared data must be protected (locks, atomics), or it has a race condition (page 8).

Remember!

  • Threads share memory; each has its own stack and registers
  • Thread switch is cheaper than process switch
  • One core still benefits when threads block on I/O
  • Node: one JS thread + event loop + workers

Why scheduling, and the vocabularyLEC-12

In plain wordsIn a multiprogramming system many processes are ready at once. When the CPU becomes free, the short-term scheduler picks one from the ready queue. The policy it uses decides throughput, fairness and responsiveness.
TermMeaningFormula
Arrival time (AT)when the process enters the ready queue
Burst time (BT)CPU time it needs
Completion time (CT)when it finishes
Turnaround time (TAT)from arrival to finishCT − AT
Waiting time (WT)time spent in the ready queueTAT − BT
Response timefrom arrival to the first time on the CPUfirst run − AT
Throughputprocesses completed per unit time
  • Goals: maximise CPU utilisation and throughput; minimise turnaround, waiting and response time.
  • Non-preemptive: once given the CPU, a process keeps it until it finishes or blocks. Simple, but a long job can starve the rest. Preemptive: the OS can take the CPU away (time slice expired, or a higher-priority process arrived). More responsive, with switching overhead.
  • Starvation: a process waits indefinitely. Convoy effect: short processes queue behind one long process.

Round robin (RR)LEC-13

In plain wordsRound robin is FCFS with a stopwatch. Each process runs for at most one time quantum (TQ); if it is not done, it goes to the back of the ready queue. Everybody gets a turn, so nobody starves. It is the standard for time-sharing systems.
  • Depends on arrival order and TQ, not on burst length. No convoy effect, no starvation, good response time.
  • Choosing TQ: too small → too many context switches (overhead dominates); too large → it degrades into FCFS. A common rule: about 80% of bursts should finish within one quantum.

  • RR has a worse average turnaround than SJF but a much better response time, which is what interactive users feel.

Multilevel queue (MLQ)LEC-14

In plain wordsSplit the ready queue into several queues by type of process, and give each queue its own algorithm. A process is permanently assigned to one queue.
Queue (high → low priority)HoldsAlgorithm
System processescreated by the OSe.g. RR
Interactive (foreground)need user input, low latencye.g. RR
Batch (background)run silentlye.g. FCFS
  • Between queues: fixed-priority preemptive (a higher queue always wins), or time-slice between queues (e.g. 80% CPU to foreground, 20% to background).
  • Problem: lower queues can starve, and the assignment is inflexible.

Multilevel feedback queue (MLFQ)LEC-14

In plain wordsLike MLQ, but processes move between queues based on how they behave. It learns which are interactive and which are CPU hogs, without knowing burst times in advance.
Use up your whole quantum and you drop one level down.
  • Rules: new jobs start in the top queue. A job that uses its whole quantum (a CPU hog) is demoted. A job that blocks for I/O before the quantum ends (interactive) stays high. A job that waits too long is promoted (ageing), so nothing starves.
  • Flexible and configurable per system; the basis of schedulers in Windows, macOS and older Unix. Linux uses the Completely Fair Scheduler (CFS, and EEVDF in newer kernels), which gives each runnable task a fair share of CPU based on how much it has used (vruntime), adjusted by its nice value.

The problem: race conditionsLEC-16

In plain wordsWhen two threads or processes touch the same data and at least one writes, the final result can depend on exactly how their steps interleave. That is a race condition. The scheduler can switch threads between any two instructions, so you cannot rely on timing.
// counter is shared, starts at 0. Two threads each run: counter++  (1000 times)
// counter++ is really THREE steps:
//   1. load counter into a register
//   2. add 1
//   3. store the register back
//
// Interleaving that loses an update:
//   T1: load  (reads 5)
//   T2: load  (reads 5)
//   T1: add, store  → 6
//   T2: add, store  → 6     // should be 7: one increment is lost
  • The code region that touches shared data is the critical section (CS). The goal is to let only one thread at a time be inside it.
  • Requirements of a correct solution: mutual exclusion (never two in the CS), progress (if nobody is in the CS, a waiting thread must be able to enter without needless delay), bounded waiting (no thread waits forever).

Condition variablesLEC-17

In plain wordsA condition variable lets a thread sleep until some condition becomes true, instead of spinning and checking. It always works together with a lock: wait() atomically releases the lock and sleeps; when another thread calls signal(), the sleeper wakes and re-acquires the lock before continuing.
// consumer waits until the queue is not empty
lock(m);
while (queue_empty())          // WHILE, not IF: re-check after waking (spurious wakeups)
  cond_wait(&not_empty, &m);
item = pop(queue);
unlock(m);

// producer
lock(m);
push(queue, item);
cond_signal(&not_empty);       // wake one waiting consumer
unlock(m);
  • Purpose: avoid busy waiting. Always test the condition in a while loop.

Readers–writers+ added

  • Many readers may read at once; a writer needs exclusive access. A reader-priority solution counts readers: the first reader locks out writers, the last reader lets them in.

Dining philosophersLEC-20

What deadlock isLEC-21

In plain wordsA deadlock is a set of processes each holding a resource and waiting for one held by another in the set, so none can ever proceed. Resources: memory, files, locks, sockets, devices, database rows. A resource may have several instances (two CPUs, a pool of connections).
  • A process uses a resource in three steps: request (wait if not free), use, release.
  • The two-lock example: T1 holds R1 and wants R2; T2 holds R2 and wants R1. Nothing recovers it, and the processes’ resources stay tied up.

The four necessary conditions (Coffman)LEC-21

#ConditionMeaning
1Mutual exclusiona resource can be used by only one process at a time
2Hold and waita process holding at least one resource waits for more
3No preemptionresources cannot be forcibly taken away; they are released voluntarily
4Circular waitP0 waits for P1, P1 for P2, … Pn for P0

▶ All four must hold at the same time. Break any one and deadlock is impossible. In a resource-allocation graph, a request edge is P → R, an assignment edge is R → P; with single-instance resources, a cycle means deadlock. With multi-instance resources a cycle is necessary but not sufficient.

Avoidance: safe states and the Banker’s algorithmLEC-22 · worked example added

  • A state is safe if there is some order (a safe sequence) in which every process can get its maximum and finish. Unsafe does not mean deadlocked, only that deadlock may happen. Grant a request only if the result is still safe.
  • Data: Available (free units), Max (each process’s declared maximum), Allocation (held now), and Need = Max − Allocation.
  • Safety check: start with Work = Available. Find a process whose Need ≤ Work; pretend it finishes, so Work += its Allocation. Repeat. If all processes can finish, the state is safe.

P00 1 07 5 37 4 3
P12 0 03 2 21 2 2
P23 0 29 0 26 0 0

P40 0 24 3 34 3 1

▶ Total resources (10, 5, 7); Available = (3, 3, 2). Walk: P1 (need 1,2,2 ≤ 3,3,2) → Work = (5,3,2). P3 (0,1,1) → (7,4,3). P4 (4,3,1) → (7,4,5). P0 (7,4,3) → (7,5,5). P2 (6,0,0) → (10,5,7). Safe sequence ⟨P1, P3, P4, P0, P2⟩, so the state is safe. A resource request (Request ≤ Need and ≤ Available) is tried by pretending to grant it and re-running the safety check; if unsafe, the process waits.

Detection and recoveryLEC-22

  • Single instance of each resource: build a wait-for graph (edge Pi → Pj if Pi waits for a resource held by Pj) and look for a cycle periodically.
  • Multiple instances: run a Banker-like detection algorithm (Work/Available, mark processes whose pending request can be met; unmarked processes at the end are deadlocked).
  • Recovery: terminate processes (abort all deadlocked ones, or one at a time until the cycle breaks, choosing the cheapest victim); or preempt resources (take a resource, roll the victim back to a safe state, and avoid starving the same victim repeatedly).

  • 4 conditions, all needed: mutual exclusion, hold & wait, no preemption, circular wait
  • Prevent (break one) · Avoid (Banker) · Detect + recover · Ignore
  • Practical fix: global lock ordering
  • Unsafe ≠ deadlocked

Logical vs physical addressesLEC-24

In plain wordsMany processes share RAM, so the OS must share it and manage it. Each process is given its own private logical (virtual) address space, starting at 0, as if it owned the machine. A hardware unit, the MMU, translates every logical address to a physical address in RAM at run time.
Logical (virtual) addressPhysical address
Generated bythe CPU, while the program runsthe MMU, after translation
Visible tothe program (it thinks this is real)only the hardware/OS; programs never see it
Range0 to maxR + 0 to R + max for a base R (contiguous case)
Set of alllogical address spacephysical address space
Physical = logical + relocation (if logical < limit, else trap). Example: base 14000, logical 356 → 14356.
  • Protection: every address is compared with the limit register. If it is out of range, the hardware traps to the OS (a segmentation fault), which usually kills the process. The dispatcher loads the base and limit of the next process on every context switch.
  • This is how the OS enforces isolation: a process cannot even name another process’s memory.

Dynamic partitioningLEC-24, corrected

  • Partitions are created at load time with exactly the process’s size. No internal fragmentation, and a better degree of multiprogramming.
  • Drawback: external fragmentation. As processes finish, holes of different sizes appear between running ones; a new 8 MB process cannot load even if two separate 5 MB and 3 MB holes exist.
⚑ corrected“No limit on the size of a process” in dynamic partitioning really means no limit from partition size; a process still cannot be larger than available contiguous RAM. The idea of pagingLEC-26

In plain wordsCut a process’s logical memory into fixed-size pages and physical RAM into same-size frames. Any page can sit in any free frame, so the process’s memory does not need to be contiguous. A page table records which frame holds each page.
Pages 0 to 3 land in frames 1, 4, 3, 7: scattered but fine.
  • Address translation: a logical address splits into page number (p) and offset (d). The page number indexes the page table to find the frame number (f); the physical address is f × page size + d. The offset never changes.
  • The page table lives in main memory; its base address is kept in the process’s PCB and in the PTBR (page table base register), so a context switch only reloads one register.
  • Page size = frame size, a power of two (typically 4 KB). Paging eliminates external fragmentation and the need for compaction.
⚑ correctedThe notes present paging as removing fragmentation completely. It removes external fragmentation, but internal fragmentation remains: the last page of a process is rarely full. On average about half a page per process is wasted, so very large pages waste more memory while very small pages make the page table larger.

Worked example: bits and table size+ added

32-bit logical address, page size 4 KB = 2^12 bytes
  offset d      = 12 bits
  page number p = 32 - 12 = 20 bits  → 2^20 = 1,048,576 pages
  page-table entry (PTE) = 4 bytes   → page table = 4 MB per process (!)

Logical address 0x00003A7C:  p = 0x00003 = 3,  d = 0xA7C
  if page 3 is in frame 9:  physical = 9 × 4096 + 0xA7C = 0x9A7C
  • Multi-level paging: a 4 MB flat table per process is wasteful, so the page table is itself paged (a two-level or four-level tree on x86-64). Only the parts of the address space in use need table pages. Inverted page tables keep one entry per frame instead, trading smaller tables for slower lookups (hashed).
  • Each PTE also holds valid/invalid, read/write/execute permission, dirty (modified) and referenced bits. Read-only code pages can be shared between processes (shared libraries).

The TLB: making paging fastLEC-26, typo fixed

In plain wordsWith the page table in RAM, every memory access would need two memory accesses (one for the table, one for the data). The TLB (translation look-aside buffer) is a small, very fast hardware cache of recent page-to-frame translations. On a hit the table is skipped; on a miss the table is read and the entry is added to the TLB.
  • Each TLB entry carries an ASID (address-space identifier) naming its process, so the TLB need not be flushed on every context switch and one process can never use another’s translation. Without ASIDs the TLB is flushed on each process switch, which is part of why process context switches are slow.
Effective access time (single-level page table)
  EAT = h × (t_tlb + t_mem)  +  (1 - h) × (t_tlb + 2 × t_mem)

TLB 10 ns, memory 100 ns, hit ratio 90%:
  EAT = 0.9 × 110 + 0.1 × 210 = 99 + 21 = 120 ns      (vs 200 ns with no TLB, 100 ns ideal)

SegmentationLEC-27

In plain wordsPaging cuts memory into equal blocks that mean nothing to the programmer. Segmentation cuts it along the program’s logical parts (code, data, stack, heap, a library), each of variable size.
  • A logical address is ⟨segment number s, offset d⟩. The segment table has a base and limit per segment. The hardware checks d < limit (else trap) and returns base + d.
  • Pros: matches the user’s view; no internal fragmentation; natural sharing and protection per segment (code read-only). Cons: variable sizes cause external fragmentation and make swapping awkward.

  • Pages (logical) → frames (physical) via the page table
  • Address = (page no., offset); offset unchanged
  • Paging: no external, some internal fragmentation
  • TLB caches translations; EAT = h·(t+m) + (1−h)·(t+2m)

Virtual memory and demand pagingLEC-28

In plain wordsVirtual memory lets a program run even though it is not entirely in RAM. The process sees one huge address space; the OS keeps only the pages in use in RAM and the rest on disk (the swap space). It is why programs can be bigger than RAM, why more programs fit at once, and why processes cannot touch each other.
  • Demand paging: bring a page into RAM only when it is accessed (a lazy swapper). A pager moves individual pages; a swapper would move whole processes, so “pager” is the right word. Pure demand paging starts a process with no pages loaded.
  • The page table’s valid–invalid bit: valid = legal and in RAM; invalid = either not part of the address space, or legal but currently on disk.
  • It works because of locality of reference.

Handling a page faultLEC-28

StepWhat happens
1The program touches a page whose valid bit is 0; the MMU raises a page fault (a trap into the OS)
2The OS checks the process’s internal table: an illegal address → terminate the process (segmentation fault); a legal one → the page is on disk, continue
3Find a free frame (if none, run page replacement, below)
4Schedule a disk read to load the page into that frame (the process waits; the CPU runs another)
5When the disk read finishes, update the page table (frame number, valid = 1)
6Restart the interrupted instruction, which now succeeds
Effective access time with page faults
  EAT = (1 - p) × t_mem + p × t_fault          p = page-fault rate

t_mem = 200 ns, t_fault = 8 ms = 8,000,000 ns, p = 1/1000:
  EAT = 0.999 × 200 + 0.001 × 8,000,000 ≈ 8,200 ns   → about 40× slower
To keep slowdown under 10% (EAT ≤ 220 ns) the fault rate must be below about 1 in 400,000.
+ addedCopy-on-write (COW): after fork() parent and child share the same frames, marked read-only. The first write to a shared page causes a fault, and the OS copies just that page. This makes fork cheap. Memory-mapped files (mmap) use the same machinery: file contents are paged in on demand.

ThrashingLEC-30

In plain wordsIf a process does not have enough frames for the pages it is actively using, it faults, evicts a page it will need again immediately, faults again, and again. The system spends more time paging than computing: CPU utilisation collapses even though the machine looks “busy”.
  • Cause: too high a degree of multiprogramming. Adding more processes raises CPU use at first, then utilisation falls off a cliff once memory is over-committed.
  • Working-set model: give each process enough frames for its current locality (the pages used in the last Δ references). If the total working sets exceed RAM, suspend a process.
  • Page-fault frequency (PFF): set upper and lower fault-rate limits; above the upper bound allocate the process another frame, below the lower bound take one away.
  • Symptoms you can see: heavy disk activity, high si/so (swap in/out) in vmstat, an unresponsive machine. Fix: add RAM, reduce load, or tune memory limits.

Remember!

  • Virtual memory = illusion of a huge address space; demand paging loads on first touch
  • Page fault steps: trap → check → free frame → disk read → update table → restart
  • FIFO 15 · LRU 12 · OPT 9 (the classic string)
  • Thrashing = more paging than work

Files, directories and the inode+ added, the PDF only lists file management

In plain wordsA file system turns a raw disk of numbered blocks into named files in a tree of directories. It decides how files are stored, found, protected and recovered after a crash.
  • On Unix a file’s metadata (owner, permissions, size, timestamps, and the pointers to its data blocks) lives in an inode, not in the file name. A directory is just a table mapping names to inode numbers.
  • Hard link: another directory entry for the same inode (a second name; the data is freed when the link count reaches 0; cannot cross file systems). Symbolic (soft) link: a tiny file containing a path; it can dangle if the target is removed.
  • Permissions: read/write/execute for owner, group and others, e.g. chmod 755 file = rwxr-xr-x.
  • Opening a file: open() returns a small integer, the file descriptor (0 stdin, 1 stdout, 2 stderr). It indexes the process’s descriptor table, which points into a system-wide open-file table, which points to the inode. Each process has a limit on open descriptors (ulimit -n); exhausting it gives the EMFILE / “too many open files” error.

In plain wordsOn a hard disk, the slow part is moving the read/write head (seek time) plus waiting for the platter to rotate (rotational latency). When many requests are queued, the order in which the OS serves them changes the total head movement. SSDs have no moving head, so this matters mainly for HDDs.

Rapid-fire concept questionssay the one-liner, then add the edge

QuestionOne-line answer
Process vs thread?A process has its own address space; threads of one process share memory but have their own stack and registers. Threads are cheaper to create and switch, but need synchronisation.
Concurrency vs parallelism?Concurrency: many tasks in progress, interleaved (even on one core). Parallelism: tasks running at the same instant on several cores.
What is a context switch and why is it costly?Saving one process’s CPU state in its PCB and loading another’s. No useful work happens, and caches/TLB lose their contents.
User mode vs kernel mode?User mode cannot run privileged instructions or touch hardware; kernel mode can. A system call or interrupt switches into kernel mode.
What is a system call?The controlled way a program asks the kernel for a service (file, process, network), implemented as a trap.
Monolithic vs microkernel?Monolithic: all services in one kernel, fast but a driver bug can crash it. Microkernel: minimal kernel, services in user space, safer but slower.
Zombie vs orphan?Zombie: finished, not yet reaped by its parent. Orphan: parent exited first; adopted by init.
What is a race condition?The result depends on the interleaving of threads touching shared data. Fix with mutual exclusion or atomic operations.
Mutex vs semaphore?Mutex: one owner, mutual exclusion. Semaphore: a counter for N resources or for signalling; no owner.
The four conditions for deadlock?Mutual exclusion, hold and wait, no preemption, circular wait. Break any one to prevent it.
Deadlock vs starvation vs livelock?Deadlock: blocked forever in a cycle. Starvation: one process is perpetually passed over. Livelock: active but making no progress.
Which scheduling algorithm minimises average waiting time?SJF/SRTF, but it needs burst times, which are unknown, so real systems estimate or use feedback queues.
Internal vs external fragmentation?Internal: waste inside an allocated block. External: free space broken into unusable pieces.
Paging vs segmentation?Paging: fixed-size, invisible to the programmer, internal fragmentation. Segmentation: variable-size logical units, external fragmentation.
What is a TLB?A small hardware cache of page-to-frame translations that avoids a page-table memory access.
What is virtual memory?An abstraction giving each process a large private address space, with only the used pages in RAM and the rest on disk.
What causes thrashing?Too little memory for the active working sets, so processes page-fault constantly. Reduce the load or add memory.
What is Belady’s anomaly?With FIFO page replacement, more frames can produce more page faults.
Hard link vs soft link?Hard: another name for the same inode. Soft: a file holding a path to the target.
What is an inode?A file’s metadata record (owner, permissions, size, block pointers). The name lives in the directory.

Quick checkanswers folded away

1. Why can a single-core machine benefit from multithreading?

When one thread blocks on I/O, another can run, so the CPU stays busy and the program stays responsive. It cannot speed up pure CPU-bound work.

2. Processes: P1 (AT 0, BT 7), P2 (2, 4), P3 (4, 1), P4 (5, 4). What is the average waiting time under FCFS?

Completion times 7, 11, 12, 16; waiting times 0, 5, 7, 7; average 4.75.

3. In round robin, what happens if the time quantum is huge? Tiny?

Huge: it behaves like FCFS. Tiny: too many context switches, so overhead dominates.

4. Why does wait() on a condition variable release the lock?

So another thread can enter the critical section and change the condition. Holding the lock while sleeping would deadlock.

5. Why can the dining philosophers deadlock with plain semaphores? Name one fix.

If all grab their left fork at once, each waits for the right fork forever (circular wait). Fixes: at most 4 seated, take both forks atomically, odd/even order, or a global order.

6. Is an unsafe state a deadlock?

No. An unsafe state only means deadlock may occur; Banker’s algorithm avoids entering it.

7. 32-bit address, 4 KB pages: how many bits are the page number and offset?

Offset 12 bits, page number 20 bits (220 pages).

8. TLB 10 ns, memory 100 ns, hit ratio 90%. Effective access time?

0.9 × (10 + 100) + 0.1 × (10 + 200) = 120 ns.

9. Which page-replacement algorithm is optimal, and why isn’t it used?

OPT (evict the page used farthest in the future). It needs knowledge of future references, so it is used only as a benchmark.

10. What does exit code 137 in a container usually mean?

The process received SIGKILL (128 + 9), commonly from the kernel’s OOM killer after exceeding its memory limit.

11. How does an OS stop one process from reading another’s memory?

Separate virtual address spaces translated by the MMU through per-process page tables, with permission bits; invalid accesses trap to the OS.

12. Why does a system call cost more than a normal function call?

It crosses the user/kernel boundary: a trap, a mode switch, argument checking, and often cache/TLB side effects.
