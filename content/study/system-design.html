What system design is

From: System Design 101 (intro) + added: requirements, scaling

Low-level design (LLD) is how you organise code inside one component: classes, methods, patterns. High-level design (HLD), which is what “system design” usually means, is about the whole system: which components exist (servers, databases, caches, queues) and how they talk, so the system stays fast and efficient. A large system is many components or services working together.

Why one machine is not enough

A single machine has a ceiling on CPU, memory, disk and network. It is also a single point of failure: if it dies or restarts, everything is down. So we spread work over many machines. That is a distributed system, and almost every idea in this notebook is a way to make many machines behave like one reliable machine.

Start with requirements

+ added: functional vs non-functional

Before drawing boxes, write down two lists.

  • Functional requirements: what the system does. For a bookmarking site: add a bookmark, list my bookmarks.
  • Non-functional requirements: how well it does it. Typical ones: latency (how fast), availability (how often it is up), consistency (do all users see the same data), durability (data is never lost), scalability (copes with growth), cost.

Non-functional requirements pull against each other. That tug-of-war is the real subject of system design.

Back-of-the-envelope estimates

From: System Design 101 (Delicious storage math) + added: method

Before designing, ask how big is this? A rough number tells you what to worry about: storage, requests per second, or bandwidth. All figures below are approximations.

The Delicious example from your notes

  • ≈ 1,000,000 new bookmarks per day, each ≈ 200 bytes → ≈ 200 MB of new data per day.
  • A 2004 machine had a ≈ 40 GB disk → 40,000 MB ÷ 200 MB ≈ 200 days ≈ about six or seven months until the disk is full.
  • That is why you must split data over machines: sharding (next chapter).
⚠ older pattern

“40 GB disk” is a 2004 detail. Today one disk holds terabytes, so a single machine would take years to fill with this data. The method is what matters; redo the math with today’s numbers for any new problem.

The method (works for any system)

  1. Pick the daily volume. Seconds in a day ≈ 86,400 ≈ 10⁵, a handy rounding.
  2. Requests per second ≈ requests per day ÷ 86,400. Example: 1,000,000 ÷ 86,400 ≈ 12 writes per second on average.
  3. Peak is higher than average. A made-up rule of thumb: plan for ≈ 2–5× average. State it as an assumption.
  4. Storage ≈ items per day × size per item × days kept. Add copies if you replicate (3 copies = ≈ 3×).
  5. Read/write ratio: most systems read far more than they write. For bookmarks, assume ≈ 10–100 reads per write (a guess). That changes the design: read-heavy systems love caches.
  6. Bandwidth ≈ requests per second × size per request. Here ≈ 12 × 200 B ≈ 2.4 KB/s, which is tiny.
Remember

The math shows storage, not write speed, is the problem for Delicious. Estimation tells you which problem you actually have.

Delicious, and how the web finds your machine

From: System Design 101 and Consistent Hashing

Back in 2003 a website called Del.icio.us started on a single laptop in a dorm room. Browsing the web was bookmark-based, and you lost your bookmarks whenever you changed browser or machine. Delicious let you log in and keep bookmarks online. It really did only two things:

addBookmark(userId, site_url)
getAllBookmarks(userId)

If you can code those two functions on your laptop with MySQL on the same laptop, version one is done. The hard part is everything after that.

Problem 1: how do people reach my laptop?

The internet only understands IP addresses, the numeric address of a machine. People type del.icio.us, not numbers. So someone has to translate a name into an address.

  1. You buy the domain name from a registrar (GoDaddy, Namecheap, and so on).
  2. Your notes say a central body, ICANN, keeps the directory of all domain names, their owners and validity dates.
  3. You create an A record that ties your domain name to your laptop’s IP address. That record gets registered centrally.

But ICANN alone is a bad design

If every lookup in the world went to one central directory, it would be a single point of failure and a bottleneck. So thousands of machines around the internet hold copies of that information. These are DNS machines (Domain Name Servers). They keep checking the central source every few hours for updates.

⚠ older pattern (a simplification)

The picture “ICANN holds everything and DNS machines copy it” is a teaching shortcut. Your notes also say they will not go deep on DNS, which is fine for now. Treat the paragraph above as the idea, and the green box as the real picture.

+ added: how DNS really works
  • DNS is a hierarchy, not one copied table. Roughly: root servers know who runs each top-level domain (like .com); that registry knows which name server is in charge of your domain; your domain’s name server holds your A record.
  • ICANN coordinates the whole system and the root. Registries run each top-level domain (for example, Verisign runs .com); registrars like GoDaddy sell the names to you.
  • Answers are cached on your ISP’s resolver and your device for a time set by the record’s TTL (time to live). That is why DNS changes can take a while to spread.
  • Record types you will meet: A (name → IPv4 address), AAAA (name → IPv6), CNAME (name → another name).

Your PDF also lists two further readings about A records versus CNAME/alias (Namecheap and DNSimple); they are on the last page.

Remember

A domain name is useless until it maps to an IP. DNS is a cached, copied phone book, and caching again shows up everywhere in system design.

Many laptops and a load balancer

From: System Design 101 + added: L4/L7, deploys

Problem 2: every new release takes me offline

Each time you ship new code you restart the laptop, and Delicious is unavailable for a few seconds. Not good. The idea: keep several laptops with the same code and the same information (keeping the information in sync is a later problem). While you deploy to laptop X, no traffic should go to X.

Something must keep track of which machines are running and split traffic among them. That is the load balancer (LB).

How does the load balancer decide?

  • Which machines are alive? Heartbeat / health check: the LB regularly pings each machine; one that stops answering gets no traffic.
  • How to split the load? Round robin (take turns), weighted round robin (bigger machines get more turns), IP hash (the same client IP tends to reach the same machine).

Your notes point to an nginx config example (link on the last page).

+ added
  • Least connections: send each request to the machine with the fewest open requests. Better when requests have very uneven cost.
  • L4 vs L7. An L4 (transport-level) balancer only looks at IP and port: very fast, but blind to what the request is. An L7 (application-level) balancer reads the HTTP request, so it can route /images and /api to different groups, end TLS, and read cookies.
  • Rolling deploy: take one machine out of rotation, wait until its in-flight requests finish (“drain”), update it, wait until its health check passes, put it back, repeat. No downtime.
  • The LB can itself become a single point of failure, so real setups run it as a redundant pair or use a managed service.
  • Sticky sessions (always send one user to the same machine) are easy but make machines non-interchangeable. The next chapter on caching explains why stateless servers are better.
Trade-off

Round robin is simple and needs no state, but ignores that some requests are far heavier.

Least connections adapts to load, but the LB must track live counts.

Sharding: splitting the data

From: System Design 101 + added: other strategies

Delicious takes off: ≈ 1 million bookmarks a day, ≈ 200 MB of new data daily (see the estimates page), and a 2004 disk fills in months. You must split the information across machines. That is sharding; each machine (or group of machines) holding a slice is a shard.

Step 1: choose the sharding key

The sharding key is the field whose value decides which shard a record lives on. Ask: what information must never be split across machines?

Key = site_url

Bookmarks of one user are scattered everywhere. getAllBookmarks has to ask every machine and merge the answers.

Key = user_id

A user and all their bookmarks live on one shard. getAllBookmarks talks to exactly one machine.

Step 2: map user_id to a shard

The mapping rule must:

  • be very cheap to compute (the load balancer cannot be slowed down),
  • spread load roughly evenly (no skew),
  • make adding a shard easy, without long downtime,
  • make removing a shard easy too.

Approach 1: user_id % number_of_shards

Great until the number of shards changes. Then the answer for almost every user changes, so almost every user’s data has to be copied to another machine, which means huge downtime. With 4 shards going to 5, a user stays put only if id % 4 equals id % 5, which happens for ≈ 1 user in 5. So ≈ 80% of users move. You can watch this on the ring lab page.

Approach 2: ranges

Say users 1 to 1M go to shard 1, the next million to shard 2, and so on. Problems from your notes: early adopters tend to be the busiest users, so one range is hotter (skew); every range’s storage only grows as people add bookmarks; and adding a new shard does not relieve the existing ones.

Trade-off
Good atBad at
% shardsDead simple, even spreadResharding moves ≈ everything
RangesRange scans, easy to understandSkew; new shards do not help old ones
Consistent hashing (next page)Adding or removing a shard moves only a slice; even-ish spreadMore moving parts to build

Consistent hashing

From: System Design 101 and Consistent Hashing + added: alternatives, replicas

The idea used in most real systems. Picture a circle of positions from 0 to 10¹⁸. A hash function H1 turns each machine id into a position on the circle; another hash H turns each user id into a position. A user belongs to the first machine you meet going around the circle from the user’s position.

In code: keep a sorted array of the machines’ hash positions. For each user, compute the hash and binary search for the first machine position bigger than it (wrapping to the first one if you run off the end). That machine owns the user.

The flaw: removing a node

Say Node 2 dies. All its users (Deyan, Affrica) go to the next node, Node 5, whose load roughly doubles. Overloaded, Node 5 may die too, dumping triple the load on Node 4, and so on: a cascading failure.

The fix: many positions per machine (virtual nodes)

Use many hash functions per machine, so each machine appears at many places on the circle. When a machine dies, its slices go to many different neighbors, not one.

  • Adding a machine: its points steal small arcs from many neighbors, so only ≈ 1/(N+1) of keys move, and they come evenly from everybody.
  • The more virtual points per machine, the smoother the spread.
+ added
  • Weights: give a bigger machine more virtual points so it takes a larger share.
  • Replication on the ring: to keep 3 copies, store each key on the next 3 distinct machines clockwise. Dynamo-style stores such as Cassandra work this way (in spirit).
  • Alternatives you may meet: rendezvous (highest-random-weight) hashing and jump consistent hash.
Trade-off

More virtual points mean smoother load, but a bigger ring table to store and update whenever the membership changes.

Remember

Consistent hashing makes the amount of data that moves proportional to what changed, not to the whole data set.

Separate the code from the storage

From: System Design - Caching 1 + added: stateless servers

Recap from before: the browser asks DNS for an IP, a load balancer spreads traffic over machines, and when data no longer fits on one machine we shard (with consistent hashing). But in that model every machine held both the code and the storage. Is that a good model?

It is not, for two reasons
  • Tight coupling: a code deployment restarts the machine, which also takes its database offline, so deployments cause unavailability.
  • Fewer resources for the code: the database also eats CPU, memory and disk on the same box.

So decouple them. Machines that run only code are called application servers (app servers). They hold no data, so they are stateless and easy to scale: add more of them behind the load balancer. The data lives in a separate database tier.

Trade-off

You gain: deploy code without touching data, scale code and storage independently, let the database use a whole machine.

You pay: an extra network hop from code to database on every query (see the latency page: a datacenter round trip is ≈ half a millisecond).

+ added: what “stateless” means in practice

A stateless server keeps nothing between requests that another server would need. Anything that must persist, such as a user’s login session, lives in the database or a shared cache. Then any request can go to any app server, and a dead server loses nothing.

Remember

Stateless app servers scale easily; the stateful tier (the database) is where the hard problems live, and most of this notebook is about it.

Caching: four places to keep a copy

From: System Design - Caching 1 + added: headers, purging

Caching means storing things closer to you, or in a faster storage system, so you can get them quickly. It happens at several levels.

1. In-browser cacheSmall items that rarely change: DNS answers (so the browser skips the DNS server), images, videos, JavaScript files. That is why a site loads slowly the first time and fast the next.
2. CDN (content delivery network)Copies of big files kept near the user, in many regions.
3. Local cacheOn the application server itself, so it does not hit the database repeatedly.
4. Global cacheOne shared in-memory cache for all app servers (also called in-memory caching). In practice: Redis and Memcache.
The database / file storageThe actual source of truth.

CDN in more detail

Your browser is in India and the files sit on servers in the US. The small HTML/code part arrives quickly because it is small, but large images and video suffer from the distance. A CDN company keeps machines in every region, stores your data on all of them, and hands out links to the copy nearest the user. Examples from your notes: Akamai, Cloudflare, Amazon CloudFront, Fastly. You pay per use.

How does your browser reach the nearest copy? Two ways from your notes: many ISPs integrate with CDNs (Netflix’s CDN works like this), and anycast (many machines share one address and the network routes you to the closest). Fetching from the nearest machine is itself a form of caching.

Two problems every cache has

From: System Design - Caching 1 + added: cache-aside, stampede

A cache is limited in size and is not the source of truth (it holds a replica). That gives two problems:

  • Stale data: the database changes but the cache still has the old copy.
  • Full cache: the cache is small, so what do you do when it fills up?

The first is answered by invalidation, the second by eviction (two pages ahead).

TTL (time to live)

Each entry is valid only for a set time. Example: you cache entry X at time T with a TTL of 60 seconds. Any request for X before T+60 s reads straight from the cache. A request at T+61 s finds X gone and fetches it again. Use TTL when being slightly out of date for a short time is acceptable.

+ added: the cache-aside pattern (the everyday one)
  1. Read: look in the cache. Hit → return it. Miss → read the database, put the result in the cache (with a TTL), return it.
  2. Write: update the database, then delete the cache entry so the next read refills it. Deleting is safer than overwriting because two racing writers cannot leave a wrong value behind as easily.

Why the hit rate matters (made-up numbers)

Say a cache hit costs ≈ 1 ms, and a miss costs ≈ 1 ms (the check) + ≈ 50 ms (your notes’ database assumption) = ≈ 51 ms. The average time is hits × 1 + misses × 51:

Hit rateAverage ≈
50%≈ 26 ms
90%≈ 6 ms
99%≈ 1.5 ms

Going from 90% to 99% hits makes things ≈ 4× faster on average. Misses are what hurt.

+ added: cache stampede

When a very popular entry expires, hundreds of requests may all miss at once and hammer the database together. Common cures: add a small random amount to each TTL (so entries do not all expire together); let only one request rebuild the entry while the others wait; refresh popular entries just before they expire. Also consider caching “not found” answers briefly (negative caching).

Trade-off

A short TTL keeps data fresher but causes more misses and more database load; a long TTL does the opposite. There is no value that is right for everything.

Keeping the cache and the database in sync

From: System Design - Caching 1

Three strategies from your notes decide how a write travels.

Write-through

A write passes through the cache first (there may be several cache machines): update the cache, then update the database, then return success. If the database write fails, the cache change is reverted. Writes get slower, reads get much faster, because the cache is always current. Good for read-heavy systems.

Write-back

Write to the cache; the moment that succeeds, return success. The database is updated later and asynchronously, without blocking the request. Use it where losing a bit of data does not matter, for example an analytics system where trends survive losing a record or two. It is inconsistent, but gives very high throughput and very low latency.

Write-around

Writes go straight to the database. The cache may be out of date, so use a TTL or a similar mechanism to refresh it from the database.

It is a three-way pull between speed, freshness and safety of data. Write-through favors freshness and safety, write-back favors speed.

Eviction: when the cache is full

From: System Design - Caching 1 + added: LFU, walk-through

To add something to a full cache you must remove something. Your notes list these strategies:

  • FIFO (first in, first out): drop the oldest entry.
  • LRU (least recently used): drop the entry untouched for the longest time.
  • LIFO (last in, first out): drop the newest entry.
  • MRU (most recently used): drop the one just used.

Choose by asking which entries are most likely to be used again? The goal is many cache hits and few misses. For typical web data, recently used things are likely to be used again, which is why LRU is the usual choice.

LRU walk-through

Cache holds 3 items. Requests arrive: A, B, C, A, D. The list shows least recent first.

+ added
  • LFU (least frequently used): drop the entry used the fewest times. Good when a few items are always popular; it can keep old popular items too long.
  • Random eviction is surprisingly decent and nearly free.
  • Implementation you can build with your DSA: a hash map plus a doubly linked list gives O(1) LRU for both lookup and update.
  • MRU or LIFO make sense only for odd patterns, such as repeatedly scanning a data set bigger than the cache.
Trade-off

Smarter policies (LFU variants) need more bookkeeping per entry. Simple ones are cheaper but guess worse.

Case study: slow code submissions

From: System Design - Caching Contd.

You submit a solution to a DSA problem on Scaler. The browser talks to the load balancer, and the submission goes to one of many app servers. That server receives the user id, problem id, code and language. To run your code it needs the problem’s input file and expected output file. They can be large, and fetching them from file storage takes ≈ 2 seconds (an assumption), so submissions are slow.

Assumptions from your notes (teaching numbers, not measurements):

  • File already on the app server’s disk: ≈ 40 ms to read.
  • Reading a table or column from the MySQL machine: ≈ 50 ms.
  • Fetching from file storage: ≈ 2,000 ms.

Catch: the input and output files can be edited, and the edit must show up in the very next submission.

First idea: a TTL

  • TTL very low (say 1 minute): files expire every minute, so most submissions miss and go to slow file storage.
  • TTL very high (say 60 minutes): invalidation happens too late. If you edit the files in that window, the change is not visible immediately.

TTL can be used (tune it with the miss rate and invalidation rate) but it is not a good fit because the requirement says immediately.

Second idea: one global cache machine

  1. In memory: one remote machine has limited RAM and the files are huge, so it fills fast and the eviction rate is high, giving many misses.
  2. On its disk: now you move huge files across the network on every request.

Neither works. What if the app server could cheaply ask whether its local copy is still current? That is the next page.

Case study: invalidate with metadata

From: System Design - Caching Contd.

Keep a small table in MySQL that describes the files, not the files themselves:

problems_test_data
problem_id | input_filepath | input_file_updated_at | input_file_created_at
(plus the same columns for the expected-output file)

When a file is changed in file storage, its row is updated too. Now name each cached file with its version, for example (problem_id)_(updated_at)_input.txt. Because the version is part of the name, the name itself tells you whether the copy is current.

On every submission

  1. Read the file’s path and updated_at from MySQL (≈ 50 ms by assumption).
  2. Build the name from them and look on the app server’s disk.
  3. Found: it is guaranteed to be the right version. Read it (≈ 40 ms).
  4. Not found: use the path to fetch it from file storage, and also save it locally for next time.
  5. Same for the expected-output file.

The metadata read is almost free because you were going to read the database for other things anyway (is it already solved, problem score, user score). Fetch the file metadata in the same query. Total on a hit ≈ 50 + 40 = ≈ 90 ms versus ≈ 2,000 ms: about 22× faster, using the assumed numbers.

Updating a file

For problem 200, an admin replaces the input file:

  1. Upload the new file to file storage (for example S3). It returns a path, say new_path.
  2. Update the metadata row: new path and updated_at = NOW().
  3. The next submission reads the new updated_at, builds a different file name, misses locally, fetches the new file from new_path, and stores it. Later submissions hit.

Old versions stay on disk until your eviction policy removes them. The database, not the cache, decides which version is valid.

⚠ source typo

The PDF’s update query is written UPDATE problem_test data WHERE problem_id = 200 SET …. Real SQL puts SET before WHERE and the table is spelled problems_test_data:

UPDATE problems_test_data
SET input_filepath = 'new_path', input_file_updated_at = NOW()
WHERE problem_id = 200;
+ added
  • This is versioned keys (also called cache busting): never edit a cached thing, make a new name for the new version. It is the same trick as app.3f9a1c.js on websites.
  • A content hash in the name works too and cannot collide the way two timestamps in the same instant might.
  • Your notes also say a separate cache per machine beats one single shared layer for these huge files, citing the latency numbers list.
Trade-off

You gain: clean invalidation (always correct, no guessing), fast hits, no expiry-time tuning.

You pay: one metadata read per submission (hidden if you already read the DB) and disk space for old versions. A submission that read the metadata just before an edit may still use the old file; decide if that is acceptable.

Remember

When you can ask a small, cheap source of truth “which version is current?”, you can cache the big thing forever and never serve stale data.

Case study: the contest ranklist

From: System Design - Caching Contd. + added: sorted sets

During a contest with huge traffic, people are on the problem list, reading a problem, or watching the rank list. If scores change constantly, computing the rank list means sorting everybody, which is expensive. If every viewer triggers that on the database, the database melts.

The idea

Compute the rank list periodically (say once a minute), keep that static copy in a cache for that minute, and serve everyone from the copy.

Local cache or global cache?

A local cache lives on each app server. With many servers, every server misses once a minute, so you recompute many times. A global cache is shared by all app servers, so there is just one miss a minute. Here global caching beats local caching. SQL databases

From: System Design - SQL vs NoSQL + added: indexes, isolation

SQL databases are relational: data sits in tables that relate to each other, each table has a fixed set of columns, and you can query across tables to pull related information together.

Normalization

Store each fact once. Imagine two tables both store a player’s score. One gets updated and the other does not: now there are two scores and nobody knows which to trust. Normalizing means keeping one copy and pointing to it from elsewhere, which avoids redundancy and keeps tables consistent.

ACID transactions

  • Atomicity: a transaction is all or nothing. No half-finished state; either every statement completes or all are rolled back.
  • Consistency: the data is valid before and after a transaction. It may be temporarily inconsistent during it.
  • Isolation: concurrent transactions do not interfere (no dirty reads, for example).
  • Durability: once committed, changes survive a reboot or crash.

Example from your notes. Rohit withdraws ₹1000, so the app must (1) check balance ≥ 1000, then (2) set balance = balance − 1000 and dispense cash. His balance is ₹1500. If the two steps run separately, another withdrawal of ₹1000 can sneak in between: balance becomes ₹500, then step 2 runs and sets it to −500. Without atomicity and isolation, concurrent changes to the same data break things. Grouping both steps into one transaction fixes it:

BEGIN;
UPDATE accounts SET balance = balance - 1000
 WHERE id = 7 AND balance >= 1000;   -- 0 rows changed means refuse
COMMIT;

Defined schema

Each table has fixed columns, and each column’s type and size is known. Example: UserID int (4 bytes) + Username varchar(20) (20 bytes) + Timestamp datetime (8 bytes) = a maximum record size of ≈ 32 bytes. Because rows have a known size, the database can calculate where records sit on disk. The price is a rigid schema.

+ added
  • Index: like a book’s index. A side structure (often a B-tree) lets the database find rows without scanning the whole table. It speeds reads, slows writes slightly, and uses extra space.
  • Isolation levels (read committed, repeatable read, serializable) trade safety for concurrency. Stronger isolation is safer but allows less parallel work.
  • Two different “consistency”s: the C in ACID means “the data obeys its rules”. The C in CAP (later page) means “all copies agree on the latest value”. Your notes warn about this confusion directly.
Remember

SQL gives you cross-table queries and ACID, in exchange for a fixed schema and (as the next page shows) trouble once data must be split across machines.

Where SQL struggles

From: System Design - SQL vs NoSQL + added: modern SQL options

1. A fixed schema does not fit every use case

Design the Product table for an e-commerce site. A t-shirt has collar type, size, color, neck type. A MacBook Air has RAM size, disk size, disk type, screen size. Products have starkly different properties:

  • They do not fit one table. Storing attributes as one big string makes filtering and searching inefficient.
  • With ≈ 100,000 kinds of products, one table per kind is a nightmare.
  • SQL is built for millions of rows in one table, not millions of tables.

You want a flexible schema that holds each product’s own attributes efficiently.

+ added

Modern SQL databases add partial answers: a JSON column type (store flexible attributes in one column and index inside it) or the “entity-attribute-value” pattern (one row per attribute). Each has costs, such as harder queries and weaker constraints. Document databases (next pages) go all in on flexibility.

2. Sharding takes away SQL’s advantages

  • When data must be sharded for size, running a SQL query gets hard and costly.
  • A JOIN across machines erases the advantages SQL offered.
  • You do not want to visit many machines for one query; you want all the data in one place.

Your notes conclude that, after sharding, SQL has “almost zero power”, and that PostgreSQL and SQLite do not support sharding at all. So you look at other storage: NoSQL.

⚠ older pattern

That last claim is true of plain, single-node installs, but it is too absolute today. You can shard SQL: Vitess shards MySQL, the Citus extension shards PostgreSQL, and distributed SQL databases such as Google Spanner, CockroachDB and YugabyteDB shard automatically and keep SQL and transactions. Their cost is coordination: cross-shard transactions and joins are slower than on one machine. Your notes also mention Facebook sharding MySQL by hand (see the manual sharding page).

Sharding forces denormalization

Take a messenger app sharded by UserID: machine M1 holds everything about U1’s conversations, M2 holds U2’s, and so on. When U1 messages U2, the message must be stored on M1 (U1’s sent box) and M2 (U2’s received box). That is denormalization: the same data in two places. Choosing the sharding key carefully minimizes such copies.

Trade-off

Normalized data is clean to update but needs joins. Denormalized data reads fast from one machine but has duplicates to keep in sync. Sharding pushes you toward the second.

LSM trees (1): from a plain file to a memtable

From: System Design - NoSQL Internals - LSM Trees + added: where real systems use it

This answers the “update problem” from earlier. NoSQL values have no fixed size, so the B-trees SQL uses (which expect fixed-size entries, with reads and writes around O(log N)) do not fit directly. The question: how do we store variable-size data so that updates are cheap and reads are fast, and how do we tune it for read-heavy or write-heavy use?

Two kinds of storage

  1. WAL (write-ahead log): an append-only record of every write. Replaying it from zero rebuilds the database. You almost never read it, except its tail (“the last Y entries after time X”).
  2. The current state of the data: what we design next, using a key-value store as the example.

Building it up, one idea at a time

  1. Brute force: one file of key, value pairs. To update ID 002 you scan the file; to read it you scan again. Values vary in size, and concurrent updates of one key need a write lock. Slow all round.
  2. Only append. A new value for ID 002 is just added at the end. Writes become very fast and need no locks, because every entry is immutable. Reads still search from the end until the first match, which is O(N). Costs: duplicate keys waste space.
  3. Add an in-memory hash index from key to its byte offset in the file. A read becomes “look up the offset, read n bytes there”. A write is an append plus one map update. Two flaws: billions of keys may not fit in memory, and old duplicates still pile up.
  4. Cut the file into chunks and keep the newest in memory. Chunks of, say, ≈ 100 MB. The newest chunk, the memtable, lives in RAM and is updated in place, so it has no duplicates. A full memtable is written to disk as an immutable chunk. In the background, compaction merges old chunks (X and Y) into a new chunk Z with duplicates removed, then deletes X and Y. The lecture suggests running it in off-peak hours.
  5. Sort the keys. Keep the memtable in a balanced tree (a TreeMap: red-black or AVL), so it can be flushed in sorted key order. That file is an SSTable (sorted string table). Binary search needs to know where an entry starts, so split each SSTable into blocks of ≈ 64 KB and keep an index of only the first key of each block. A 1 GB file is ≈ 16,000 blocks, so that index easily fits in memory.
The LSM tree in four parts
  • A memtable (sorted, in memory): all new writes land here, overwriting the same key.
  • A list of SSTables on disk, newest to oldest.
  • An in-memory block index for each SSTable.
  • A compaction process that merges SSTables like a merge sort of sorted arrays.

Writing

write(key, value):
    memtable[key] = value                 # that is the whole write
    # (also append it to the WAL first, for crash safety: next page)

flush():                                  # when the memtable is big enough
    new_sstable = []
    for key, value in memtable.sorted_items():
        put into the current 64 KB block; start a new block when it is full
        remember the first key of every block in the index

Newest first, because the newest entry for a key is the true one.

Questions the lecture raises

The machine restarts and the memtable (RAM) is lost?

That is what the WAL is for. Before the machine serves requests again it replays the log entries written after the last flush, rebuilding the memtable. This is fast, because everything happens in memory; the slowest step is reading the log from disk.

How does it work for column-family stores?

Mostly the same, with small changes: a write appends to (rowKey, columnFamily); compaction merges the entries it finds instead of keeping only the newest; and a read for “the last X entries” takes what the memtable has, then keeps reading SSTables until it has X entries or runs out.

How does delete work?

A delete is just another write: a special value called a tombstone. If the newest value found for a key is a tombstone, the answer is “key does not exist”. The real space is reclaimed later, when compaction merges the files.

+ added: the delete-vs-write remark in your NoSQL Contd. notes

That lecture says delete is much faster than write because it only removes a reference while a write changes every bit. That is true for deleting a file in a file system (it is why deleted files can often be recovered). In an LSM store a delete is itself a write (the tombstone), so it costs about the same as any other write, and disk space returns only after compaction.

Reading a key that does not exist is very expensive

You check the memtable and then every SSTable, scanning a 64 KB block in each, only to learn it is not there. Fix: a Bloom filter per SSTable, a tiny in-memory structure answering “might this key be in this file?”

  • doesKeyExist(key) returns false: the key is definitely not there. Skip the file.
  • It returns true: the key may or may not be there. Go and look.
  • It must be very space-efficient, so it fits in memory. The more accurate it is, the more reads it saves.

The lecture links an interactive Bloom filter tutorial (last page).

+ added
  • A Bloom filter never gives a false “no”, but it can give a false “yes”. Roughly ≈ 10 bits per key gives ≈ 1% false “yes” answers; more bits, fewer mistakes (approximate figure).
  • WAL durability trade-off: forcing every log write to disk before replying is safest but slowest; batching the forced writes is faster but a crash can lose the last few.

Transactions and rollback

From: System Design - SQL vs NoSQL (questionnaire points) + added: 2PC, saga

How a bank transfer is rolled back

A sends ₹1000 to B. This is not one instant action; the transaction has states:

  1. Money is deducted from A. The transaction enters a state your notes call send_initiated (just a name).
  2. If B’s account is credited, the state becomes send_completed.
  3. If B’s deposit fails because of an internal problem, A’s side is rolled back: the ₹1000 is added back to A. The bank may first retry the transfer, which is why money sometimes returns after 1–2 days.
  4. If the failure is permanent, A’s deduction is reversed for good.
+ added: this is the “saga” idea

When one transaction spans several machines, you cannot rely on one database to undo everything. Instead you run a sequence of local steps, each with a compensating action that undoes it (debit ⇄ refund). Compare the two main techniques:

Two-phase commit (2PC)Saga
HowA coordinator asks all parties “can you commit?” (prepare), then tells all to commit or abortLocal transactions in order; if one fails, run compensations
You gainAll-or-nothing across machinesNo long locks; keeps working while parts are slow
You payLocks held while waiting; blocks if the coordinator dies; slowStates are visible in between (eventually consistent); compensations are hard to write

To make retries safe, give each transfer an idempotency key so doing it twice has the same effect as doing it once.

ACID on top of NoSQL

Your notes say: ACID is not built into NoSQL, but you can build it. Keep a central shard machine, send every write through it, and allow a write only after getting the write lock from that machine. That gives atomicity and isolation. And atomicity and isolation are not the same as consistency.

+ added: ACID vs BASE

BASE is the playful opposite of ACID: basically available, soft state, eventually consistent. It means “stay up and let copies agree later”. It describes a mindset more than a precise guarantee.

From: System Design - SQL vs NoSQL (“Problem Statement 2”) + added: one possible sketch

The task from your notes: design a manual sharding system (a black box with Store, Retrieve and Add machines) that supports:

  • adding a new shard, with data migration,
  • when a machine dies inside a shard, taking the steps needed to restore the replication level,

Read this first

The lecture’s own answer is on the next three pages (orchestrating shards, and multi-master). What follows here is my earlier sketch, built from the ideas in this notebook, with its costs. Compare the two: they overlap a lot, and the lecture adds standby machines, a staging phase and a real phase, and multi-master.

A sketch

  • Router: hashes the key onto a consistent-hash ring of shards (with virtual points) and sends the request to that shard.
  • Shard: a small group of machines holding the same data (say a leader plus two copies; the “3 copies” is a common choice, not a rule). Writes go to the leader and are copied to the others.
  • Metadata service: a small, highly reliable store holding the shard map and which machines belong to which shard. The Zookeeper pages cover a tool built for this.
  • Failure detector: heartbeats notice a dead machine.

When a machine dies

  1. Detect it (missed heartbeats) and mark it down in the metadata service. If it was the leader, elect another.
  2. Pick a spare machine and copy the shard’s data from a surviving replica.
  3. When the copy has caught up, add it to the shard. The replication level is restored.

When you add a shard

  1. Insert the new shard’s points into the ring. Only the arcs it takes over need to move.
  2. Copy those key ranges to the new shard while the old shards keep serving.
  3. Catch up recent writes (forward them, or replay a log), then flip the shard map to the new version.
  4. Delete the old copies. During the flip, check the new shard first and fall back to the old.
Trade-off
  • The metadata service is a dependency; if it goes down you cannot change the map, so it must be replicated itself.
  • Copying data uses network and disk, so throttle it or you hurt live traffic.
  • Three copies cost ≈ 3× the storage but survive a machine loss; more copies cost more.
+ added: still to decide

How do reads see fresh data (leader only, or copies too)? What happens if two machines both think they are leader? How big should a shard be so that moving one is quick? The next chapter on consistency and replication helps with the first two.

Orchestrating shards (1): who gets the new machine?

From: NoSQL Contd. (Database Orchestration and Shard Creation) + added: caveats

This is the lecture’s answer to the manual-sharding problem. Goal: a system that supports adding and removing machines, spreads load and storage evenly, and keeps a configured replication level. You give it the sharding key and the replication level as config.

Bad starts

Key = first letter of the username
  • Uneven storage and load (more names start with “a” than “x”) and under-used resources.
  • A hard ceiling of 26 shards, and if “a” grows huge there is no way to shard it further.
  • Any estimate of how many names start with each letter may be wrong.
“Add a machine when load passes a threshold”

It sounds sensible, but the threshold will probably be crossed at peak traffic, exactly when moving data away adds more load. Resharding should be planned, not triggered by pain.

Recap: consistent hashing

Several hash functions put each shard (S1, S2, S3) at several places on the ring; the user id hashes to a point and belongs to the first shard clockwise. Adding S4 puts its points on the ring so it takes a slice from each of S1, S2 and S3, evening out the load. (In code it is a sorted array, not a literal circle.)

SulochanaDB: the example system

  • Starts empty with three shards S1, S2, S3. Each shard is one master and two slaves.
  • DB clients run consistent-hashing code to route a key to its shard.
  • Reads can go to any of the three machines. How writes behave depends on whether you want a highly available or highly consistent system (the earlier master–slave page).

Open questions: how to add or remove machines, and what happens when one dies? Two new machines Mx and My arrive. Options: add them to an existing shard, keep them on standby, or create a new shard.

Manmeet’s algorithm (priority order)

  1. Restore the replication level (replace crashed machines first). Under-replication risks losing data or availability, so it comes first.
  2. Create a new shard.
  3. Otherwise keep the machines on standby.

With N new machines and shards of M machines: the leftover N % M go to replace crashed machines; the rest, a multiple of M, form new shards.

The fix the class made: suppose N = 3, M = 3 and one machine in S1 has died. N % M = 0, so nobody is available to replace it! So always keep a threshold of X standby machines (X can depend on the number of shards), and make new shards only from the machines above that reserve (N − X).

Standby machines need not sit idle: they can join existing shards as extra slaves. If a slave dies in such a shard, you do nothing, because the backup is already there.

Something must carry out these rules. It is the orchestrator, which goes by different names: NameNode (Hadoop), JobTracker, HBase Master.

⚠ older pattern

JobTracker belongs to the first Hadoop generation (Hadoop 2 replaced it with YARN’s ResourceManager). Also, the class says the N % M rule is a heuristic; it is a teaching algorithm, not a standard.

Other points from the class discussion

  • One machine must not belong to more than one shard; that defeats consistent hashing and makes things complex.
  • Rack-aware means slaves come from different racks; data-center-aware means different data centers.
  • Heartbeats are very cheap, so do not try to save on them. The class said Unix has 65,536 sockets by default and uses one.
  • CAP applies whenever data is on two machines that must talk.
⚠ small correction

65,536 is the number of TCP port numbers (2¹⁶), not a general socket limit. The conclusion (heartbeats cost almost nothing) still holds.

Trade-off

Standby machines cost money while idle but make recovery instant; with too few, a failure leaves a shard under-replicated until hardware arrives.

Orchestrating shards (2): creating a shard without downtime

From: NoSQL Contd. (Database Orchestration and Shard Creation) + added: example numbers

The big problem when adding a shard is the cold start: it begins empty. Migration is done in two phases.

Staging phase

  • Nobody above (the DB clients) knows the new shard exists. It is not on the hash ring, so the system behaves as if it did not exist.
  • Run a simulation to find which user ids will go to the new shard once it joins, meaning the hash ranges it will own and the shards currently holding them.
  • Start copying those ranges. Say staging starts at T1 = 10:00:00 PM and the copy finishes at T2 = 10:15:00 PM, so the shard is “warmed up”.
  • Catch: writes between T1 and T2 may be missing. If Manmeet saved two bookmarks at 10:01 PM they went to the old shard S1, and nothing guarantees they reached the new one.

Real phase

  • At T2 the new shard goes live on the ring, with slightly incomplete data.
  • It quickly catches up with the entries written between T1 and T2. This takes seconds; say it ends at T3 = 10:15:15 PM.
  • If Manmeet reads her bookmarks between T2 and T3 there is a choice: be highly available and return what the new shard has (possibly stale), or be highly consistent and be unavailable for about 15 seconds. Either is a tiny window compared with a 15-minute outage.
  • After T3 the new shard tells the old ones to delete the ranges it now serves, removing duplicates.
WhenWhat happensWho serves the range
Before T1New shard unknownOld shards
T1 to T2Copy ranges (staging)Old shards (new writes land here)
T2 to T3New shard live; deltas catching upNew shard (possibly stale) or briefly unavailable
After T3Old shards delete the moved rangesNew shard

The existing reserve machines are better tied to the shard they came from, so reserve machines already in place can seed the new shard, and the freshly arrived machines take over the reserve spots.

+ added: how the catch-up usually works

The “delta” is typically replayed from a write log of the old shard (the same idea as the WAL on the LSM page), applied in order until the new shard is within a few seconds of live.

How many reserve machines?

Reserved machines = X × number of shards, where X depends on the largest number of machines likely to be dead at the same time. That depends on machine quality and age. You can estimate it from the probability that several fail together and the expected number dead.

+ added: an illustration (made-up numbers)

If each machine has a ≈ 1% chance of being down at a given moment and you run 300 machines, the expected number down is ≈ 300 × 0.01 = ≈ 3 at any time (expected value is n × p). So a reserve for several simultaneous failures makes sense. Use your own failure data, not my 1%.

The other approach, used by DynamoDB and Cassandra, needs no reserve at all: multi-master, next page.

Trade-off

The two-phase migration is more machinery than “just move the data”, but it keeps the system serving throughout and hides the move from clients.

Multi-master and tunable consistency

From: NoSQL Contd. (Database Orchestration and Shard Creation) + added: calculator, caveats

In a multi-master system every machine is a master. There are no slaves and no reserves: each machine joins the hash ring as soon as it is live.

Where do the copies go?

With replication level 3, a user U1 lands at a point on the ring. The three copies go to the next three distinct machines clockwise: say M1, M2, M3. Why that choice? If M1 dies, U1’s requests would go to M2 anyway, so M2 should already hold a copy; and if both M1 and M2 die, M3 still has one. Note that M2 holds copies of only the users whose range it backs up, not a full copy of M1.

Tunable consistency: R and W

  • X = replication level (copies).
  • W = how many copies must acknowledge a write before it counts as successful. R = how many copies must answer a read. Both are at most X.
  • R = 1, W = 3 (X = 3): highly consistent. A write succeeds only when all copies have it; but if one machine is slow or down, writes start failing.
  • R = 1, W = 1: highly available. Any one copy answers, any one copy accepts the write; the others catch up using the gossip protocol. A read may hit a stale copy.
  • Higher R + W means more consistency. If R + W > X every read overlaps with the latest write, which is a highly consistent setup. Changing just R and W makes it consistent or available, hence “tunable”.

Example: a shopping cart (DynamoDB’s classic use)

The cart should be as available as possible, but not often inconsistent. With X = 5, choose R = 2, W = 2, so writes go to two machines. If two replies disagree, merge them by their timestamps:

Reply 1Reply 2Merged cart
Lux Soap 10:00 PM; Oil 10:15 PMLux Soap 10:00 PM; Mask 10:20 PMLux Soap, Oil, Mask
⚠ read carefully
  • With X = 5, R = 2, W = 2 we get R + W = 4, which is not greater than 5. So a read can miss the latest write. The cart accepts that because it merges later; do not call this “strongly consistent”.
  • Merging carts by simple union can bring back an item the customer deleted. The original Dynamo paper describes this effect. Real designs use extra metadata (version vectors) to detect conflicts.
  • As far as I know, the DynamoDB service today does not expose R and W; it offers eventually consistent or strongly consistent reads. Cassandra does expose them (consistency levels such as ONE, QUORUM, ALL). The R and W idea comes from the Dynamo design, so check your database’s own documentation.
Trade-off

Multi-master removes the single write bottleneck and the reserve machines, but you inherit conflict handling and the consistency choice yourself.

CAP theorem, told as a story

From: System Design - CAP Theorem, PACELC Theorem and Master-Slave

Rohit starts a company called “reminder”. People phone 123456 and ask him to note a reminder; when they call back he reads it out. He writes entries in a diary. Business booms, and he can only take one call at a time, so he hires Raj. The same phone number now rings at either of them, and each has their own diary.

Problem 1: inconsistency

Person X calls once and reaches Raj, who writes “X: 3 PM flight”. Later X calls back, reaches Rohit, who has no entry and says “you have no flight”. X misses the flight. The two diaries are out of sync: different data on two machines.

Fix: on every write, both write the entry, then return success. Now both diaries agree.

Problem 2: availability

One day Raj is out. A request comes in, but by the rule above success can only be returned after both have written. So how can Rohit return success?

Fix: accept the entry anyway; the next day Raj catches up on every entry before he starts taking calls again.

Problem 3: a network partition

Rohit and Raj have a fight and stop talking. X calls Raj to add a reminder, and Raj cannot ask Rohit to write it too.

  • If Raj writes the entry and returns success, the machines are inconsistent (X calls back, reaches Rohit, no entry).
  • If Raj refuses and returns failure to stay consistent, that is an availability problem: until they talk again, every new reminder fails.

Two machines holding the same information plus a partition between them means you must choose between consistency and availability. That is the CAP theorem.

The three words

WordPlain meaningStory
ConsistencyEvery read sees the latest writeBoth diaries match
AvailabilityEvery request to a working machine gets an answer (not an error)Rohit takes the call even when Raj is away
Partition toleranceThe system keeps working when the network between machines breaksThe fight
⚠ older pattern (a misleading summary)

Your PDF says a system can provide “only two of the three”. That is a handy slogan but misleading: partitions will happen whether you like it or not, so you do not really choose to drop P. The real choice is what to do when a partition happens: keep consistent (refuse some requests) or stay available (risk stale or conflicting data). Your own Problem 3 above shows exactly that. I read the article your PDF links (Martin Kleppmann) and it makes the same point, adding that CAP uses very narrow definitions (its “consistency” means linearizability, its “availability” means every working node answers) and that many real systems fit neither “CP” nor “AP” neatly.

+ added

Do not mix up the C of CAP (“all copies agree on the latest value”) with the C of ACID (“the data follows its rules”). They share a letter, not a meaning.

PACELC: the rest of the story

From: System Design - CAP Theorem, PACELC Theorem and Master-Slave + added: consistency models

CAP only talks about what happens during a partition. PACELC adds the normal days:

If there is a Partition (P)

choose Availability or Consistency.

Else (E), no partition

choose Latency or Consistency.

Latency is the time to process a request and return a response. Even with a healthy network, making every copy agree takes coordination, which takes time. So you must pick between very low latency and high consistency; they compete.

Examples from your notes

  • Banking: consistency matters, so ideally immediate consistency. In reality ATM transactions (and many banking systems) use eventual consistency.
  • Facebook news feed: availability matters more than consistency.
  • Quora: availability matters more.
  • Facebook Messenger: consistency matters even more than availability, because a miscommunication can disturb human relations.
+ added: consistency models, weakest to strongest
  • Eventual: if writes stop, all copies will end up equal, but a read right now might be stale.
  • Read-your-writes: you always see your own updates (you post, you see your post), even if others lag.
  • Causal: if one update caused another (a reply to a comment), everyone sees them in that order.
  • Strong (linearizable): every read sees the latest completed write, as if there were one copy. The most expensive in latency and availability.

Different parts of one system can use different levels: the feed can be eventual while payments are strong.

+ added: PACELC labels, with a warning

People write systems as “PA/EL” (favoring availability, then latency) or “PC/EC”. Treat such labels as rough descriptions only; many databases behave differently depending on their settings, which is the same complaint the Kleppmann article makes about CP/AP.

The Kleppmann article, Google’s Spanner paper (“does Spanner violate CAP?”) and two videos are linked on the last page. Spanner reaches strong consistency across the world, at the cost of coordination, so it is a good thing to read about once the basics settle.

Master–slave (leader–follower) replication

From: System Design - CAP Theorem, PACELC Theorem and Master-Slave + added: modern names, lag

In a master–slave system exactly one machine is the master; the rest are slaves. Rules from your notes:

  • All writes go to the master first.
  • Reads can go to any machine.
  • When the master dies, a new master is chosen by an election algorithm.
+ added: today’s names

Most current documentation says primary / replica or leader / follower instead of master / slave. Same idea. The heading “Master Slave Theorem” in the PDF is a slip: it is a design pattern, not a theorem.

Three flavors, by when you say “success”

1. Highly available, not guaranteed to sync

Masterhas itSlave 1maybeSlave 2maybe

The master writes and returns success right away; it tries to sync the slaves later. Example: Splunk log ingestion. Throughput is huge, and missing a few log lines is fine.

2. Highly available and eventually consistent

Masterhas itSlave 1has itSlave 2soon

The master writes, and once one slave has written too, success is returned. The rest sync afterwards. Example: storing posts for a news feed. Posts must not be lost but may show up late.

3. Highly consistent

Masterhas itSlave 1has itSlave 2has it

The master and all slaves write; only then is success returned. Example: banking.

+ added: the usual words
  • Flavor 3 is synchronous replication; flavor 1 is asynchronous; flavor 2 is like semi-synchronous (wait for one copy).
  • Strictly, flavor 1 is not even “eventually consistent”: if the master dies before syncing, the write is simply lost.
  • Replication lag: right after a write you read from a slave that has not caught up and see old data. A common fix: read your own recent writes from the master.
  • Quorum systems (write to W of N copies, read from R, with W + R > N) are another way to trade consistency for speed.
  • Electing a leader safely is hard (two machines may both believe they lead, the “split brain”). Tools such as Zookeeper and algorithms such as Raft exist for it; the Zookeeper pages show how Zookeeper does it.

Drawbacks

  1. One master is a bottleneck when writes are very heavy.
  2. In a highly consistent system, more slaves means more failure risk and more latency, since every one must acknowledge. With ≈ 1,000 slaves the design stops working; you must shard more.

Zookeeper (1): tracking who is the master

From: System Design: Zookeeper + Kafka + added: caveats

The problem: tracking state

In master–slave, every write must reach the master, so every app server must know who the master is. When the master dies, a new one is chosen and everyone must learn it consistently.

Naive idea: a dedicated machine whose only job is to know the master. Two issues:

  1. It is a single point of failure: if it is down, no writes can happen even though the master is healthy.
  2. Every request pays an extra hop to find the master.

Use a cluster instead of one machine, and new questions appear. How do the machines agree on who the master is? How do they all hold the same information? How do app servers avoid the extra hop?

Zookeeper

Zookeeper is a general system that keeps small pieces of data in strongly consistent form. Its storage looks like a file system: a tree of files and directories. Each file is a ZK node (a “znode”; do not confuse it with a machine).

/
└── clusterx
    ├── master_ip     ephemeral:  "10.0.0.2"
    └── max_conns     persistent: "500"

Master election in one line

Every machine in cluster X tries to write its own IP into the same ephemeral node, /clusterx/master_ip. Only one write succeeds. Say M2 wins. While M2 stays alive and heartbeats, anyone who reads the node gets M2’s address.

Watches: no more asking again and again

The master changes rarely, maybe once a day. Making every app server ask Zookeeper on every request is wasteful. So reverse it: a client reads the value and sets a watch, meaning “tell me when this changes”. Zookeeper keeps a list of subscribers per node and notifies them on a change or deletion. Clients keep the value locally and the extra hop disappears.

⚠ nuance

In real Zookeeper a watch fires once; after being notified, the client has to read again and set a new watch. The lecture’s “keep subscribing” picture hides that detail (the next page does re-read after a master change).

+ added
  • Zookeeper also offers sequential nodes (the server appends an increasing number), the basis for locks and queues.
  • Alternatives with similar jobs: etcd and Consul (both built on majority agreement protocols).
  • Use it for small coordination data like “who is master”, not for bulk storage.

Zookeeper (2): the cluster, majority and failover

From: System Design: Zookeeper + Kafka + added: fault tolerance, stale reads

So far Zookeeper was one machine, which is itself a single point of failure. In reality it is an odd number of machines that elect a leader among themselves, at setup and whenever the leader dies.

How a write works

  1. The write goes to the leader (say Z3), for example “set /master_ip to ip-x”.
  2. The leader broadcasts it to the others.
  3. If a majority (the leader included) acknowledge, the write succeeds. Otherwise it is rolled back.

In a cluster of 5, 3 must acknowledge; in 7, 4. The total stays at 5 even if one machine is dead, so you still need 3.

If ten machines try to become master at the same instant, all ten requests reach the leader. It takes a lock so one goes first; that write is kept only if a majority acknowledge. Then the lock is released for the next request, which now finds the node taken and fails.

Why a majority and not half?

Suppose success needed only half of 5 machines. A network partition separates z1, z2 from z3, z4, z5. Write 1 (master = ip1) succeeds on z1 and z2; write 2 (master = ip2) succeeds on z4 and z5. Now half the machines say ip1 and half say ip2: split brain. A majority rule makes this impossible, because any two majorities share at least one machine, which will reject the second write.

That is why the number is odd: an even size adds a machine without adding tolerance. Without a reachable majority, writes stop (the “consistency over availability” side of CAP).

When the master dies

  1. The master stops sending heartbeats, so the ephemeral node /clusterx/master_ip is deleted.
  2. Every watcher is notified.
  3. The slaves race to write their IP; the first to succeed is the new master.
  4. App servers delete their local copy of the master address. On the next write request they read Zookeeper again (and set a new watch). If the value is null, the request fails: no master has been chosen yet.
  5. The old master, when it returns, reads the node, finds the new master, and becomes a slave. (If it returns fast enough to find the node empty, it competes with the other slaves.)
+ added: two things the lecture leaves out
  • Stale reads: by default a client reads from whichever Zookeeper machine it is connected to, which can lag behind the leader. The Kleppmann article from the CAP page explains this; a sync before a read makes it up to date, at some cost.
  • The zombie master: a master that was paused (for example by a long garbage-collection stop) may wake up still believing it is master. Systems guard against it with fencing tokens: each new master gets a higher number, and storage rejects writes that carry an older number.
Trade-off

Majority agreement buys one trustworthy answer to “who is master?”, at the price of slower writes and no writes at all without a majority. That is acceptable for tiny, rarely changing data.

Kafka (1): doing work asynchronously

From: System Design: Zookeeper + Kafka (and Microservices 2 recap) + added: caveats

The problem: async tasks

In Messenger, Abhi sends Raj a message and it is written to Raj’s database. After that we also want to: (1) notify Raj, (2) email Raj if he has not read messages for 24 hours, (3) update analytics. The sender should not wait for any of that, and if one of those fails the message itself has not failed. How do we reply “success” immediately and still do the rest reliably?

A persistent queue and pub/sub

A persistent queue is written to disk so events are not lost. It works as publish/subscribe:

  • Publish: when something of interest happens (a message sent, an item bought on Flipkart), publish an event to the queue.
  • Subscribe: each interested system consumes the events it cares about: the notification, email and analytics systems for “message sent”; the invoice system for “item bought”.

Topics

One queue holding unrelated events would feed subscribers garbage (the invoice system would see vendor messages). So events are grouped into topics, and each system subscribes only to the topics it needs.

Kafka is a very high-throughput system that implements a persistent queue with topics. Persistent queues help when producers and consumers work at different speeds, there are several consumers each at their own pace, and the producer must not be blocked.

Kafka vocabulary

ProducerA system that publishes events to a topic (there can be many)

BrokerAny machine in the Kafka cluster; a fancy word for a machine storing events
PartitionA topic is split into partitions, so Kafka can spread the load and consumers can read in parallel
Retention periodHow long events are kept; older ones are periodically cleaned up. A queue holds events for a while, not forever
+ added: Kafka is really a log

Unlike a classic queue, Kafka does not delete an event when it is read. It appends events to a log and each consumer tracks its own position (its offset, next page). That is why several independent consumers can read the same topic, and why a consumer can re-read old events within the retention period (by default ≈ 7 days; it is configurable).

⚠ older pattern

Kafka used to depend on Zookeeper to store its own cluster metadata. Recent Kafka versions replace Zookeeper with a built-in agreement mechanism (KRaft), and newer major versions no longer support Zookeeper mode. Check your version’s documentation.

Trade-off

An event-driven design makes the sender fast and decouples teams, but adds a hop (so slower end to end), a system to run, and “eventually” behaviour.

Kafka (2): partitions, keys, consumer groups and offsets

From: System Design: Zookeeper + Kafka and Microservices 2 + added: delivery guarantees

A topic too big for one machine

Configure a number of partitions for the topic. A single partition cannot be split across machines, but different partitions can live on different machines (brokers), so Kafka spreads them.

But ordering?

With several partitions, how do you know which partition holds the next newest message? Tracking global order costs throughput, and you often do not need it. For Flipkart’s customer-to-vendor messages, order across different users does not matter; order within one user’s messages does.

So a producer can attach a key. Kafka computes hash(key) % number_of_partitions, so equal keys always land in the same partition, and ordering is kept inside a partition. Use sender_id as the key and each sender’s messages stay in order. (It is the sharding key idea again.)

+ added: the % N trap returns

If you later change the number of partitions, hash(key) % n changes for most keys, so existing keys can move to another partition and ordering guarantees for them break across the change. Pick the partition count with growth in mind (the sharding page showed the same problem).

A topic too big for one consumer

Use a consumer group: several consumer machines that share one topic. Each consumer is assigned one or more partitions exclusively, so it only gets events from those. Therefore it is useless to have more consumers than partitions. Events are processed in parallel across the group.

Never losing events

Replicate. You configure a replication count; for each partition one replica is primary and the others are copies spread over brokers. Example from the lecture: 3 brokers, 2 topics, 2 partitions each, replication 2.

Which machine do I talk to?

Any broker. It redirects you to the right one.

Reading only new events: offsets

A consumer group tracks an offset per topic and partition: how far it has read. Next time it fetches only events after the offset. For retries, do not acknowledge until the event is processed; as long as there is no acknowledgement, the offset does not advance, so the event can be delivered again.

+ added: what that means for guarantees
  • Committing the offset after processing gives at-least-once delivery: a crash in between means a repeat. Committing before gives at-most-once: a crash means a lost event.
  • So consumers should be idempotent (the queues page), or use a unique id to ignore repeats.

Message queues and streams

+ added page Gap-fill: the Kafka pages before this one are the lecture’s version; this page adds the general vocabulary.

A message queue lets one part of the system hand work to another without waiting. The sender (producer) drops a message and moves on; a receiver (consumer) processes it when it can. Example: a code submission goes into a queue, and a pool of workers picks submissions up and judges them.

Why use one: it absorbs traffic bursts, lets the two sides scale and fail independently, and lets you retry failed work.

StyleHow it behavesGood for
QueueEach message goes to one consumer, then is removedSharing work among workers
Pub/subEach message goes to every subscriberFan-out: one event, many reactions
Log / streamAppend-only record; consumers remember their own position and can replayEvent history, many independent readers

Four ideas you must know

  • Delivery guarantees: at-most-once (may lose, never repeats), at-least-once (never loses, may repeat), and “exactly-once”, which in practice means at-least-once delivery plus processing that tolerates repeats. Be sceptical of the phrase.
  • Idempotency: processing a message twice gives the same result as once. Attach a unique id and remember which ones you have handled. Charging a card twice is the classic horror.
  • Ordering: usually guaranteed only within one partition. Messages with the same key (say a user id) go to the same partition, which is the sharding-key idea again.
  • Dead-letter queue: a side queue for messages that keep failing after N tries, so a “poison” message does not block everything.
Trade-off

A queue makes the system more robust and decoupled, but adds delay, one more thing to run, and “eventual” behaviour the user may see (“your submission is queued”).

Case study: search typeahead (2)

From: System Design - Case study 2 (Typeahead) + added: decay table

The hashmap approach (the practical one)

Tries cannot be saved in ordinary databases unless you write one yourself, but every key-value store works. Use two key-value stores:

  • Frequency: search term → how many times searched.
  • Top5Suggestions: every prefix → its top five terms.

Write: an updateFrequency(S) only changes the entries for the prefixes of S, and those updates can be asynchronous (a queue feeding the shards). Read: for the query “mich”, consistent hashing finds the shard holding the key “mich” and returns its top five. Note that “mic” and “mich” may land on different shards. Key-value databases shard by the key automatically.

Reads and writes compete: cut the writes

One frequency update triggers many prefix writes, and heavy writes hurt getSuggestions. Exact counts do not matter, only relative popularity does. Two ways to write less:

Threshold approach

  • Do not update the trie directly. Count in a separate buffer hashmap.
  • When a term’s buffered count reaches a threshold (say 50), add the threshold to the main store and reset the buffered count to zero. Terms searched fewer than 50 times a day (the long tail) never cause a write.
  • Buffer size: 10 billion searches × 40 bytes ≈ 400 GB at the very worst; in reality far less, since keys exist only for distinct terms. It fits on one machine, and you can flush it at the end of the day.

Sampling approach

Like an election exit poll: only the trend matters, so record every 100th occurrence of a term instead of all. That cuts writes ≈ 100×. It works well for high-frequency terms.

Trade-off

Sharding the trie

Shard by prefix. At the third level there are 26 × 26 × 26 = 17,576 possible subtrees (“aaa”, “aab”, …); with digits, 36³ = 46,656 ≈ 50,000. Problem: disproportionate load. “mic” and “the” are busy; “aaa” is idle. So group some prefixes on the same shard (for example “aaa” with “mic”) and map by consistent hashing on the first three characters. The query “mich” goes to the shard of the hash of “mic”.

Sharding the hashmap store is easy: any key-value database does it, with consistent hashing and the key as the sharding key.

Recency: time decay

“Shania Twain” may have been huge five years ago and quiet now; it should not stay on top. Subtracting a fixed number from every term each day is unfair: a term with frequency 2 would vanish, while one with 1,000 would hardly notice. Think in percentages instead: each day Freq = Freq / TDF (time decay factor), and Freq++ on each new search. With TDF = 2, today’s search weighs 1, yesterday’s ½, the day before ¼, and so on. A term nobody searches fades out by itself.

Case study: design Messenger (2)

From: System Design - Case study 3 (Messaging) + added: caveats

Problem 1: sharding

By userId (a mailbox per user)
  • getConversations, getMessages: one machine, easy.
  • sendMessage: 2 writes (sender’s and recipient’s machines) that must stay consistent. Hard.
By conversationId
  • getMessages and sendMessage: one machine, one write.
  • getConversations (“Sachin’s latest 10”): would have to ask every machine.

Fix for the second: a secondary database: user → list of conversations, sorted by recency, with a snippet and last-message time. Now getConversations reads only there, but a send costs 3 writes: the message, then re-ordering the conversation in both users’ lists.

Large groups (Slack, MS Teams, Telegram): sharding by user would make one message in a 1,000-member group cost ≈ 1,000 writes, so they shard by conversation and make the conversation-list ordering best-effort. For 1:1 chats userId looks better (2 writes versus 3), but conversationId is not terrible either. This lecture continues with userId.

Problem 2: consistency of sendMessage

Consistency here means: if user1 sends “Hi” and gets no error, user2 must receive it. In which order should the two writes happen?

Case 1: sender first

Fail → error. Success → write the recipient: success is fine; failure → roll back, return error. Dangerous: the sender may refresh and still see a message the recipient never got.

Case 2: recipient first

Fail → error. Success → the message has reached the recipient; now write the sender’s copy. If that fails, queue it and retry until it lands. Worst case: the sender briefly does not see their own message.

Case 2 is better: the system stays consistent, and the only flaw is a temporary gap for the sender.

+ added

Case 2 is the saga idea from the transactions and microservices pages: do the step that matters most, then retry the rest until it succeeds (“forward recovery”) instead of undoing. The gap is a “read-your-writes” violation on the consistency-models list.

Problem 3: the right database and cache

The system is read- and write-heavy, which pull against each other, so reduce it to one on the storage side. Writes cannot be absorbed (batching or sampling would lose immediacy), so the plan is to absorb reads with heavy caching. That cache must hold a lot (so it must be sharded), stay consistent with the DB (use write-through), and avoid race conditions between concurrent writes for the same user.

Idea: use the app servers as the cache. Assign users to app servers with consistent hashing. Because one server owns a user, it can take a write lock per user, so writes for that user happen one at a time. Since not all users fit, evict with LRU by user.

Pros
  • Scales horizontally: add servers, cache more.
  • Race conditions and consistency handled cleanly.
Cons
  • If a server dies, its users are unavailable for a few seconds until reassigned.
  • Cold start: after a restart the first requests are slower, as data must be read from the DB.

Database: with most reads absorbed, you need a store that is good at heavy writes. The lecture picks HBase: a column-family design that suits a mailbox and is tuned for write volume (the LSM idea earlier).

⚠ older pattern

HBase is a valid but older pick. Other wide-column or LSM-based stores (Cassandra, ScyllaDB, DynamoDB) fit the same role. Choose by your team’s experience and the consistency you need.

Trade-off

The “app server as cache” design buys simple per-user locking at the price of a few seconds of unavailability whenever a server fails.

Case study: full-text search (1)

From: HLD Case Study 4 Elastic Search + added: worked example

You work at LinkedIn and must let people search all matching posts. Why not SQL?

A B+ tree index works for short values (a word or two). For long text, a query such as SELECT * FROM posts WHERE content LIKE '%job post%' cannot use the index; it goes through every row and does a string search in every post: a full table scan. Your notes give it as O(N·M²) for N rows of M characters; whatever the exact bound, it is far too slow and “will bring LinkedIn down”. NoSQL has the same issue: key-value, column-family and document stores all need to go through every row or value.

The right structure: an inverted index

A hashmap or trie where the key is a word and the value is the list of documents that contain it. (Your notes call it the “inverse index”; the usual name is inverted index.) Apache Lucene does this. Each entry (an entire post) is a document. Four steps:

  1. Character (word) elimination: drop words like “a”, “an”, “the”.
  2. Tokenization: break the post into words.
  3. Token index / stemming: reduce words to a root. “ran” and “running” become “run”; “crashed” and “crashes” become “crash”.
  4. Reverse indexing: for each word store (document id, position) pairs. If document 5 reduces to decent(1) product(2) wrote(3) money(4), then decent → [(5,1)].

Case study: Elasticsearch’s sharding and flows (2)

From: HLD Case Study 4 Elastic Search + added: trade-offs

Sharding

  • Elasticsearch shards by document id. A document is never split; it belongs to exactly one shard.
  • You choose the number of shards at setup. If that number rarely changes, something simpler than consistent hashing works: a document goes to shard hash(document_id) % number_of_shards.

Replication

You also set the number of replicas at setup. Why: machines die (replicas keep the shard alive and the data safe), and reads can go to any replica, which shares the read load. As in master–slave, one copy in each shard group is the primary and the others are followers.

Example from your notes: 3 nodes, 2 shards (0 and 1), with every shard on all three nodes: three copies of each.

With few nodes, several shards share a node; adding nodes lets you spread them out and control how many shards sit on each node (the Sematext link on the last page).

⚠ source wording

The notes say “num_replicas = 3” for the picture above, which shows three copies in total (one primary and two replicas). In Elasticsearch’s own settings the replica count is the number of copies in addition to the primary, so that picture is a replica setting of 2.

Write (index a document)

Find the shard from the document id, then the node holding that shard’s primary. The request goes there and is indexed like a Lucene write. The notes say updates reach the followers asynchronously.

⚠ older pattern (check this one)

As far as I know, Elasticsearch’s documentation describes the primary forwarding the write to the in-sync replicas and acknowledging only after they have applied it, so replication is effectively synchronous within the in-sync set. I did not re-check the current docs, so treat the notes’ “async” with care.

Read (a phrase, find matching documents and positions)

Any document in any shard might match, so a read must go to every shard. The node that receives the request becomes the coordinating node:

  1. Resolve the request to the relevant shards.
  2. Pick an active copy of each shard (primary or replica).
  3. Send shard-level read requests to those copies.
  4. Combine the results and answer.

If a shard copy does not respond, the coordinating node tries another copy in the same group. Repeated failures can leave no copy available. For fast answers, some APIs return partial results when a shard fails.

+ added
  • This read pattern is scatter–gather: cost grows with the number of shards touched.
  • Newly indexed documents are not searchable instantly; they appear after a short “refresh” (about a second by default). Search is “near real time”, consistent with choosing availability.
  • The number of primary shards is hard to change later (you split, shrink or re-index), so plan for growth when you set it. That is the % N problem from the sharding page.

Storing very large files (HDFS)

A Facebook post’s image is not stored in the database; only metadata is (user_id, post_id, timestamp…), plus a URL that points to the media in a separate storage system. This lecture asks how that storage holds very large files: a 50 TB video or an ever-growing log file.

Requirements: store huge files, be reliable and durable (never lose them), allow downloads, and allow analytics.

Idea: cut the file into chunks on many machines

What chunk size? Chunks of 1 MB would give 50 TB ÷ 1 MB = 50 × 10⁶ MB ÷ 1 MB = 5 × 10⁷ parts (≈ 50 million). Too many small parts causes two problems:

  1. Collation: joining a huge number of pieces to answer a download is overhead.
  2. Metadata cost: you must record, for each chunk, which machine holds it.

HDFS: the Hadoop Distributed File System

  • Default chunk size 128 MB in HDFS 2.0 (64 MB in HDFS 1.0). At 128 MB, 50 TB is ≈ 390,000 chunks, about 128× fewer than with 1 MB chunks.
  • The NameNode is the metadata table: for each file, which chunk is on which data node (“File 1, chunk 1 is on machine 3”). There is only one NameNode server, and it is replicated.
  • Why 128 MB? Designers benchmark the common operations (store, download, analyse) on typical file sizes with different chunk sizes and pick the size that performs best.
  • Reliability: never keep a chunk on one machine; replicate it on other data nodes. The rack-aware rule: do not put copies on the same rack, because one power failure takes the whole rack down.

Upload

  1. The client sends a stream of data to an app server, which runs an HDFS client.
  2. The app server asks the NameNode for the chunk size (say 128 MB).
  3. When it has collected 128 MB (or reaches end of file) it records the chunk’s metadata at the NameNode and sends the chunk to a data node. “File F1, chunk n, is on D3.”
  4. Repeat for the next chunk. A 200 MB file becomes 128 MB + 72 MB. Each chunk is also replicated (master–slave style) to other nodes.

Latency is not great, since there is a single stream of data.

Download

The app server asks the NameNode for the file’s chunks and their data nodes, fetches them, and streams each chunk to the client as soon as it arrives (streaming returns in the Hotstar case study, which is not in your files).

The torrent analogy

A 1,000 MB movie in 100 parts of 10 MB. If 100 people have it, you can download all parts in parallel from different people; whoever finishes first gets asked for the next part you have not asked anyone for, and for slow parts you can ask a second source. Cutting into chunks makes parallelism possible.

⚠ older pattern (simplifications)
  • HDFS replicates each chunk with a default replication factor of 3, writing through a pipeline of data nodes, rather than a classic master–slave split. Also, the data usually streams from the client through the pipeline, not buffered 128 MB at a time at an app server.
  • One NameNode is a single point of failure, so modern HDFS runs an active and a standby NameNode.
  • The lecture title says “S3”, but the notes describe only HDFS. S3 is Amazon’s object store; it also splits large uploads into parts (“multipart upload”), but its internals are not in your notes.
Trade-off

Big chunks: little metadata, fast streaming, but a small file wastes a chunk’s bookkeeping and parallelism is coarse. Small chunks: fine parallelism, but a huge metadata table and slow reassembly.

Nearest neighbors (1): from brute force to grids

From: System Design - S3 + Quad trees (nearest neighbors) + added: geohash, distance

Many systems depend on location, and ordinary database designs struggle with them. Problem: on a map app, find the nearest X places (say ten restaurants) around you.

1. Brute force

Fetch every place with its latitude and longitude, compute the distance to each from your position with the 2D formula d = √[(x₂ − x₁)² + (y₂ − y₁)²], and sort. Across the whole world it takes a very long time.

2. A square around you

You cannot mark a circle in a database, so use a square of half-width k:

SELECT * FROM places
WHERE lat < x + k AND lat > x - k
  AND long < y + k AND long > y - k

Problems: finding a good k is hard, and the query is slow, since only one of the lat or long indexes can be used, so it still scans a lot of points.

3. A grid

Divide the world into small cells (say 1 km² each). Then you only look in your cell and the adjacent ones:

SELECT * FROM places WHERE grid_id IN (grid1, grid2, grid3, ...)

How big should a cell be? Not the same everywhere: tiny in dense areas, huge over the ocean. The rule of thumb is to size a cell by the number of points inside, about 100 points per cell. Places also keep being added, so the cells must adapt. That is what a quadtree does (next page).

⚠ older pattern (a simplification)

Straight-line distance on latitude and longitude is a fine approximation for a city, but not for long distances: the Earth is a sphere (use the great-circle “haversine” formula), a degree of longitude gets shorter toward the poles, and longitude wraps around at ±180°. Real systems often use a database’s spatial index instead of hand-made SQL.

+ added: geohash, the other popular answer

A geohash turns a (lat, long) point into a short string where places that share a longer prefix are close together. You then search by prefix. Your notes list geohash and a geohash vs quadtree vs R-tree comparison among the references. Edge case: two close points on opposite sides of a cell boundary have different prefixes, so you also search the neighbouring cells.

Nearest neighbors (2): the quadtree

From: System Design - S3 + Quad trees (nearest neighbors) + added: clean pseudocode

Creation

Treat the whole world as the root holding all places. If a node has more than 100 points, split its rectangle into four equal children; repeat for every child that still has more than 100. Leaves end up with at most 100 points, and the tree’s height is about log N for N places (more precisely, log base 4 of N ÷ 100).

Which grid am I in?

Take the node’s corners. Compute the middle point (Xmid, Ymid), compare x and y with it to pick one of four children, and repeat until you reach a leaf. Time = the tree height ≈ O(log N).

# children: 0 = top-left, 1 = top-right, 2 = bottom-left, 3 = bottom-right
findgrid(x, y, node):
    if node.is_leaf(): return node.grid_id
    xmid = (node.x1 + node.x2) / 2
    ymid = (node.y1 + node.y2) / 2
    right = x > xmid
    top   = y > ymid
    return findgrid(x, y, node.children[(0 if top else 2) + (1 if right else 0)])
⚠ source typo

The PDF’s pseudocode ends with Else y > (Y1 + Y2) / 2: where a plain else is needed, and its child numbering does not match the text’s quadrant description. The version above fixes both; any consistent numbering works.

Each place in the world carries its grid number in a MySQL table, so the neighbours query is simply WHERE grid_id IN (...). If the grid has too few places, include the neighbouring grids:

  • Next pointers: link leaves to their siblings while building the tree and walk left or right.
  • Probe points: take a point just beyond the boundary in all 8 directions (for example x + 0.1) and run a log N search for each.

Add and delete a place

  • Add (x, y): find its leaf. If it stays under the threshold (100), add it. Otherwise split the leaf into four and redistribute its points, updating the grid id of about 100 places in the database.
  • Delete is the reverse: if the four children together fall below the threshold, merge them into the parent. Deletions are less common.

Does it fit in memory? (the lecture’s estimate)

For 100 million places: if every leaf averaged 20 places there would be ≈ 100 M ÷ 20 = 5 M leaves, and with all the levels above ≈ 5 M × (1 + ¼ + 1⁄16 + …) = 5 M × 4⁄3 ≈ 6.7 M nodes (the notes say ≈ 6.5 million; the same ballpark, from 1.33 × 10⁸ ÷ 20).

ItemSize (approx., the lecture’s assumptions)
One node: boundary ≈ 64 B + 4 child pointers ≈ 16 B≈ 80 B
All nodes: 6.5 M × 80 B≈ 520 MB
All places: 100 M × 32 B≈ 3.2 GB
Total≈ 3.7 GB, about 4 GB: fits in one machine’s memory

Production machines often have 64 GB of RAM, so 4 GB is fine; keep copies on several machines so a failure does not lose access.

⚠ small correction

The notes use 16 bytes per coordinate. Ordinary double-precision numbers take 8 bytes, so a boundary is more like 32 bytes. That only makes the tree smaller; the conclusion (it fits in memory) stands.

Trade-off

Splitting at exactly 100 keeps cells uniform but causes many splits and merges; the Uber page softens this with ranges and periodic rebalancing.

Case study: design Uber

From: System Design - Case Study 5 (Design Uber) + added: caveats

Prerequisite: the quadtree pages. The earlier nearest-neighbor problem had fixed places; here cabs move. We build intracity Uber. Users book a cab; a cab is available or unavailable and only available cabs count. Use case: a rider at (lat, long) is matched with the nearest available cabs; nearby cabs are notified in round-robin order and each driver can accept or reject.

Sharding key: the city

Suppose there are ≈ 10 million cabs worldwide (an assumption) and you stand in Mumbai: you do not care about the rest. Shard by city, which may span more than one region. Every city is an independent hub, and the problem shrinks to a few hundred thousand cabs at most; even the busiest Indian cities have around 50,000 (the lecture’s estimate).

Why equal grids fail inside a city

Some areas are dense and some sparse. In a busy area you do not want a cab 5 km away, but in a sparse area that is fine. So the right grid size depends on location and time; a quadtree built on cab density adapts.

Moving cabs

  • Each cab pings its location (say every 60 seconds), keeping a map cab_id → (x, y).
  • Brute force inside one city (a few thousand cabs) works.
  • Better: do not touch the quadtree on every move. Cabs only send an update if the location changed in the last minute (checked on the phone). The driver app also knows its current grid and boundary. If the cab stays inside, nothing changes in the tree. Only when it crosses into another grid does the backend update cab → grid (kept in Redis).
  • Inside test for a grid with corners (a, b) and (c, d): a ≤ x ≤ c and d ≤ y ≤ b.

Don’t rebuild grids instantly

Splitting a grid the moment it passes 50 cabs, and merging when it falls below, would cause many writes as cabs move in and out. Two softer rules:

  • Use a range (say 50 to 75 cabs) rather than a single threshold, and change dimensions only when a grid leaves the range.
  • Run a periodic job (every ≥ 3 hours) to split or merge leaves. It works because traffic patterns change slowly.

Summary

  1. For a city, build a quadtree from current cab locations (dynamic grids by density).
  2. Keep cab → last known location and the quadtree for nearest-cab queries.
  3. Do not flood the tree: send location only when changed, update the tree only when the grid changes, and rebalance grid sizes periodically.
⚠ older pattern

A 60-second update interval is a teaching number; real ride apps refresh cab positions much more often, though I have not checked Uber’s actual figures. Slower updates mean riders may be matched to a cab that is no longer where the map shows it.

+ added
  • Two riders can pick the same cab at once; reserve the cab with a short lock owned by one machine, the same “one owner per contested resource” idea as IRCTC.
  • Uber itself built and open-sourced a hexagonal grid system called H3 as an alternative to quadtrees and geohashes.
Trade-off

Fresher locations improve matching but multiply write traffic; the grid-boundary trick trades a little staleness for far fewer writes.

Check yourself

A cab drives 200 metres inside one grid for 10 minutes. How many quadtree updates happen? (None. Only a grid change triggers one.)

Generate 8-byte numeric ids that are unique and incremental: if id i₁ is made at time t₁ and i₂ at t₂, then t₁ < t₂ should imply i₁ < i₂.

Trade-off

Snowflake needs no central coordination and makes ids fast, but depends on clocks and on someone assigning unique machine ids (Zookeeper is a natural helper, see its page).

Design a rate limiter (1)

From: System Design - Popular interview subtopics + added: where it lives

A rate limiter controls how much traffic a client may send to a server. It helps prevent attacks such as DDoS. Throttling means controlling how much customers use the APIs in a given period. A limiter can run on the client side or the server side; the server side is the one that protects you.

In the lecture’s picture it sits in the path client → load balancer → API gateway, and the gateway then forwards to services.

Example: a user at IP 10.20.30.40 may make at most 5 requests per 60 seconds. The sixth request in that minute is rejected with HTTP status 429; after the window moves on the user can send again. The data structure is a hashmap keyed by IP address.

The lecture lists four algorithms: token bucket, leaking bucket, fixed window counter and sliding window counter. It works out the last two in detail (next page).

Solution A: a timestamp queue per IP

Keep a deque of request timestamps for each IP (map<ip, queue>). With a window of 5 seconds, anything older than 5 seconds does not matter. A snapshot at t = 15:

Deque at t = 1510111212131415

A new request arrives at t = 16. The window starts at 16 − 5 + 1 = 12, so drop everything older than 12:

Deque at t = 16121213141516

Now the deque size is the number of requests in the last 5 seconds. If it is below the limit, accept the request (and push its timestamp); otherwise drop it. Because requests arrive in time order, the queue stays sorted.

Problems with this solution
  • With ≈ 10,000 requests in a window, you must delete them one at a time, so processing time grows.
  • It is memory-intensive: every request’s timestamp is stored.
+ added: the two algorithms the notes list but do not explain
  • Token bucket: a bucket holds up to B tokens and gets new tokens at a steady rate. Each request takes one token; with none left, the request is rejected. It allows short bursts (up to B) while keeping a steady average rate.
  • Leaking bucket: requests join a queue that is emptied at a fixed rate; if the queue is full, requests are dropped. It smooths traffic into a constant flow.
Trade-off

The timestamp queue is exact but costs memory and time per request. The counters on the next page save both by being approximate.

The limit is 3 requests per 5 seconds; the deque holds 11, 12, 14 and a request arrives at t = 15. Which entries are dropped, and is the request accepted? (Window starts at 11, nothing older than 11 is removed, so the deque has 3 entries: 3 is the limit, so the request is rejected.)

Design a rate limiter (2)

From: System Design - Popular interview subtopics + added: distributed caveats

Fixed window counter

Threshold: 100 requests per 50 seconds. Keep one counter per bucket of 50 seconds (0–50, 51–100, 101–150…). It is cheap, but has a flaw: 100 requests in seconds 40–50 and another 100 in seconds 51–60 are each allowed, yet together that is 200 requests in 20 seconds, twice the intended rate.

Sliding window counter (an approximation)

Keep just two counts per client: the previous bucket and the current one. Buckets are 50 seconds. Say 60 requests came in the bucket 51–100 and 40 so far in the new bucket from t = 101 to 120.

  1. The part of the current bucket that has passed: 20 of 50 seconds = 40%.
  2. So the sliding window still includes the other 60% of the previous bucket: 60% of 60 = 36.
  3. Estimated count = 36 + 40 = 76.

Compare 76 with the threshold. You store just map<ip, pair<prev_count, cur_count>>, far less than the queue of timestamps.

MethodMemory per clientAccuracyFlaw
Timestamp queueOne entry per request in the windowExactMemory; per-request deletes
Fixed windowOne counterBoundary bursts up to 2×The 200-in-20-seconds problem

The lecture calls the sliding window counter the “best solution”; it is the best balance of memory and accuracy for many cases, not the most accurate one.

+ added: when you have many servers
  • If several gateway machines each count separately, a client can exceed the limit by spreading requests. Keep the counters in a shared store such as Redis.
  • Two gateways reading and then writing the same counter can race; use an atomic increment or a small script that runs in one step.
  • Decide what to do if the counter store is down: fail open (allow everything) or fail closed (reject). Each has a cost.
  • Rate limits can be by IP, by user, by API key or by endpoint (the microservices gateway notes list IP-based, service-based and API-based rules).
Trade-off

Stricter, more exact limiting costs memory and coordination; looser limiting is cheap but lets small bursts through. Match it to what you are protecting.

Microservices (1): services and monoliths

From: System Design - Microservices 1 + added: caveats

The plan for these classes: understand microservices, their problems and the design patterns around them: distributed transactions (two-phase commit as an anti-pattern, saga, CQRS), observability, the circuit breaker, and event sourcing. Nothing is implemented; the aim is the ideas.

What is a service?

Think of Google Search. When you type, you ask for typeahead suggestions; when you press search, you get a page of results. Those are two different jobs. A service is a combination of an application layer and a storage layer (app servers, database, caches and more) that offers certain APIs to do a job. The typeahead service has two: getTopXSuggestions(prefix) and updateFrequency(term). Anyone, a client or another service, can call them. The search-results service calls the typeahead service whenever a search happens.

The restaurant analogy

A restaurant has a kitchen, cooks, ingredients and waiters. You talk only to the waiters. The waiters are the APIs; the whole restaurant is the service.

Monolith

If the whole site is one big service, it is a monolith: the client talks to a load balancer, which sends requests to app servers all running the same single codebase, compiled into one executable. A single codebase does not mean a single file; it can still be modular and use the LLD patterns you know. Every app server can handle every kind of request. Behind it sit one or several databases, sharded or not. Monoliths are good when the project is small and not very complicated.

Why a monolith starts to hurt

  • As the codebase grows, new engineers take longer to understand it, and one change may have many dependencies.
  • Even a tiny change needs the whole project rebuilt and redeployed; build times grow.
  • Every app server runs all the code, so if one use case is very slow, requests pile up and slow down everything else.
The lecture’s advice

Keep using a monolith until you actually hit these problems. Microservices create many new challenges, are expensive and slow to get right, so do not move unless required.

SOA vs microservices

If it gets too big you can break it into parts in two styles:

Microservices (2): Flipkart, the client and the gateway

From: System Design - Microservices 1 + added: L4/L7 caveat

Flipkart as a monolith vs microservices

Monolith: app servers run one massive project containing the code for the home page, deals, product page, cart, checkout and order delivery. There may be several databases (products, images…), but every app server runs the same big executable.

Microservices: with thousands of developers running experiments daily, some pieces are clearly independent. A user’s profile (name, address, picture) is rarely needed: most of the time you browse products. Payment is another independent flow, and so are notifications and invoices. A possible split:

  • UserService: show and update the profile.
  • ProductService: product page and search: inventory, full-text search, all product details.
  • PaymentService, OrderService (track and update after ordering), CartService, InvoiceService, ReviewService.
Do not over-split

Do not separate parts that depend heavily on each other. If product search and product description need the same information, keep them in one service. Likewise, splitting user and user login is a poor idea if login constantly needs the user data. Dependencies cannot be zero, though; the invoice service depends on the order service, since invoices follow an order. So services must talk to each other, and one business transaction may cross several of them.

How does the client talk to many services?

Take the Facebook page: the menu on the left, the newsfeed in the centre, ads, events and “people you may know” on the right, your name at the top. Each can be its own service (News Feed, Ads, Events, People-you-may-know, User). The browser first fetches the page skeleton, then fires asynchronous requests in parallel: /newsfeed/<user_id>, /events/<user_id>, /ads/<user_id>, /pymk/<user_id>, /user/<user_id>. So the page does not get slow in proportion to the number of services; the calls overlap.

API gateway

DNS gives the IP of a load balancer. But the load balancer works at the network layer and does not know which microservice exists or where. So we need machines that know the services and how to route to them: API gateways. They sit behind the load balancer and work at the application layer.

  • The gateway is not one machine; there are several for availability, and each holds all the routing logic, so the load balancer can send a request to any of them.
  • Being at the application layer, it can also do authentication (is the session token valid? reject if not), rate limiting (IP-based, service-based or API-based rules; see the rate limiter pages) and encryption/decryption.
+ added

Modern layer-7 load balancers can also route by URL path, so the gateway’s real value is the shared cross-cutting jobs (authentication, rate limits, request shaping) in one place. The cost: it is a critical component and a place where business logic should not creep in.

Microservices (3): benefits and costs

From: System Design - Microservices 1

Benefits

  • Separation of concerns: each service chooses its own tech stack and database. ProductService may be Java Spring Boot with MongoDB (schema-less products) and an Elasticsearch full-text index; UserService could be Python with MySQL, no sharding.
  • Independent deployment: a service that rarely changes need not be redeployed; a busy one is deployed often.
  • Easier testing: the expected API responses are clear, and if they hold, a change does not affect others.
  • Independent scaling: UserService with little traffic can have a few app servers and a small DB; ProductService can have many app servers, a sharded MongoDB and a large Elasticsearch cluster.
  • Robustness: a critical bug in one service affects only it; others can isolate themselves (the circuit breaker page).

Costs

  • More latency: a monolith request goes load balancer → app server → database. With microservices it is load balancer → API gateway → the service’s load balancer → app server → database, and if more data is needed, more calls to other services.
  • More expensive: each service needs at least one app server and one database whatever its traffic. With 20 services you need at least 20 app servers, 20 DB machines, plus gateway machines.
  • Harder logging and tracing: one request passes many services, and to debug a failure you must look through each one’s logs.
  • Data inconsistency: OrderService and PaymentService may both store “payment done / pending”. Updating one does not guarantee the other stays in sync. You can only get eventual consistency across services, not immediate.

The questions the rest of the lectures answer

  1. How do you do observability: find the source of a failure across services?
  2. How do you make a transaction that spans services happen reliably (distributed transactions), and can you reduce latency and fix consistency?
  3. If one service fails, how do the others keep working (circuit breaker)?
+ added

Two more costs that beginners underestimate: versioning (a service’s API changes must not break its callers) and team and operations overhead (every service needs monitoring, deployment, on-call). Both are reasons to wait until a monolith really hurts.

Trade-off

You gain: independent teams, scaling, tech choices, fault containment.

You pay: latency, money, debugging difficulty, eventual consistency.

Microservices (4): observability

From: System Design - Microservices 1 + added: modern tools

Code fails: bugs, missed corner cases, bad machines, network trouble. Failure is fine; not knowing is not. Observability means:

  1. How do I quickly detect that there is a problem?
  2. How do I diagnose and fix it?
  3. How do I verify it is fixed?

With microservices a request crosses several services and some calls are asynchronous, which makes this harder.

Tracing: where did it fail?

Example: a message is sent (Messenger). It goes through the load balancer and API gateway to the message service, which stores it for sender and recipient. It also asks the notification service (asynchronously) to notify the recipient; that service keeps only a user → device mapping.

The async call can fail, and you cannot retry forever, so maybe the notification is never sent. A safer design is to publish an event on a queue like Kafka and let the notification service subscribe (the start of an event-driven architecture). If a receiver never got the notification, you need to find which hop failed.

Distributed tracing

  • Create a unique trace id (here the messageId) and pass it with the request through every service.
  • Log it everywhere and bring all logs to one searchable place.
  • Search by the id; where the logs stop is where the failure is.
  • Any database that can do full-text search can hold the logs: Splunk, or Elasticsearch with Logstash feeding it and Kibana as the screen on top (the “ELK” stack).

Alarms: detecting trouble

You must be told before you search anything. That needs aggregated numbers:

  • messages reaching each service; failure rate per service and per machine; CPU use;
  • latency, such as the P90 or P95 (the time under which 90% or 95% of requests finish);
  • what percentage of users see more than 1 second.

Store such numbers in a time-series database, not in logs (logs are best-effort and you only need a number per minute). A collector on each machine aggregates keys and values every minute and ships them to the central store. Code just publishes a key and value, for example publish("messagestore.latency", 50). You then ask: values for this key per minute, per 5 minutes, per day, combined by sum, max, min, average or p95.

Once you have the metrics you can set rules (“error rate above X”) that send email or phone calls; services such as PagerDuty automate paging. Clouds offer a built-in time-series service (AWS CloudWatch).

⚠ older pattern

The ods.publish call in the lecture is the style of an internal metrics system at a large company. Open-source and cloud equivalents today include Prometheus, Grafana and the managed services of each cloud. Distributed tracing also has a standard now, OpenTelemetry. The lecture’s picture covers two of the usual three pillars of observability (traces and metrics); the third is plain logs.

Trade-off

More logging and tracing means faster diagnosis but more storage and cost; many teams sample traces rather than keep all of them.

Microservices (5): transactions across services

From: System Design - Microservices 2 + added: caveats

The problem

In a monolith with one MySQL database, transferring ₹10 from A to B is a single ACID transaction. But if A is at Axis and B at SBI, two systems with separate databases must change together. The same appears inside a company: placing a Flipkart order means adding the order (Orders), reducing stock (Inventory), taking payment (Payments), then Shipping, each with its own code and database. How do we make it reliable?

Two-phase commit (and why it is an anti-pattern)

Take an iPhone 15 order: add an order entry and change inventory from 100 to 99. Two-phase commit simulates one transaction over the network:

  1. “Are you ready?” Both services lock the iPhone 15 row, so all other reads and writes on it block.
  2. Execute the update on both.
  3. When both confirm, ask both to release the lock.

For a long transaction the lock is held a long time, everything touching that row queues behind it, and the user experience degrades. So microservices treat it as an anti-pattern.

⚠ small naming fix

The agenda in your notes says “two phase locking”, but the body describes two-phase commit. Two-phase locking is a different concept (a way a single database orders its own transactions). The pattern here is two-phase commit.

The saga pattern

  1. Break the transaction into steps, each doable inside one service.
  2. Run the steps. On success, all steps ran. On failure, either retry, or roll back earlier steps reliably.

Example: Axis to SBI. Step 1: check A’s balance is at least ₹1000 and subtract it (else show an error). Step 2: ask SBI to add ₹1000 to B. If step 2 fails, undo step 1. Each step is atomic on its own and has a reliable undo.

Orchestration

One service is the owner, for example a transaction service in the bank. It calls every step in order and retries or rolls back when something fails.

Choreography

No single owner; it is event-driven. Each service does its own write atomically, then publishes an event to a persistent queue like Kafka, and other interested services subscribe and do their own writes.

Flipkart: the OrderService stores the order and publishes new_order_created with the details. InvoiceGenerationService, ProductService (reduce inventory) and NotificationService all subscribe, work in parallel, and publish their own events when done (new_invoice_created, inventory_updated, user_notified). A permanent failure is also an event (invoice_generation_failed), and affected services subscribe to it and roll back. Retry is easy with Kafka: an offset advances only when you acknowledge, so do not acknowledge until the event is processed. In effect the transaction runs as a coordinated set of events.

OrchestrationChoreography
SpeedFaster: direct callsSlower: each event adds a hop through the queue
ReliabilityThe orchestrator may die, making rollback hardNo single machine whose failure causes inconsistency
ObservabilityEasy: look at the orchestrator’s logs; see which step is slowNeeds a proper observability framework (tracing)

Kafka reminder from the lecture: add partitions to scale, use a partition key for ordering (recipient id for messages), and use consumer groups to parallelise consumers (see the Kafka pages).

+ added

Both styles need idempotent steps, since retries mean a step can run twice, and each step needs a compensating action (refund, restock). A cancel step cannot always undo a real-world action (an email already sent), which is why saga designs order steps so that the hardest-to-undo comes last.

Trade-off

Sagas avoid long locks, but customers can see in-between states (stock reserved, payment pending). You trade the tidy isolation of ACID for availability and speed.

Microservices (6): CQRS

From: System Design - Microservices 2 + added: event sourcing

The problem: a join across two services

Two services: Messages and Notifications. On Facebook, pages (businesses) get messages and notifications too, and they are a small share of all users. For pages you want: the average notifications a page gets, the average messages, and which pages get many messages but few notifications. That needs a join across the two services’ data, for a small slice of the data.

Service 1 must not query service 2’s database directly; that is an anti-pattern because it breaks separation of concerns. So how do you join?

CQRS

  1. Separate commands (create, update, delete) from queries (reads).
  2. Writes keep going to their own services: addMessage to Messages and addNotification to Notifications.
  3. Create another database (maybe a third service) just for the cross-service reads. For the small slice you care about (pages only), publish the data there from both services, for example through Kafka that the new service consumes, or through database hooks or scripts.
  4. Nothing is written directly to it; it only receives copies. All the read queries go to this service, which already holds the joined information.

CQRS is simply: for a particular use case, separate the read side from the write side.

⚠ small naming fix

The notes expand CQRS as “command-query-request-segregation”. The standard name is Command Query Responsibility Segregation.

+ added: event sourcing (in your agenda, not in the text)

The first lecture’s agenda lists event sourcing, but the notes I read do not describe it. In short: instead of storing only the current state, store every event as the source of truth (“item added”, “item removed”), and rebuild the state by replaying them. It echoes the write-ahead log on the LSM page and a Kafka topic, and it pairs naturally with CQRS, where the read database is just a view built from the events. I added only this summary, not details.

Trade-off

CQRS gives you fast, joined reads without breaking service boundaries, but the read copy is eventually consistent and you must keep the publishing pipeline reliable.

Microservices (7): the circuit breaker

From: System Design - Microservices 2 + added: caveats

The problem

Services: user, message, notification, SMS, email, push notification. Suppose the notification service has trouble (maybe a bad deployment). Requests flow user → message → notification, and the third step keeps timing out. More and more requests wait on it, which loads up the message service with queued I/O, which then fails, and the user service is next: cascading failure.

A second risk: when notification tries to recover, it has a backlog and new requests keep arriving, so recovery is slow. This is the thundering herd.

Goal: when a service is unhealthy, let it recover and stop others from dying with it.

The solution, step by step

  1. Sort the errors. “User not found” or “bad request format” are normal failures and say nothing about the service’s health. Timeouts, connection resets and server errors mean the service is degraded or buggy. Only the second kind count.
  2. Decide when the service is down or recovered. For example: more than 100 such failures in the last minute means down. Keep the count somewhere shared, say the global cache of the calling service.
  3. Keep one of three states for each service you call:
StateMeaningWhat the caller does
ClosedHealthySend requests normally
OpenUnhealthySend nothing; fail fast or call a fallback; give it time to recover
Half-openTestingSend a small share of requests (say 1%) and measure success

It starts closed. If failures pass the threshold it switches to open. Every T seconds it moves to half-open to test. If the success rate is good, back to closed; otherwise to open again, and this repeats.

state = shared_store.get("notification_breaker")       # my tidy version of the lecture's sketch
if state == "open":
    return fallback()                                  # or just fail fast
if state == "half-open" and random() >= 0.01:
    return fallback()                                  # only ~1% are allowed through as probes
try:
    response = call(notification_service)
    record_success()
    return response
except (Timeout, ConnectionReset, ServerError):
    record_failure()
    if failures_in_last_minute() > THRESHOLD: shared_store.set("notification_breaker", "open")
    return fallback()

A separate timer moves “open” to “half-open” every T seconds, and a good probe success rate moves it to “closed”.

⚠ terminology

The lecture calls timeouts and resets “non-transient” failures. Those are normally transient (they may pass). The lecture means “signs the service is unhealthy”, as opposed to ordinary client errors. I would call them “health failures”.

+ added
  • A fallback is the graceful-degradation idea: show cached data, queue the notification for later, or skip it, instead of returning an error.
  • Libraries implement this so you do not write it yourself (for example Resilience4j; Netflix’s Hystrix was a well-known early one and is in maintenance mode).
  • Combine it with timeouts, retries with backoff and jitter, and bulkheads (the reliability page).
Trade-off

A breaker that trips easily protects callers but turns a blip into a feature outage; one that trips late lets the cascade start. Tune the threshold and test it.

API design basics

+ added page Gap-fill, linked to the LIMIT/OFFSET you saw in the newsfeed case.

An API is the set of calls one program offers to another. Three popular styles:

StyleIdeaStrengthCost
RESTResources with URLs and HTTP verbs (GET, POST, PUT, DELETE), statelessSimple, works with browsers, caches wellMay over- or under-fetch data
gRPCTyped calls with compact binary messages over HTTP/2Fast, strict contracts, good between internal servicesHarder to call from a browser or debug by eye
GraphQLOne endpoint; the client lists exactly the fields it wantsFlexible for varied clientsCaching and rate limiting are harder; costly queries need guarding

Pagination (ties to your LIMIT x OFFSET y)

  • Offset: LIMIT 20 OFFSET 400. Simple, but the database still walks past the first 400 rows, so deep pages get slower, and if rows are inserted meanwhile you may see repeats or gaps.
  • Cursor (keyset): “give me 20 items older than this timestamp/id”. Stays fast on deep pages and stable. This is what “first 10 tweets, then the next 20” in the column-family case really wants.

Other basics

  • Versioning: put /v1/ in the path or use a header, and prefer adding fields over changing them so old clients keep working.
  • Rate limiting: cap how many requests a client may make so one caller cannot overload you. Common algorithms: token bucket, fixed window, sliding window. Reply 429 Too Many Requests and say when to retry. The rate limiter pages work an example.
  • Idempotent methods: GET, PUT and DELETE are safe to repeat; POST is not, so give POSTs an idempotency key when repeats would hurt.
Trade-off

The flexible styles (GraphQL) move complexity to the server; the strict ones (gRPC) buy speed at the price of convenience. Choose by who calls you.

Monolith vs microservices

+ added page A short recap; the full lecture notes are in the Microservices chapter.

MonolithMicroservices
ShapeOne deployable program, usually one databaseMany small services, each owning its data, talking over the network
You gainSimple to build, test, debug and deploy; transactions are easyTeams deploy and scale each part independently; one failure can stay contained
You payEverything scales and deploys together; a big codebase gets tangledNetwork calls (slow, failure-prone), distributed transactions, harder debugging, many things to operate

A common beginner rule: start with a well-organized monolith and split off a service when a real pain (team size, scaling one hot part) demands it.

Service discovery

Service instances come and go. How does service A find a healthy instance of B? Either the caller asks a registry (client-side discovery, a list kept up to date by health checks, for example in Consul or etcd) or the call goes through a balancer or DNS name that tracks instances (server-side discovery, as in Kubernetes services). It is the load balancer’s health-check idea from earlier, applied between services.

API gateway

A single front door for clients. It routes requests to the right service and commonly handles authentication, TLS, rate limiting and caching. Risks: it can become a bottleneck or single point of failure if not made redundant, and it tempts you to stuff business logic into it.

Trade-off

Microservices trade simplicity for independence. If your team is small and your traffic modest, the cost usually exceeds the benefit.

Staying up when things break

+ added page Gap-fill. It links back to cascading failure and cache stampede.

At scale something is always failing. Reliability is about containing failures so they do not spread.

Availability in “nines”

Computed for a 365-day year; the real figure depends on how the provider counts.

TargetDowntime allowed per year ≈
99% (two nines)≈ 3.7 days
99.9%≈ 8.8 hours
99.99%≈ 53 minutes
99.999%≈ 5 minutes

The toolbox

  • Replication and failover: keep copies so a dead machine is replaceable (earlier pages).
  • Timeouts: never wait forever for another service. Decide how long is too long.
  • Retries with exponential backoff and jitter: if a call fails, wait a little and try again; double the wait each time, and add a random amount (jitter) so thousands of clients do not retry in the same instant. Retry only calls that are safe to repeat (idempotent). 
    wait = random(0, min(cap, base * 2 ** attempt))   // "full jitter"
  • Circuit breaker: after many failures, stop calling the sick service for a while (the circuit is open), then let one trial call through (half-open); if it works, resume. It protects the caller and gives the sick service room to recover. The Microservices chapter walks through it in detail.
  • Bulkheads: separate pools of resources, so one overloaded feature cannot use up everything (like watertight compartments in a ship).
  • Graceful degradation: when something fails, serve a reduced version rather than an error: show cached or slightly stale data, skip the ranking, hide the non-essential widget.
+ link back

Retries without backoff turn a small failure into a flood (a retry storm), the same shape as the cascading failure on the consistent-hashing page and the stampede on the caching page.

Trade-off

Every protection adds complexity and can itself misbehave (a breaker that opens too eagerly makes an outage out of a hiccup). Test them.

1. Why does the Delicious data need sharding, and what did the first estimate show?

≈ 200 MB of new bookmarks a day fills a small (2004) disk in months, so you must split the data. The math showed storage, not write speed, was the problem.

2. Why is user_id a better sharding key than site_url for Delicious?

The frequent operation is “all bookmarks of a user”. With user_id it touches one shard; with site_url it touches all of them.

3. What happens to data when you go from 4 to 5 shards with user % N, versus consistent hashing?

With % N about 80% of users move. With consistent hashing only about 1/5 move, taken from many neighbors.

4. What do virtual nodes fix?

One machine’s failure dumping all its load on one neighbor (cascading failure). Many points per machine spread its slice over many neighbors.

5. Why separate application servers from the database?

Deploys no longer take storage down, each tier gets its own resources and scales independently. The cost is an extra network hop.

6. TTL or metadata for the test-data cache? Why?

Metadata with versioned file names. A low TTL misses constantly, a high TTL serves stale files; the version in the name makes invalidation exact.

7. Why prefer a global cache for the contest ranklist?

One shared copy means one recomputation per refresh instead of one per app server.

8. Why is the Facebook newsfeed hard with user_id sharding, and what did the numbers suggest?

Friends’ posts live on other shards. The last 30 days of all posts is only ≈ 180 GB, so a replicated derived store of recent posts can answer it.

9. Name two things SQL does well and two things that hurt it at scale.

Well: joins across tables, ACID. Hurts: rigid schema for varied data; sharding makes joins and transactions span machines.

10. Pick a key for Slack and say why not UserID.

GroupID. With UserID one message must be written on many machines.

11. Key-value, document or column-family for “latest 20 tweets of a hashtag”?

Column-family, keyed by hashtag: read only the first entries, with an offset to continue. A key-value store would return the whole value.

12. State CAP and PACELC in one sentence each.

CAP: during a partition choose consistency or availability. PACELC: and when there is no partition, choose latency or consistency.

13. In master–slave, what changes between the three flavors?

How many copies must have the write before success is returned: none, one, or all.

14. How is a failed money transfer undone, and what keeps retries safe?

A compensating action refunds the sender; an idempotency key stops a retry from applying twice.

15. Why is an LSM tree good at writes, and what does it pay for it?

A write is a memory update plus a sequential log append. It pays in reads (several files may be checked) and in background compaction work.

16. What does a Bloom filter answer, and what can it get wrong?

“Definitely not here” or “maybe here”. It can wrongly say “maybe”, never wrongly say “no”.

17. A shard with a master and 2 slaves loses a slave and no spare machine exists. What rule of Manmeet’s algorithm was missing?

A reserve of X standby machines, kept ahead of creating new shards.

18. With 3 copies, which (R, W) pairs guarantee reads see the latest write?

Any pair with R + W > 3, such as (2, 2), (1, 3) or (3, 1).

19. Why must the master’s Zookeeper node be ephemeral, and why a majority for writes?

Ephemeral so it disappears when the master dies; majority so two partitioned groups cannot both succeed (split brain).

20. Why do equal keys keep their order in Kafka?

Equal keys hash to the same partition, and order is guaranteed inside a partition.

21. Why store the top five suggestions in every trie node, and what does it cost?

Reads become O(prefix length); every update must refresh all ancestor nodes.

22. Which Messenger write order is safer, sender first or recipient first?

Recipient first: the worst case is the sender briefly missing their own message, not a phantom message the recipient never got.

23. Why can’t a normal SQL LIKE query search long posts well, and what replaces it?

It scans every row. An inverted index maps words to the documents that contain them.

24. How do you find the neighbouring places of a point with a quadtree?

Find your leaf, query its grid id plus the neighbouring leaves’ ids (next pointers, or probing 8 points beyond the boundary).

25. What stops a moving cab from flooding the quadtree with writes?

The app updates only if the position changed, and the tree only when the cab crosses a grid boundary.

26. Name the five parts of a Snowflake id.

Sign bit, 41-bit timestamp, 5-bit data center, 5-bit machine, 12-bit sequence.

27. Why can a fixed-window rate limiter let through twice the limit?

A burst at the end of one window and the start of the next both count as allowed.

28. Why is two-phase commit an anti-pattern in microservices, and what replaces it?

Long-held locks slow everything. A saga of local steps with compensations replaces it.

29. What problem does CQRS solve, and what does it cost?

Cross-service reads without touching another service’s database. The read copy is eventually consistent.

30. Describe the circuit breaker’s three states.

Closed (normal), open (send nothing), half-open (probe with a small share).
