Data, information, database, DBMSLEC-1

In plain wordsData is raw facts (numbers, names, readings) with no meaning on its own. Information is data that has been processed and put in context so you can decide something. A database is an organised collection of related data, and a DBMS is the software that stores, protects and retrieves it for many users and programs at once.
DataInformation
Formraw, unorganised factsprocessed, organised, in context
Meaningnone by itselfsupports decisions
Examplea list of 4,000 birth dates“there are 100 senior citizens, the sex ratio is 1.1”
  • Quantitative data is numerical (price, weight). Qualitative data is descriptive (name, colour).
  • DBMS examples: MySQL, PostgreSQL, Oracle, SQL Server, MongoDB. An RDBMS is a DBMS built on tables (relations) of rows and columns.
  • SQL is a language, not a database. MySQL is an RDBMS that understands SQL.

Three-schema architecture and data independenceLEC-2

In plain wordsThe DBMS hides complexity behind three levels of abstraction so many users can see the same stored data in the way that suits them, and so the storage can change without breaking applications.
LevelAlso calledDescribesWho uses it
Externalview levelthe part of the data one user group sees (sub-schemas, views); also a security layerend users, applications
Conceptuallogical levelwhat data is stored and the relationships and constraintsDBAs, designers
Internalphysical levelhow it is stored: files, indexes, compression, encryptionthe DBMS itself
  • Physical data independence: changing how data is stored does not change the logical schema or the applications.
  • Logical data independence: changing the logical schema (for example adding a column) does not break the external views or programs.
  • Schema = the structure (changes rarely), like variable declarations. Instance = the data at one moment (changes constantly), like the variable values.

  • DBA: schema definition, storage and access methods, authorisation, backups, patches and upgrades.

Tables, tuples, degree and cardinalityLEC-7

In plain wordsThe relational model stores data as relations (tables). A row is a tuple, a column is an attribute with a permitted set of values called its domain. The table’s name and columns are the relation schema.
  • Degree = number of columns. Cardinality = number of rows. (Not the same “cardinality” as the ER relationship ratio.)
  • Properties of a table: unique name; unique column names; atomic values (no lists in a cell); no two identical rows; row and column order mean nothing; integrity constraints are enforced.

The keysLEC-7

KeyMeaningExample in student(id, email, phone, name)
Super keyany set of attributes that uniquely identifies a row(id), (email), (id, name), (id, email, phone)…
Candidate keya minimal super key: remove any attribute and it stops being unique; never NULL(id), (email)
Primary keythe candidate key you chose; unique, not null, one per table(id)
Alternate keycandidate keys not chosen(email)
Foreign keya column(s) that references another table’s key. The table holding the FK is the child (referencing); the other is the parent (referenced). May be NULLorders.customer_id → customers.id
Composite keya key made of two or more columns(student_id, course_id)
Surrogate keya synthetic key with no business meaning, generated by the DBauto-increment id, UUID
+ addedNatural vs surrogate key: natural keys (an email, a national id) carry meaning, can change, and can be long. Surrogate keys are small, stable and never change, so most designs use a surrogate primary key and add a UNIQUE constraint on the natural key. A column can be a primary key and a foreign key at once (a 1:1 extension table).

Integrity constraintsLEC-7

ConstraintRule
Domainevery value must fit the column’s type and range (CHECK, ENUM, data type)
Entityevery table has a primary key and it is never NULL
Referentiala foreign key value must exist in the parent table, or be NULL
Key constraintsPRIMARY KEY, UNIQUE, NOT NULL, DEFAULT, CHECK, FOREIGN KEY
  • PRIMARY KEY = UNIQUE + NOT NULL, one per table. UNIQUE allows NULL, and a table can have many. (MySQL, PostgreSQL and Oracle allow several NULLs in a unique column; SQL Server allows only one.)
  • Constraints are enforced by the database, so they hold no matter which application writes the data.
⚑ correctedThe reference says a compound key is “a PK formed using 2 FKs”. Terms vary by textbook; composite key (two or more columns) is the standard word. A key made of two foreign keys is exactly the primary key of a junction table. Also, the “six key constraints” list mixes true keys with ordinary column constraints, so remember them as column and table constraints.

Remember!

  • Super ⊃ candidate ⊃ primary; the rest are alternate
  • FK may be NULL; it must otherwise match a parent key
  • PK = UNIQUE + NOT NULL
  • Degree = columns, cardinality = rows

⚑ correctedThe references list VARCHAR as 0 to 255: that is the old limit; in MySQL VARCHAR can be up to 65,535 bytes (shared with the rest of the row), while CHAR is 0–255. They say FLOAT/DOUBLE have “23 / 24–53 digits”: that is binary bits of precision, roughly 7 and 15 decimal digits. DECIMAL is not “double stored as a string”: it is exact fixed-point arithmetic. SELECT, WHERE and the operatorsLEC-9 · Apna College

In plain wordsSELECT picks the columns, FROM names the table, WHERE keeps only the rows that match. Everything else (grouping, sorting, limiting) refines that result.
SELECT name, age FROM customers;                  -- chosen columns
SELECT * FROM customers WHERE country = 'India';  -- all columns, filtered rows
SELECT DISTINCT country FROM customers;           -- remove duplicate rows
SELECT name AS customer_name FROM customers;      -- alias

-- comparison: =  >  <  >=  <=  <> (or !=)
SELECT * FROM customers WHERE age >= 18 AND country = 'India';
SELECT * FROM customers WHERE country IN ('India', 'Japan');           -- shorthand for OR
SELECT * FROM orders    WHERE total BETWEEN 100 AND 500;               -- inclusive both ends
SELECT * FROM customers WHERE email IS NULL;                           -- NULL needs IS NULL
SELECT * FROM customers WHERE name LIKE 'A%';                          -- starts with A
SELECT * FROM customers WHERE name LIKE '_r%';                         -- 'r' is the 2nd letter
SELECT * FROM customers WHERE NOT (country = 'India');
  • LIKE wildcards: % = any number of characters (zero or more), _ = exactly one. '%or%' contains “or”; 'a%o' starts with a and ends with o.
  • AND binds tighter than OR. Use brackets: A OR B AND C means A OR (B AND C).
  • SELECT without FROM: SELECT 55 + 11;, SELECT NOW();. (Oracle needs the dummy table DUAL; MySQL accepts it optionally.)

ORDER BY, LIMIT and paginationApna College

SELECT name, age FROM customers ORDER BY age DESC, name ASC;   -- first by age, ties by name
SELECT * FROM orders ORDER BY total DESC LIMIT 5;              -- top 5
SELECT * FROM orders ORDER BY id LIMIT 10 OFFSET 20;           -- page 3 of 10 (slow for deep pages)
SELECT name, salary * 12 AS yearly FROM employees ORDER BY yearly;   -- ORDER BY may use the alias
  • Default sort is ascending. Without ORDER BY the row order is not guaranteed.
  • NULLs: MySQL sorts them as the smallest value (first in ASC); PostgreSQL treats them as the largest and supports NULLS FIRST / NULLS LAST (MySQL does not).
  • Deep pages: OFFSET 1000000 still reads and discards a million rows. Use keyset pagination (WHERE id > :last_id ORDER BY id LIMIT 20).

GROUP BY, aggregates and HAVINGLEC-9 · Apna College

In plain wordsGROUP BY puts rows into buckets by a column, then an aggregate (COUNT, SUM, AVG, MIN, MAX) summarises each bucket. HAVING filters buckets; WHERE filters rows before they are grouped.
SELECT country, COUNT(*) AS customers, AVG(age) AS avg_age
FROM customers
WHERE age IS NOT NULL            -- row filter, runs BEFORE grouping
GROUP BY country
HAVING COUNT(*) > 50            -- group filter, runs AFTER grouping
ORDER BY customers DESC;
WHEREHAVING
Filtersindividual rowsgroups
Runsbefore GROUP BYafter GROUP BY
Can use aggregatesnoyes
Also works inSELECT, UPDATE, DELETEessentially SELECT with grouping
  • Every non-aggregated column in SELECT must appear in GROUP BY (strict mode / ONLY_FULL_GROUP_BY, PostgreSQL always).
  • GROUP BY with no aggregate behaves like DISTINCT.
  • COUNT(*) counts rows; COUNT(col) counts non-NULL values; COUNT(DISTINCT col) counts distinct non-NULL values. Aggregates other than COUNT(*) ignore NULLs.

NULL: three-valued logicthe source of many bugs

In plain wordsNULL means “unknown or missing”, not zero and not an empty string. Any comparison with NULL gives UNKNOWN, and WHERE keeps only rows that are TRUE.
SELECT NULL = NULL;            -- NULL (unknown), not TRUE
SELECT * FROM customers WHERE age = NULL;     -- returns nothing, ever
SELECT * FROM customers WHERE age IS NULL;    -- correct
SELECT 5 + NULL;               -- NULL
SELECT COALESCE(age, 0) FROM customers;       -- replace NULL with a default
SELECT NULLIF(a, 0);           -- returns NULL when a = 0 (avoid divide by zero)

-- The NOT IN trap: if the subquery returns any NULL, NOT IN returns NO rows
SELECT * FROM customers WHERE id NOT IN (SELECT customer_id FROM orders);     -- risky
SELECT * FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);   -- safe
+ addedNULL in a UNIQUE column, in GROUP BY (all NULLs form one group), in DISTINCT (treated as equal) and in ORDER BY all behave differently from =. Interviewers love “what does COUNT(col) return when everything is NULL?” (0).

Remember!

  • WHERE filters rows, HAVING filters groups
  • FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • = NULL never works: IS NULL
  • NOT IN + NULL = no rows

The join typesLEC-9 · Apna College

In plain wordsA join stitches rows of two tables together wherever a condition matches, normally foreign key = primary key. The join type decides what happens to rows that find no partner.
JoinKeepsUnmatched rows
INNER JOINonly rows that match in both tablesdropped
LEFT JOINall rows of the left table, plus matchesleft rows kept; right columns are NULL
RIGHT JOINall rows of the right table, plus matchesright rows kept; left columns are NULL
FULL OUTER JOINall rows of bothkept on both sides with NULLs. Not in MySQL: emulate
CROSS JOINevery combination (Cartesian product): 10 × 5 rows → 50no condition
Self joina table joined to itself via two aliaseshierarchies, comparisons within one table
-- customers with their orders (only customers who have orders)
SELECT c.name, o.id AS order_id, o.total
FROM customers c
INNER JOIN orders o ON o.customer_id = c.id;

-- every customer, with or without orders
SELECT c.name, o.id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id;

-- customers with NO orders (anti-join)
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;

-- FULL OUTER JOIN emulated in MySQL
SELECT * FROM a LEFT JOIN  b ON a.id = b.id
UNION
SELECT * FROM a RIGHT JOIN b ON a.id = b.id;

-- self join: each employee with their manager
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;       -- LEFT keeps the top boss (manager NULL)
  • Use aliases (c, o) and qualify columns to avoid “ambiguous column” errors. USING (id) is a shorthand when the column has the same name on both sides.
  • The old comma style FROM a, b WHERE a.id = b.a_id is an inner join, but a forgotten WHERE silently makes a cross join. Prefer explicit JOIN … ON.
  • Joining three tables just chains the joins: … JOIN orders … JOIN order_items ….

Join traps interviewers test+ added

+ added
  • A filter on the right table in WHERE silently turns a LEFT JOIN into an inner join, because NULL rows fail the test. Put it in ON: LEFT JOIN orders o ON o.customer_id = c.id AND o.total > 100.
  • One-to-many multiplies rows. Joining customers to orders returns one row per order, so SUM(c.credit) over the join counts a customer’s credit many times. Aggregate in a subquery first, or use COUNT(DISTINCT c.id).
  • Joining on a nullable column: NULL = NULL is not true, so such rows never match.
  • Performance: join columns need an index (the foreign key side especially). Foreign keys in InnoDB are indexed automatically; in PostgreSQL they are not.
⚑ correctedThe SQL notes’ LEFT JOIN example shows a “NULL / Monitor” row. A left join from Customers can never show an order that has no customer: that row belongs to the RIGHT and FULL join results. The sample tables are also inconsistent between examples (order 103 changes from Headphones to Monitor). Trust the rules above, not those result tables.

Set operationsLEC-9 · Apna College

In plain wordsJoins glue tables side by side (more columns). Set operations stack the results of two SELECTs on top of each other (more rows). Both queries need the same number of columns, in the same order, with compatible types.
OperatorResultNotes
UNIONall rows from both, duplicates removedneeds a sort or hash to de-duplicate
UNION ALLall rows from both, duplicates keptfaster; use it when you know there are no duplicates
INTERSECTrows in bothMySQL 8.0.31+, PostgreSQL, SQL Server, Oracle
EXCEPT / MINUSrows in the first but not the secondEXCEPT: PostgreSQL, SQL Server, MySQL 8.0.31+; MINUS: Oracle
SELECT name FROM customers
UNION
SELECT name FROM suppliers;

-- emulating INTERSECT / EXCEPT on older MySQL
SELECT DISTINCT c.name FROM customers c WHERE EXISTS (SELECT 1 FROM suppliers s WHERE s.name = c.name);       -- INTERSECT
SELECT DISTINCT c.name FROM customers c WHERE NOT EXISTS (SELECT 1 FROM suppliers s WHERE s.name = c.name);   -- EXCEPT
⚑ correctedThe notes say set operations “always give distinct rows”. That is true for UNION, INTERSECT and EXCEPT by default, but UNION ALL does not. They also say INTERSECT and MINUS must be “emulated” and that set operations are “generally faster than joins”: both depend on the version and the query, so measure with EXPLAIN instead of assuming.

Remember!

  • INNER = matches · LEFT = all left · FULL = both
  • Right-table filter belongs in ON for a LEFT JOIN
  • Anti-join: LEFT JOIN … IS NULL, or NOT EXISTS
  • UNION dedupes, UNION ALL doesn’t

SubqueriesLEC-9 · Apna College

In plain wordsA subquery is a SELECT inside another query, whose result feeds the outer query. It breaks a hard question into steps.
-- WHERE: customers who ordered something over 500
SELECT name FROM customers
WHERE id IN (SELECT customer_id FROM orders WHERE total > 500);

-- scalar subquery: employees paid above the average
SELECT name, salary FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- FROM (derived table): highest rating among Indian movies
SELECT MAX(rating) FROM (SELECT * FROM movie WHERE country = 'India') AS temp;   -- derived table needs an alias

-- SELECT: a value computed per row
SELECT c.name, (SELECT COUNT(*) FROM orders o WHERE o.customer_id = c.id) AS order_count
FROM customers c;
  • Correlated subquery: the inner query refers to the outer row, so it conceptually runs once per outer row. A normal subquery runs once.
  • EXISTS stops at the first match and returns true/false; IN compares against a whole list. EXISTS is safer with NULLs (see NOT IN trap) and is often faster for “is there any related row?”.
  • ANY / ALL: salary > ALL (SELECT salary FROM interns).
-- correlated: employees earning more than the average of THEIR department
SELECT e.name, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(salary) FROM employees WHERE dept_id = e.dept_id);
⚑ correctedThe SQL notes’ subquery example is invalid: it selects Quantity from Products and multiplies by Price, but Quantity lives in Orders; the table needs a join first. And the table “joins faster, subqueries slower” is a myth: the optimiser often rewrites one into the other. Choose for clarity, then check EXPLAIN.

CTEs: WITH+ added, expected in interviews

In plain wordsA common table expression gives a subquery a name, defined at the top, so the query reads top to bottom instead of inside out. MySQL 8+ and PostgreSQL support it.
WITH big_spenders AS (
  SELECT customer_id, SUM(total) AS spent
  FROM orders
  GROUP BY customer_id
  HAVING SUM(total) > 1000
)
SELECT c.name, b.spent
FROM big_spenders b
JOIN customers c ON c.id = b.customer_id
ORDER BY b.spent DESC;

-- recursive CTE: walk an org chart from the top boss down
WITH RECURSIVE chain AS (
  SELECT id, name, manager_id, 1 AS level FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, e.manager_id, c.level + 1
  FROM employees e JOIN chain c ON e.manager_id = c.id
)
SELECT * FROM chain ORDER BY level;

ViewsLEC-9

In plain wordsA view is a saved query that behaves like a virtual table. It stores no data of its own: each time you read it, the underlying query runs on the base tables.
CREATE VIEW trainer_contacts AS
SELECT c.course_name, c.trainer, t.email
FROM courses c JOIN contact t ON c.id = t.id;

SELECT * FROM trainer_contacts;
CREATE OR REPLACE VIEW trainer_contacts AS SELECT …;   -- or ALTER VIEW
DROP VIEW IF EXISTS trainer_contacts;
  • Why: hide complexity, give each user group only the columns they may see (security), keep one definition of a tricky join.
  • Simple views (one table, no aggregates) are updatable; joins, GROUP BY and DISTINCT make them read-only.
  • Materialized view (PostgreSQL, Oracle): stores the result and must be refreshed, so reads are fast but can be stale. MySQL has none built in.

What a window function is+ added, in every senior SQL screen

In plain wordsAn aggregate with GROUP BY collapses many rows into one. A window function does the calculation over a set of related rows but keeps every row. OVER (...) says which rows belong to each row’s “window” and in what order.
function() OVER (
  PARTITION BY col     -- split rows into groups (like GROUP BY, but rows stay)
  ORDER BY col         -- order inside each group
  ROWS BETWEEN … AND … -- optional frame: which rows around the current one
)

SELECT name, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg,        -- every row also sees its dept average
       salary - AVG(salary) OVER (PARTITION BY dept_id) AS vs_avg
FROM employees;

Functional dependenciesLEC-11

In plain wordsA functional dependency X → Y means: if you know X, there is exactly one possible Y. student_id → name. X is the determinant, Y the dependent. Normalisation is the process of arranging columns so every dependency is on a key, which removes redundancy.
  • Trivial FD: Y is a subset of X ((id, name) → name). Non-trivial: Y is not inside X.
  • Armstrong’s axioms: Reflexivity (if Y ⊆ X then X → Y), Augmentation (X → Y gives XZ → YZ), Transitivity (X → Y and Y → Z give X → Z).
  • Prime attribute = part of some candidate key. Non-prime = not part of any.

What an index isLEC-14

In plain wordsAn index is a separate, sorted data structure that maps a search key to the location of the row, like the index at the back of a book. Without it the database reads the whole table (a full scan); with it, it jumps straight to the match.
  • Search key = the indexed column(s). Data reference = pointer to the row (or the primary key).
  • Indexing is optional and secondary to the data. It speeds up WHERE, JOIN, ORDER BY and GROUP BY, and costs space and write time.
  • Advantages: faster reads and less I/O. Limits: extra storage; every INSERT, UPDATE and DELETE must also update every index.

How it works: the B+ tree+ added

In plain wordsMost relational indexes are B+ trees: a balanced, shallow tree where internal nodes route the search and the sorted leaf nodes (linked together) hold the keys. A lookup takes O(log n) page reads, usually 3 to 4 even for hundreds of millions of rows, and a range scan just walks the linked leaves.
Root → internal → linked leaves. Equality and range queries both stay fast.

Composite indexes: the leftmost-prefix rule+ added

CREATE INDEX idx_orders ON orders (customer_id, placed_on, status);

-- Uses the index:
WHERE customer_id = 7
WHERE customer_id = 7 AND placed_on >= '2025-01-01'
WHERE customer_id = 7 ORDER BY placed_on           -- the index even provides the sort

-- Cannot use it efficiently (skips the leading column):
WHERE placed_on >= '2025-01-01'
WHERE status = 'paid'

-- Rule of thumb for column order: equality columns first, then range / sort columns

Why an index is not used+ added

  • A function on the column: WHERE YEAR(placed_on) = 2025 → use a range placed_on >= '2025-01-01' AND placed_on < '2026-01-01'.
  • Leading wildcard: LIKE '%son' can’t use a B-tree; LIKE 'son%' can.
  • Type mismatch: comparing a string column to a number forces conversion of every row.
  • Low selectivity: an index on a boolean or a status with 3 values rarely helps; the optimiser prefers a scan when many rows match.
  • OR across different columns, !=, and the left-prefix being skipped.
  • Stale statistics (ANALYZE TABLE) can mislead the optimiser.

  • Index = sorted B+ tree; O(log n) lookup
  • Reads faster, writes and space slower
  • Composite: leftmost prefix, equality before range

Transactions and ACIDLEC-12

In plain wordsA transaction is a logical unit of work made of one or more statements that must succeed or fail together. Transferring money is the standard example: debit one account and credit another, never just one.
START TRANSACTION;                       -- BEGIN in PostgreSQL
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
SAVEPOINT after_debit;

-- something goes wrong?
ROLLBACK TO after_debit;                 -- undo only the part after the savepoint
COMMIT;                                  -- make everything permanent   (or ROLLBACK; to undo it all)

Locks, MVCC and deadlocks+ added

  • Locks: shared (read; many allowed) and exclusive (write; one only), at row or table level. Row locks allow concurrency; lock escalation and table locks hurt it.
  • MVCC (multi-version concurrency control): InnoDB and PostgreSQL keep several versions of a row, so readers do not block writers and writers do not block readers.
  • Pessimistic vs optimistic: lock first and assume conflict (FOR UPDATE) versus assume no conflict and detect it at write time (version column).
  • Deadlock: T1 holds row A and waits for B while T2 holds B and waits for A. The database detects the cycle and aborts one transaction (an error you must retry). Prevent it with a consistent lock order, short transactions, and good indexes (fewer rows locked).
  • Starvation: a transaction waits forever because others keep getting the lock.

ReplicationLEC-17, LEC-21

  • What: copy the same data to several servers. Why: availability (a server can fail), read scaling and disaster recovery. This is “useful redundancy”, different from the bad redundancy that normalisation removes.
  • Synchronous: the primary waits for replicas before confirming a write, so there is no data loss but writes are slower. Asynchronous: it confirms immediately and replicas catch up, so it is fast but a failover can lose the last writes and reads can lag. Semi-sync waits for at least one replica.
  • Failover: promote a replica when the primary dies (automatic with Orchestrator, Patroni, Atlas, RDS Multi-AZ). Beware split brain: two nodes both think they are primary.
  • Reading your own writes: after a write, read from the primary (or stick the user to it for a few seconds), so they do not “lose” what they just saved.

LetterMeaning

What NoSQL is, and where it came fromLEC-15, LEC-16

In plain words“NoSQL” (read “not only SQL”) means non-relational databases that store data in forms other than tables, usually with a flexible schema and easy horizontal scaling. They grew up in the late 2000s when storage got cheap, data got messier, apps needed to iterate fast, and cloud scale-out became normal.
  • Advantages: flexible schema; horizontal scaling by sharding and replica sets; built-in replication for high availability; fast reads and writes when data is shaped like the queries (“data accessed together is stored together”).
  • Disadvantages: duplicated data and costlier updates; weaker or no joins; fewer consistency guarantees in some systems; different tools and query languages; no single type fits every need.
  • Use when: agile development with changing schemas, semi-structured or huge data, scale-out requirements, real-time streaming, micro-services each owning a store.

  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM employees
) t WHERE r = 2 LIMIT 1;

-- c) LIMIT/OFFSET on distinct values; wrap it so you return NULL (not no rows) when it doesn't exist
SELECT (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1) AS second_highest;

2 · Find, then delete, duplicatesasked everywhere

-- find
SELECT email, COUNT(*) AS n FROM users GROUP BY email HAVING COUNT(*) > 1;

-- delete, keeping the lowest id per email (works in MySQL 8 and PostgreSQL)
DELETE FROM users
WHERE id IN (
  SELECT id FROM (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn FROM users
  ) t WHERE rn > 1
);
-- then prevent them:  ALTER TABLE users ADD UNIQUE (email);

7 · Running total and month-over-month changewindow functions

WITH monthly AS (
  SELECT DATE_FORMAT(placed_on, '%Y-%m') AS month, SUM(total) AS revenue   -- PostgreSQL: TO_CHAR(placed_on, 'YYYY-MM')
  FROM orders
  GROUP BY DATE_FORMAT(placed_on, '%Y-%m')
)
SELECT month, revenue,
       SUM(revenue) OVER (ORDER BY month)                                   AS running_total,
       revenue - LAG(revenue) OVER (ORDER BY month)                         AS change_vs_prev,
       ROUND(100 * (revenue - LAG(revenue) OVER (ORDER BY month))
                 / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 1)        AS pct_change
FROM monthly;

-- users whose next order came within 7 days of the previous one
SELECT DISTINCT customer_id

  SELECT customer_id, placed_on,
         LAG(placed_on) OVER (PARTITION BY customer_id ORDER BY placed_on) AS prev_on
  FROM orders

9 · Pivot rows to columns, conditional aggregationno PIVOT keyword needed

SELECT customer_id,
       SUM(CASE WHEN status = 'paid'      THEN total ELSE 0 END) AS paid_total,
       SUM(CASE WHEN status = 'refunded'  THEN total ELSE 0 END) AS refunded_total,
       COUNT(CASE WHEN status = 'pending' THEN 1 END)            AS pending_orders
FROM orders
GROUP BY customer_id;

Rapid-fire concept questionssay the one-liner, then add the edge

QuestionOne-line answer
Primary key vs unique key?Both enforce uniqueness. Primary: not null, one per table, the row identity. Unique: may be NULL, many per table.
Clustered vs non-clustered index?Clustered: the table’s rows are stored in index order (one per table; InnoDB’s primary key). Non-clustered: a separate structure with pointers to rows (many).
WHERE vs HAVING?WHERE filters rows before grouping; HAVING filters groups after, and can use aggregates.
UNION vs UNION ALL?UNION removes duplicates (extra work); UNION ALL keeps them and is faster.
INNER vs LEFT join?INNER keeps only matches; LEFT keeps every left row, filling NULLs for no match.
IN vs EXISTS?IN compares to a list; EXISTS checks for any matching row and stops early. EXISTS is safe with NULLs; NOT IN is not.
COUNT(*) vs COUNT(col) vs COUNT(DISTINCT col)?All rows / non-NULL values / distinct non-NULL values.
CHAR vs VARCHAR?CHAR is fixed length (padded); VARCHAR stores only what is used. VARCHAR in almost every case.
View vs materialized view?A view re-runs its query each time; a materialized view stores the result and must be refreshed.
Procedure vs function vs trigger?Procedure: called, may change data. Function: returns a value, usable in a SELECT. Trigger: fires automatically on a data change.
What is normalisation? Why denormalise?Splitting tables to remove redundancy and anomalies (1NF to BCNF). Denormalise to cut joins for read-heavy paths, accepting duplicates.
What are ACID properties?Atomicity, Consistency, Isolation, Durability: the guarantees of a transaction.
Dirty read vs phantom read?Dirty: reading uncommitted data. Phantom: the same range query returns new or missing rows.
Optimistic vs pessimistic locking?Optimistic: detect conflicts at write time with a version column. Pessimistic: lock rows up front (FOR UPDATE).
What is an index’s downside?Extra storage and slower inserts, updates and deletes, since every index must be maintained.
How do you find and fix a slow query?Slow-query log, EXPLAIN, check for full scans and rows examined, add or reshape an index or rewrite, re-measure.
What is the N+1 query problem?One query for a list, then one per item. Fix with a join or a batched IN, or ORM eager loading.
Sharding vs replication vs partitioning?Replication copies the same data (availability, reads). Partitioning splits a table. Sharding splits it across servers (write and storage scale).
What is CAP?During a network partition you choose consistency or availability; partition tolerance is not optional.
Prevent SQL injection?Parameterised queries, least-privilege DB users, allow-list identifiers, never build SQL from strings.
Soft delete vs hard delete?Soft: set deleted_at and filter it out (recoverable, but every query must filter and uniques get tricky). Hard: remove the row.

Quick checkanswers folded away

1. Which key is a minimal super key, and what happens to the candidate keys you don’t pick as primary?

A candidate key is a minimal super key. The ones not chosen as primary are alternate keys (usually given a UNIQUE constraint).

2. A LEFT JOIN with WHERE o.total > 100 returns no customers without orders. Why?

Unmatched rows have NULL o.total, which fails the WHERE test, turning the left join into an inner join. Move the condition into the ON clause.

3. SELECT * FROM t WHERE x NOT IN (SELECT y FROM u) returns nothing. What is probably wrong?

u.y contains a NULL, so every comparison is UNKNOWN. Use NOT EXISTS or filter the NULLs out.

4. What is the logical execution order of a SELECT?

FROM/JOIN, WHERE, GROUP BY, HAVING, window functions, SELECT, DISTINCT, ORDER BY, LIMIT.

5. Which normal form removes partial dependencies? Transitive ones?

2NF removes partial dependencies on part of a composite key; 3NF removes transitive dependencies between non-key columns.

6. Rows with salary 9000, 9000, 7000: what do RANK and DENSE_RANK give the 7000 row?

RANK = 3 (a gap after the tie); DENSE_RANK = 2.

7. Why does WHERE YEAR(placed_on) = 2025 ignore the index on placed_on?

A function on the column makes the value computed per row, so the sorted index can’t be searched. Use a range: placed_on >= '2025-01-01' AND placed_on < '2026-01-01'.

8. An index is on (a, b, c). Which of WHERE b = 1, WHERE a = 1 AND c = 2 can use it?

Leftmost-prefix rule: b = 1 alone cannot. a = 1 AND c = 2 can use the index for a only (and filter c afterwards).

9. What does each ACID letter protect against?

Atomicity: partial updates. Consistency: invalid states. Isolation: concurrent interference. Durability: loss after a crash.

10. Which isolation level is the default in MySQL InnoDB, and in PostgreSQL?

MySQL InnoDB: REPEATABLE READ. PostgreSQL: READ COMMITTED.

11. Name two costs of sharding.

Cross-shard joins and transactions are hard; re-sharding and hot shards; a routing layer; scatter-gather queries without the shard key.

12. What do you choose during a partition in a banking system, and in a social feed?

Banking: consistency (CP), refusing some requests. Social feed: availability (AP) with eventual consistency.
