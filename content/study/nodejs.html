What is Node.js? A short historyNotes ep-1

In plain words. Before Node, JavaScript was a chef who could only cook in the browser’s kitchen. Ryan Dahl took the chef’s engine out of that kitchen so it could cook on any laptop or server, and he built it so the chef never stands idle waiting for the oven.
  • Node.js = JavaScript runtime built on Chrome’s V8 engine
  • Built by Ryan Dahl in 2009; maintained by the OpenJS Foundation
  • Executes JavaScript outside the web browser: “Run JavaScript everywhere”
  • To run JS you always need a JS engine. Ryan began with SpiderMonkey (Firefox), then switched to V8 within two days
  • Joyent, a company building something similar, hired Ryan and funded the project
  • Original name: web.js; renamed Node.js because its scope goes beyond web servers
  • Why it exists: the Apache HTTP Server was a blocking server, so Ryan wanted a non-blocking I/O one that handles many requests with fewer threads

Node.js: JS on the serverNotes ep-2

  • Node lets developers use JavaScript on the client and the server: one language, one ecosystem
  • A server is just a remote computer (a CPU working remotely) that provides resources and services over a network
  • V8 (Google): open-source, high-performance JavaScript and WebAssembly engine written in C++; used in Chrome and Node; cross-platform; embeddable in any C++ application

V8 deep dive: from code to executionNotes ep-8

  • 1. Parsing: lexical analysis (tokenization) breaks code into tokens; syntax analysis turns tokens into an AST (Abstract Syntax Tree)
  • 2. Interpreter (Ignition) converts the AST to bytecode, which is executed; garbage collection runs alongside
  • 3. Optimization: if Ignition spots hot code, it passes it to the TurboFan compiler, which makes optimised machine code that is executed
  • 4. Deoptimization: if the optimised code can’t hold, Ignition turns it back to bytecode and runs that

JavaScript is synchronous and single-threadedNotes ep-6

  • Synchronous = one after another. V8 runs code as soon as it’s sent; line 4 runs after line 3
  • JS needs only one thread to run
  • In synchronous programming, execution is blocked until the current task finishes
  • Inefficient for I/O-bound tasks (file reading, network requests): it can block the entire thread
⚠ imprecise in the notes. “It can run on a single thread or a single process.” A thread and a process are different things: JavaScript runs on one thread inside a Node process.

How sync and async code really executeNotes ep-6

  • Sync run: a Global Execution Context (GEC) is pushed on the call stack; each function call gets its own context on top; values live in the memory heap; when a function finishes, its result returns to the GEC and it leaves the stack. At the end the stack is empty and the garbage collector cleans the heap
  • libuv = a multiplatform C library providing async, event-loop-based I/O: “Asynchronous I/O made simple”
  • Whenever V8 sees an API call, file read or setTimeout, it offloads it to libuv; libuv registers it and keeps the callback while V8 moves to the next line
  • When libuv finishes a task and sees the call stack is empty, it puts the callback on the call stack and V8 runs it quickly
  • So even with a single thread, Node does many async operations together

The event loop+ gap topic

+ added
In plain words. The event loop is one waiter in a busy restaurant. He takes an order, hands it to the kitchen (the OS or thread pool), and immediately takes the next table’s order. When the kitchen rings the bell, he delivers the dish. He is never standing idle at the kitchen door, unless he stops to cook himself, and then every table waits.
  • Phases in order: timers → pending callbacks → poll (I/O) → check (setImmediate) → close callbacks, then around again
  • Between callbacks, Node empties the process.nextTick queue, then the promise microtask queue
  • setTimeout(fn, 0) means “not before 1 ms”, never “right now”
  • If poll has nothing to do, it waits for I/O; if setImmediate is queued, it moves on to check

libuv & the event loopNotes ep-9

In plain words. The event loop is a supervisor with a clipboard, walking round the same five stations again and again. At each station he empties that station’s queue, and between every stop he handles anything marked urgent.
  • While V8’s call stack is busy, libuv collects finished async tasks in the callback queue
  • The event loop’s job: keep checking the call stack and callback queue, and run the right thing, at the right time, in the right order (FIFO per queue)
  • Before every phase, process.nextTick() and promise callbacks run (the notes draw them in the middle of the cycle)
  • One full cycle of the event loop = one tick
  • JavaScript itself stays “a synchronous single-threaded language”; async I/O is handled by libuv + the OS

Thread pool, and “single- or multi-threaded?”Notes ep-10

  • libuv’s thread pool has 4 threads by default (UV_THREADPOOL_SIZE = 4)
  • It is used for: fs, dns lookup, crypto, user-specified input
  • Networking happens on sockets; API calls do not use the thread pool. libuv talks to the OS through epoll (Linux) and kqueue (macOS): scalable I/O event notification mechanisms
  • Is Node single- or multi-threaded? If you give it a synchronous task it is single-threaded; for async tasks it uses libuv’s 4-thread pool and acts multi-threaded. The answer: “it depends” on the task
  • Change the size: process.env.UV_THREADPOOL_SIZE = 8;

How require() works behind the scenesNotes ep-5

In plain words. require is a librarian. She finds the book (resolve), opens it (load), puts it in a private reading room so it can’t scribble on other books (wrap), reads it out (evaluate), and keeps a copy at the desk so the next person gets it instantly (cache).
  • 1. Resolving: Node finds the path: a local file (./local), a JSON file, or a module in node_modules, among other possibilities
  • 2. Loading: the file content is loaded; the process varies for JavaScript, JSON or other types
  • 3. Wrapping in an IIFE: the module code is wrapped in an Immediately Invoked Function Expression, which keeps its variables and functions private
  • 4. Evaluation: the wrapped code runs; module.exports is set and becomes visible to other files
  • 5. Caching (very important): the result of require() is cached, so a module loads and executes only once
  • Why can’t we reach another file’s variables? All of a module’s code is wrapped inside a function when you require it
  • IIFE = Immediately Invoked Function Expression. Node passes module and require in as parameters, then hands the wrapped code to V8, which knows how to run an IIFE

export async function retry(fn, { retries = 3, delayMs = 200 } = {}) {
  let lastErr;
  for (let i = 0; i <= retries; i++) {
    try { return await fn(i); }
    catch (err) {
      lastErr = err;
      await new Promise((r) => setTimeout(r, delayMs * 2 ** i)); // backoff
    }
  }
  throw lastErr;
}

Controllers & the request/response cycleRef §9

In plain words. A controller is the clerk at the counter: reads the form you handed in, checks it’s filled out, looks up the records, does the job, and slides back a receipt.
  • A controller reads from req, talks to models, writes to res
  • Six-step shape, used by every controller: read → validate → check rules → side effects → persist → respond

src/controllers/user.controller.js

const registerUser = asyncHandler(async (req, res) => {
  // 1. Read input
  const { fullName, email, username, password } = req.body;

  // 2. Validate
  if ([fullName, email, username, password].some((f) => f?.trim() === "")) {
    throw new ApiError(400, "All fields are required");
  }

  // 3. Business rules: uniqueness
  const existedUser = await User.findOne({ $or: [{ username }, { email }] });
  if (existedUser) throw new ApiError(409, "User with email or username already exists");

  // 4. Side effects: file uploads
  const avatarLocalPath = req.files?.avatar[0]?.path;
  const avatar = await uploadOnCloudinary(avatarLocalPath);

  // 5. Persist
  const user = await User.create({ fullName, email, password, username, avatar: avatar.url, ... });

  // 6. Respond (without sensitive fields)
  const createdUser = await User.findById(user._id).select("-password -refreshToken");
  return res.status(201).json(new ApiResponse(201, createdUser, "User registered Successfully"));
});

⚠ possible error (step 4). req.files?.avatar[0] throws a TypeError when no avatar was sent, because avatar is undefined. Use req.files?.avatar?.[0]?.path, then reject with a 400 if it is missing.

export function rateLimit({ windowMs = 60_000, max = 5 } = {}) {
  return (req, res, next) => {
    const now = Date.now();
    const rec = hits.get(req.ip);
    if (!rec || now > rec.resetAt) {
      hits.set(req.ip, { count: 1, resetAt: now + windowMs });
      return next();
    }
    if (++rec.count > max) {
      res.set('Retry-After', String(Math.ceil((rec.resetAt - now) / 1000)));
      return res.status(429).json({ message: 'Too many requests' });
    }
    next();
  };
}

Password hashing with bcryptRef §17

In plain words. Hashing is a meat grinder: easy to turn a steak into mince, impossible to turn the mince back. You can’t recover the password, you can only grind a guess the same way and compare the mince.
  • Never store plaintext passwords. bcrypt is a slow, salted hash designed to resist brute force
  • Cost factor 10 = 2^10 rounds: slows attackers, keeps login under a few hundred ms. Tune upward as hardware improves
  • The !this.isModified("password") guard stops re-hashing an already-hashed password on every update
userSchema.pre("save", async function (next) {
  if (!this.isModified("password")) return next();   // important guard
  this.password = await bcrypt.hash(this.password, 10);
  next();
});

userSchema.methods.isPasswordCorrect = async function (password) {
  return await bcrypt.compare(password, this.password);
};
save() hashes on the way in; isPasswordCorrect() compares a login attempt to the hash
+ added
  • bcrypt only reads the first 72 bytes of a password; very long passphrases are silently truncated
  • Many guides now prefer argon2id; Node also ships crypto.scrypt. I did not re-check the current OWASP cost recommendations
  • Use the same error for “no such user” and “wrong password”, so attackers can’t discover which emails exist

Unsafe: storing password as sent, or comparing with ===. Also never log request bodies from the login route.

export const verifyJWT = asyncHandler(async (req, _, next) => {
  try {
    const token =
      req.cookies?.accessToken ||
      req.header("Authorization")?.replace("Bearer ", "");

    if (!token) throw new ApiError(401, "Unauthorized request");

    const decodedToken = jwt.verify(token, process.env.ACCESS_TOKEN_SECRET);

});

Error handling patternsRef §21

In plain words. When something goes wrong in a kitchen, a good cook doesn’t drop the plate and run. He calls “error!”, a manager catches it in one place, and the customer gets a polite, consistent apology.

async function rateLimit(req, res, next) {
  const id = req.user?.id ?? req.ip;                       // set app.set('trust proxy', 1) behind a proxy
  const windowSec = 60, max = 100;
  const key = `rl:${id}:${Math.floor(Date.now() / 1000 / windowSec)}`;

  const count = await redis.incr(key);                     // atomic across all servers

  if (count > max) {

    return res.status(429).json({ error: 'Too many requests' });
  }
  next();
}

  size() { return this.a.length; }
  push(x) {
    const a = this.a; a.push(x);
    let i = a.length - 1;
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (this.cmp(a[i], a[p]) >= 0) break;
      [a[i], a[p]] = [a[p], a[i]]; i = p;
    }
  }
  pop() {
    const a = this.a, top = a[0], last = a.pop();
    if (a.length) {
      a[0] = last;
      let i = 0;
      for (;;) {
        const l = 2 * i + 1, r = l + 1; let m = i;
        if (l < a.length && this.cmp(a[l], a[m]) < 0) m = l;
        if (r < a.length && this.cmp(a[r], a[m]) < 0) m = r;
        if (m === i) break;
        [a[i], a[m]] = [a[m], a[i]]; i = m;
      }
    }
    return top;
  }
}

function topK(events, k) {
  const counts = new Map();
  for (const e of events) counts.set(e, (counts.get(e) ?? 0) + 1);

  const heap = new MinHeap((x, y) => x[1] - y[1]);          // smallest count at the top
  for (const entry of counts) {
    heap.push(entry);
    if (heap.size() > k) heap.pop();                        // drop the least frequent of the K+1
  }
  return heap.a.sort((x, y) => y[1] - x[1]);                // [[event, count], …] highest first
}
// topK(['a','b','a','c','a','b'], 2) → [['a',3], ['b',2]]
  • Alternative: bucket sort by count (counts are at most n): O(n) time, more memory
  • Why not sort everything: O(u log u) when you only need K; the heap does O(u log K)
  • Unbounded stream: Space-Saving or Count-Min Sketch + a small heap give approximate top-K in fixed memory
  • “Top K in the last hour”: keep counts per time bucket (for example per minute) and expire old buckets
  • Distributed: each shard sends its local counts or top-K, a coordinator merges; exact answers need counts (or K large enough) from every shard, because a global heavy hitter can be mid-ranked locally

1 · What prints, and in what order?

// CommonJS
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
process.nextTick(() => console.log('D'));
(async () => { console.log('E'); await null; console.log('F'); })();
console.log('G');
Show answer

A E G D C F B. Sync code first: A, E (the async function runs synchronously until its first await), G. Then the nextTick queue: D. Then promise microtasks in the order they were queued: C, then F. Last, the timer: B. (In an ES module the promise callbacks may come before D.)

2 · What’s wrong with this Express code?

app.get('/user/:id', async (req, res) => {
  const user = await User.findOne({ _id: req.params.id });
  if (!user) res.status(404).json({ error: 'not found' });
  res.json(user);
});
Show answer
  • No return after the 404, so it also runs res.json(user): ERR_HTTP_HEADERS_SENT
  • An invalid id throws a Mongoose CastError; validate with mongoose.isValidObjectId and answer 400
  • On Express 4 the rejection isn’t forwarded: wrap in asyncHandler
  • Returns the whole user document, maybe including password; use .select("-password -refreshToken")
  • Error body shape differs from ApiError/ApiResponse

3 · When do you pick cluster over worker_threads?

Show answer

cluster to use all cores for a server: many copies of the app share one port. worker_threads to move a CPU-heavy task off the main thread inside one process. Trade-off: cluster workers don’t share memory, so shared state goes to Redis or the DB.

4 · 401 or 403? A logged-in user opens an admin-only route.

Show answer

403. The server knows who they are (authenticated) but they aren’t allowed (authorization). 401 is for a missing or invalid token.

5 · Why use createReadStream to send a 5 GB file?

Show answer

readFile would load all 5 GB into memory before sending a byte. A stream moves it in small chunks, starts immediately, and backpressure keeps memory flat. Use pipeline so errors and cleanup are handled.
